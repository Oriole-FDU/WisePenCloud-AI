# 调研路径：从一次搜索委派到团队协作

先读 [架构对比](05-architecture-comparison.md) 与 [搜索协作案例](06-search-collaboration-walkthrough.md)
，再看 [Codex 实现专篇](02-codex-multi-agent.md) 和 [DeepSeek 实现专篇](03-deepseek-multi-agent.md)
。这些正文已经解释实现思路；本文件安排理解之后的源码核验、继续深入和实验顺序。

本项目的启动操作另见 [实验启动说明](01-experiment-startup.md)。下面的阅读产物用于巩固和验证，不要求先读源码才能理解报告。

## 1. 从一个搜索任务画出最短链路

使用同一个贯穿例子：主代理需要比较几个项目的某项能力，让每个子代理调查一个项目的官方来源，最后合并带来源的结论。

先不讨论 Team、任务数据库或 UI。画出用户输入、主代理上下文、模型委派调用、子代理输入、搜索结果、子代理完成消息和主代理答案。分别找出两套实现在哪一步建立新的会话/上下文。

本阶段只需回答： **“给子代理一段任务”与“复制主代理历史后继续执行”分别在哪里发生？**

## 2. 先理解 Prompt / Context，再读创建子代理

| 阅读对象                                      | 要找的事实                                                 | 阅读产物             |
|-----------------------------------------------|------------------------------------------------------------|----------------------|
| Codex 的 turn/context 路径与 V2 spawn         | fresh 与 fork 的历史、开发者指令、工具、模型设置各来自哪里 | 一张父子上下文差异表 |
| DeepSeek 的 activation 与 spawn/fork Provider | 父 Agent、组合配置、事件历史和输出合同如何传入子级         | 同一张表的另一列     |

不要从 `clone`、`fork` 的字面含义推断深拷贝或所有状态共享。沿调用点确认共享资源、独立历史和快照边界。Rust 中区分普通值的复制与
`Arc` 句柄共享；可用 Python 中“复制列表”和“多个对象持有同一引用”帮助理解，但以实际类型为准。

## 3. 跟一次创建、消息和等待

沿两份源码图给出的调用链，各追踪一个完整例子：创建子级 → 注册身份 → 提交初始任务 → 返回控制 → 接收完成结果。

接着只改变一项：父代理给已经存在的子代理再发一条消息。

需要逐项写清：

- 消息只入队，还是会启动一个新轮次？正在运行和闲置的目标是否不同？
- 能否向同级、祖先或其他会话发送？权限判断在哪里？
- `send_message`、`followup_task`、`wait`、`interrupt` 分别改变什么状态？不要把不同系统的同名工具当成相同语义。
- 父代理离开一次等待，是否意味着子代理被取消？取消会作用于当前 activation、整个会话还是后代？
- 完成结果写入哪个会话的历史，何时对模型可见，恢复后是否可能重复送达？

本阶段产物是一张时间线，不必遍历所有边界分支。先读相应测试了解预期，再读实现解释原因；此时无需先编译整个 Codex 或搭建
DeepSeek 的全部 UI。

## 4. 再比较 Team 与普通委派

DeepSeek 单独阅读实验性的 Agent Team 领域、模型工具和共享任务 DAG；Codex 则先确认该快照实际提供哪些树形协作、消息和身份能力。只有找到对应领域对象，才将它们纳入同一比较列。

报告已经给出下列基线结论。继续读源码时，可围绕对应边界增加证据，而不是从零猜测各对象的意义：

| 维度     | Codex 本地 V2                                               | DeepSeek 的本地 subagent / Team                                        |
|----------|-------------------------------------------------------------|------------------------------------------------------------------------|
| 身份     | ThreadId、AgentPath 和父子关系                              | 本地 child Session；TeamId 等于 root SessionId，另有 roster            |
| 生命周期 | 线程身份、驻留 runtime、活跃 turn 分层                      | 稳定子会话与一次 activation 分层；Team 建员 phase 另行持久化           |
| 任务     | 所读 native 主链没有共享认领任务领域对象                    | Team 有 owner、revision/CAS 与 blockedBy DAG；更新任务不会自动驱动模型 |
| 消息     | QueueOnly 和 TriggerTurn 分开；消费/历史/rollout 需分层追踪 | 本地消息与 Team peer Steer 可唤醒；Team journal 与目标 inbox 职责分开  |
| 并发     | 活跃执行和驻留容量分开，不能当成任务队列                    | activation 树容量与 Team 成员/任务上限分开                             |
| 写入协调 | 线程路径不能证明文件隔离                                    | Team 当前共享 checkout，writeScopes 提供提示和警告                     |
| 恢复     | 线程关系与历史可恢复，本地 mailbox/通知有具体边界           | Team 重放 Lead roster/task 并核对 child 证据，消息按目标正常策略恢复   |

共享任务板、消息投递和运行调度是三个责任，分别追踪。界面里的成员列表或任务列表不自动代表调度器。

## 5. 回到工具调用与输出处理

阅读模型可见 schema、工具注册和执行入口，再追到子代理如何获得搜索工具。特别检查任务文本是否能越过宿主授权边界，以及输出进入父代理时是否保持来源。

映射到 WisePen 时，从已有 `ToolRegistry`、`ToolScope`、`McpRemoteTool` 和 `system_default_web_search` 开始。沿用现有 MCP
搜索服务、缓存信封和工具输出读取机制；基础设施继续照常使用。这一步先写职责映射和差异，不直接迁移一整套外部框架。

推荐的阅读产物只有三项：工具合同草图、父子上下文边界、完成/消息/取消时序。确认后再决定第一段实现。

## 6. 后续搜索实验的递进路线

以下是后续可执行实验的规划，本次没有运行这些实验，也没有创建相应多代理实现。

| 阶段            | 只改变的条件                                   | 观察结果                                     |
|-----------------|------------------------------------------------|----------------------------------------------|
| A：单代理基线   | 固定一小组需多来源综合的搜索问题，使用现有工具 | 答案、引用、检索调用数、耗时和模型 token     |
| B：fresh 子代理 | 加入独立子任务的委派与结果汇总                 | 分工是否独立，是否重复搜索，汇总是否丢失来源 |
| C：fork 上下文  | 在同一任务和模型条件下比较 fresh/fork          | 继承历史的收益、污染、额外 token 与重复事实  |
| D：持续协作     | 只在确需补充研究的题目中加入后续消息           | 消息是否唤醒正确目标，能否复用已有研究结果   |
| E：Team 任务板  | 只在任务间确有依赖或共享认领需求时引入         | 共享任务是否比父代理直接分配更有价值         |
| F：生命周期     | 针对已选择方案验证取消、完成和恢复             | 无悬挂执行、结果可追踪、恢复不会重复发布     |

比较时固定问题集、模型/Provider、搜索数据条件和总预算，记录并发数及 fresh/fork；不能把“多用了搜索预算”直接当成多代理设计收益。使用现有
Nacos、Mongo、Kafka、Redis 等记录与运行能力，避免将实验变成基础设施替换项目。

第一轮评估优先关注来源支持的答案质量、遗漏事实、冲突事实与重复工作，再看延迟和成本。先保存原始工具调用与结果，让后续结论能够回查；不先建设通用评测平台。
