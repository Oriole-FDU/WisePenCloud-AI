# RAG V4 问题与根因

## 0. 文档目的

本文件是对 `00-rag-v4-restructure-plan.md` 的事实核对，不是新的目标架构，也不开始实现 `rag_v4`。目标是确认旧实现中哪些问题确实存在、它们为什么出现，以及后续讨论应按什么顺序收敛。

核对范围：

- 原实现：`services/wisepen-rag-service/src/rag/` 及其测试；
- 现有 Common 检索实现：`services/wisepen-common/src/common/utils/retrieval/`；
- 参考实现：`services/rag/references/LightRAG/`、`services/rag/references/llama_index/`。

本文把“代码已经证明的问题”和“00 计划提出但尚未决定的设计”分开。没有消费者、生产者或测试证据的字段和接口，不在本文件中当作既定合同。

## 1. 核对结论

当前实现不是一个可以继续局部修补的完整 RAG 链路。问题集中在三层：

1. **资源隔离和权威事实没有形成可证明的边界**：可信用户身份已经由 Common/MCP 链路自动注入，但所有 RAG 事实和投影仍以 `resource_id` 为主要键；ACL、资源 ID 命名空间、active revision 和投影读取之间没有形成一个可验证的请求边界。
2. **核心流程在中途断开**：检索上下文增强和 dynamic parent 尚未实现，文档检索命中后仍会抛出迁移异常；图谱索引是独立调用，发布状态没有统一的投影生命周期。
3. **接口按照当前用例堆叠，而不是按照能力分界**：向量和图拓扑 repository 同时承担 provider CRUD、检索策略、ACL 过滤、revision 生命周期和投影完整性；插件又进入通用 chunk 摄入和序列化链路。

因此，后续不应从 `VectorStorage`、`GraphStorage` 或 LightRAG prompt 直接开始。第一步必须先把可信身份、资源 ACL、revision、active 可见性和失败语义说清楚，再冻结 `DocChunk` 与最小读写事实。

## 2. 当前实现基线

| 链路 | 当前事实 | 主要入口 |
|---|---|---|
| 文档事件 | Kafka payload 包含 `resourceId`、`version`、`content`；handler 直接构造 `ContentRevision` | `api/kafka.py`、`application/events.py` |
| 摄入 | `MarkdownChunker` 产生 Common chunk，`DocumentPreparer` 重写 section/chunk ID，保存 Mongo staged 事实 | `application/document/preparation.py` |
| 文档索引 | `DocumentIndexBuilder` 读取 staged revision，生成 dense embedding，调用一个 `DocumentVectorRepository.write_revision()`，然后 apply | `application/document/indexing.py` |
| 文档检索 | Qdrant dense/BM25 各取候选，RAG 自己做 chunk 并集，再调用 `common.utils.ranking.RankingPipeline` | `application/retrieval/hybrid_retriever.py` |
| 图谱事实 | 自定义 Instructor/Pydantic 抽取、ontology 校验、跨 chunk 合并和 `GraphChunkSource` 写入 Mongo | `application/graph/graph_fact_builder.py` |
| 图谱投影 | 另一个 builder 把 Mongo facts 写入 Neo4j、节点 Qdrant、边 Qdrant | `application/graph/graph_indexing.py` |
| 读取 | 通过 index state 找 active revision，再批量读取文档和本地 ACL，最后在内存判权 | `application/snapshot.py`、`application/reading.py`、`application/outline.py` |
| 组合根 | 一个 `Container` 直接构造全部客户端、仓储、builder、retriever 和 endpoint 依赖 | `container.py` |

当前 `pyproject.toml` 的 wheel 仍只打包 `src/rag`。`src/rag_v4` 尚不存在，这证明 00 计划的重构目录还是未来方案，不是当前实现的一部分。

## 3. 已确认的问题与根因

### P0-1：可信身份已存在，但 RAG 资源隔离合同未闭合

**现象和证据**

- Common 已有可信身份链：Chat 的 `McpServiceClient` 从 `SecurityContextHolder` 读取用户和群组角色并通过受保护请求头传递；接收端 `SecurityHeaderMiddleware` 校验 `X-From-Source` 后写回 `SecurityContextHolder`。MCP 工具读取的是该安全上下文，而不是调用参数中的 `user_id`：`services/wisepen-chat-service/src/chat/service_client/mcp_service_client.py`、`services/wisepen-common/src/common/web/middleware/security_header.py`、`services/wisepen-mcp-service/src/wisepen_mcp/capabilities/core/tool_metadata.py`。
- RAG 的 `PermissionScope` 只有 `user_id` 和 `group_roles`，没有 tenant/workspace 字段：`src/rag/domain/acl.py`。这不是“用户身份未注入”的证据，而是 RAG 当前只声明了资源级 ACL 维度。
- `ContentRevision`、`Document`、`DocChunk`、`ResourceAcl`、`ResourceIndexState` 都以 `resource_id` 为外部身份；Mongo 实体的唯一索引也只有 `resource_id` 或 `resource_id + content_revision`：`src/rag/application/document/models.py`、`src/rag/domain/entities/*.py`。
- Qdrant 的 payload 和删除/查询过滤以 `resource_id`、ACL 展平字段为主，没有 tenant/workspace predicate：`src/rag/core/persistence/qdrant/common.py`、`document_vector_repository.py`、`graph_vector_repository.py`。
- Neo4j 的 source predicate 只过滤 ACL、`resource_id` 和 metadata：`src/rag/core/persistence/neo4j/graph_topology_repository.py`。
- 旧 RAG HTTP 入口只从安全上下文中的登录用户和网关群组角色构造 `PermissionScope`：`src/rag/api/endpoints/common.py`；旧入口没有 tenant/workspace 上下文，也没有 MCP capability 层的显式适配。

**根因**

旧实现把“资源 ID 全局唯一”和“ACL 足以隔离所有请求”当作隐含前提，没有把这两个前提写成 RAG 可验证的合同。LightRAG 参考实现明确把 workspace 带入 storage namespace/payload/filter；当前 RAG 只借鉴了资源级 ACL。可信用户身份解决了调用方伪造 `user_id` 的问题，但不会自动证明资源 ID 是否全局唯一，也不会自动让 Mongo、Qdrant、Neo4j 的所有读取都执行同一套 ACL 语义。

**影响**

平台已经确认资源 ID、用户 ID 和群组 ID 全局唯一，因此不把“跨租户 ID 碰撞”作为本项目的待解决问题；但这个唯一性仍应作为可测试的平台输入合同，约束未来 provider、重建任务和批量 API。另一个独立问题是，未来 MCP capability、RAG application 和后台 Kafka 消费者必须明确哪些路径使用可信请求身份，哪些路径使用事件中的资源 ACL；不能把调用参数中的 `user_id` 当成安全来源。

**已确认的子方案入口**

资源、用户、群组 ID 全局唯一，不新增 tenant/workspace 字段。RAG 只接受 MCP 适配层从可信 `SecurityContextHolder` 构造的 `PermissionScope`；工具参数不接收 `user_id`、群组角色或任意 ACL；上游 Resource ACL 是权威来源，RAG 保存可重建投影，查询必须在最终资源回查时建立 ACL 快照并 fail-closed 判权。具体合同见 [02-可信身份与 ACL 边界.md](02-可信身份与%20ACL%20边界.md)。

### P0-2：active revision 与 ACL 的一致性语义未定义，且各路径重复实现

**现象和证据**

- `ActiveDocumentSnapshotLoader.load_documents()` 先读 index states，再读 documents 和 ACL，最后在 Python 中比较：`src/rag/application/snapshot.py:38-77`。
- `locate_sections()` 先按 section 查询候选文档，再分别读 state/ACL，仍没有 revision/ACL 版本 fence：`snapshot.py:79-118`。
- `HybridRetriever._load_visible_chunks()` 重复实现一套流程：先并行读 state/ACL，再读 active documents，再逐 chunk 判权：`src/rag/application/retrieval/hybrid_retriever.py:231-270`。
- `GraphRetriever` 也有自己的 `_visible_sources()` 和候选回查路径，未复用同一个 snapshot 对象。

**根因**

“snapshot”目前只是多个批量读取后的 Python 变量集合，代码没有声明这些读取需要达到哪一级一致性。状态、ACL、正文和索引候选分别由不同 repository 读取，查询过程中没有统一的版本自洽规则；授权表达式又在 `ResourceAcl.can_read()`、Qdrant filter 和 Neo4j predicate 中重复维护。

这不是“所有事实必须处于同一时间点”的证明。Mongo、Qdrant、Neo4j 不具备天然的跨后端原子观察点，ACL 与内容版本也有独立生命周期。真正需要先区分的是：内容混版和 ACL 绕过属于不可接受的正确性问题；active 在请求期间切换、ACL 投影短暂落后和批量中单资源异常，则需要产品和运维合同决定容忍度。

**影响**

当前代码至少存在两类已确认风险：候选 Chunk、Document 和 active revision 可能没有由统一 capability 约束，导致内容混版；不同入口可能使用不同的 ACL 预过滤和回查语义，导致授权绕过或不必要的拒绝。至于请求是否必须看到最新 active revision、ACL 延迟允许多长、单资源异常是否中断整批，当前计划尚未定义，不能直接用 Fence、事务或重试代替这些决策。

**后续讨论**

先确定三个合同：一致性边界（强一致、版本自洽、最终一致分别覆盖哪些事实）、系统责任边界（上游提供哪些 ACL 版本与事件顺序保证，RAG 只消费哪些保证）、业务容错边界（ACL 延迟、请求开始时固定 active revision、部分结果和异常策略）。统一 snapshot capability 的价值是消除入口间语义漂移，不是承诺跨后端强一致。

### P0-3：发布、投影和删除没有统一的生命周期事实

**现象和证据**

- `DocumentPublication.apply_revision()` 只检查 Mongo 文档、DocChunk 和 `DocumentVectorRepository.is_complete()`，随后更新 applied 指针：`src/rag/application/publication/document_publication.py`。
- `DocumentReadyHandler` 只调用 `DocumentPreparer` 和 `DocumentIndexBuilder`，没有调用 `GraphFactBuilder` 或 `GraphIndexBuilder`：`src/rag/application/events.py:15-43`。
- 图谱 builder 只能在 revision 已经 active 后单独运行，并且每次写 Neo4j、节点 Qdrant、边 Qdrant 前后分别检查 active：`src/rag/application/graph/graph_indexing.py:77-171`。
- `ResourceDestroyHandler` 在清除可见性后同步删除三个外部投影；没有 projection manifest、清理任务实体或按投影记录的重试状态：`src/rag/application/events.py:54-84`。

**根因**

当前 `ResourceIndexState` 只知道 staged/applied 文档指针，不知道每个 projection 的期望记录、完成状态、失败状态和重建任务。投影完整性通过 provider-specific 的 `is_complete()` 询问，删除则由事件 handler 直接串行调用多个外部服务；跨 Mongo/Qdrant/Neo4j 没有可恢复的应用级生命周期事实。

**影响**

文档 active 可以成功而图谱事实/拓扑/图向量缺失或落后；某个删除投影失败时，Kafka 重试只能重放整个 handler，无法记录哪个投影已完成。旧投影可能在 active 切换或删除之后继续存在，查询只能依赖过滤而不是可观察的清理状态。

**后续必须讨论**

明确“文档可用”和“图谱可用”是核心与附加能力，分别需要什么状态、重试和告警；再决定是否引入 projection manifest、任务表或 outbox。不能先把所有 provider 方法抬到一个通用 storage 接口。

### P0-4：检索上下文与返回父块是硬断点

**现象和证据**

- `DocumentIndexBuilder._enhance()` 在 `enhancement_enabled=True` 时无条件抛出 `ContextMigrationRequired`，`_generate_retrieval_context()` 也是只抛异常的 `NoReturn`：`src/rag/application/document/indexing.py:135-162`。
- `HybridRetriever._build_dynamic_parents()` 无条件抛出同一异常；它位于完成召回、回查、精排之后的必经路径：`src/rag/application/retrieval/hybrid_retriever.py:180-197`。
- 测试明确把这个异常当作当前合同：`tests/application/document/test_context_migration.py`。
- `tests/application/retrieval/test_context_expander.py` 导入 `rag.application.retrieval.context_expander`，但当前源码目录没有该文件；测试收集因此不能代表上下文能力已实现。

**根因**

旧的 span/parent 方案被主动撤出后，新的连续 Markdown context builder 和 dynamic parent assembler 没有接入 ingestion/retrieval 主流程。图谱 target-only context 已有一个独立函数，但普通检索 context 没有实现。

**影响**

默认关闭增强时可以生成向量，但开启增强会在索引阶段失败；即使召回和 rerank 成功，Hybrid HTTP 请求也会在父块构建阶段失败。当前没有“部分能力成功”的对外合同，容易把基础检索和附加阅读能力绑死。

**后续必须讨论**

先定义 `DocChunk -> retrieval text`、连续窗口预算和 parent 响应的最小行为，再决定是否需要一个轻量 `ContextExpander`。图谱抽取必须继续 target-only，不能用普通检索前缀替代证据边界。

### P1-1：RAG 仍维护一套独立的旧检索合同

**现象和证据**

- RAG 的 container、HybridRetriever、GraphRetriever 和响应模型都导入 `common.utils.ranking` 的 `RankCandidate`、`RankDecision`、`RankingPipeline`：`src/rag/container.py`、`src/rag/application/retrieval/*.py`。
- `DocumentVectorRepository` 暴露 `search_dense`、`search_bm25`、`write_revision`、`is_complete`，HybridRetriever 在应用层自己做两路候选并集：`src/rag/domain/repositories/document_vectors.py`、`hybrid_retriever.py:294-323`。
- Common 的 `common.utils.retrieval` 已有 `Candidate`、`Retriever`、`FusionRetriever`、`RoundRobinFusion`、`RrfFusion`，但当前 RAG 没有适配它。

**根因**

Common 检索迁移和 RAG 迁移被分开回退，RAG 保留了旧的 ranking 和 provider-specific candidate contract；新的 Fusion 能力没有在 RAG 边界建立 adapter。

**影响**

候选、Fusion、rank 和最终结果在 Chat/Common/RAG 之间语义不一致；Dense/BM25 的 scope、ACL、Mongo 回查和领域结果转换无法与通用 Fusion 组合验证。继续在旧接口上补丁会同时扩大两套契约。

**后续必须讨论**

冻结 RAG 的中间候选和最终结果边界，确认 Common `Candidate`/`RankedCandidate` 只承载通用检索事实；Qdrant 查询策略、ACL 和正文回查留在 RAG adapter/application。

### P1-2：repository 同时拥有 provider 原语、策略和业务生命周期

**现象和证据**

- `DocumentVectorRepository` 同时负责写 revision、删除资源、判断完整性、Dense/BM25 查询，并接收 `PermissionScope`、`ResourceAcl` 和 metadata filter：`src/rag/domain/repositories/document_vectors.py:23-60`。
- `GraphTopologyRepository` 同时负责 replace/delete、遍历候选、ACL scope、资源范围、关系/节点过滤和方向/深度：`src/rag/domain/repositories/graph_topology.py:52-80`。
- Qdrant repository 直接序列化 ACL、构造权限 filter、建立 collection、写入/查询/删除；Neo4j repository直接拼接 ACL 和 metadata predicate：`src/rag/core/persistence/qdrant/*.py`、`src/rag/core/persistence/neo4j/graph_topology_repository.py`。
- `Container` 需要同时装配所有 provider client、应用 builder、retriever、ranking 和 plugin registry：`src/rag/container.py:78-318`。

**根因**

接口按“当前 RAG 用例”命名，而不是按存储原语、投影写入、检索策略和权限编排分界。由于没有独立的 projection receipt/manifest 和 query value object，provider 方法自然承接了所有上层策略。

**影响**

无法用不带 ACL/HTTP/revision 的 fake storage 验证 provider 原语；第二个存储实现会被迫复制业务参数；repository 变更会同时影响写入、查询、发布和删除。

**后续必须讨论**

只从真实替换需求倒推最小 storage contract，分别定义事实存储、投影写入、provider adapter 和 retriever/application 的责任。LlamaIndex 的启发是“存储与检索器解耦”，不是复制其 Node 类型。

### P1-3：插件能力污染通用 chunk 摄入和图谱选择

**现象和证据**

- `DocChunk` 永久携带插件 `metadata` 字段；Mongo repository 依赖 registry codec 解码具体子类：`src/rag/application/document/models.py:127-132`、`src/rag/core/persistence/mongo/doc_chunk_repository.py`。
- `DocumentPreparer` 在每个 chunk 生成时调用 `chunk_metadata_builder`：`src/rag/application/document/preparation.py:100-116`。
- `RagPlugin` 暴露 `chunk_selector`，`GraphFactBuilder` 用 `plugin.select_chunks(chunks)` 决定哪些 chunk 进入 LLM 抽取：`src/rag/application/plugins/core/plugin.py`、`src/rag/application/graph/graph_fact_builder.py:217-241`。
- 同一个 registry 同时负责 document metadata、chunk metadata codec、filter compiler 和 graph plugin：`src/rag/application/plugins/core/registry.py`、`container.py:90-104`。

**根因**

垂类扩展被设计成通用 ingestion 的参与者，试图通过逐 chunk metadata 和 selector 预留未来能力；没有区分“所有文档都要建立的 chunk 事实”和“某个 graph producer 自己需要的输入选择”。

**影响**

普通文档摄入依赖插件注册表和 metadata 序列化；插件可以静默改变图谱事实覆盖范围，导致文档索引、图谱抽取和查询过滤共享一份难以审计的 chunk 事实。

**后续必须讨论**

保留真正被检索或图谱消费的显式字段；ontology、deterministic producer 和 query filter 由插件自有边界负责。是否保留某个 metadata 字段必须由实际 producer/consumer 对证明。

### P1-4：图谱实现有独立语义，但还没有 LightRAG 可对照的内核边界

**现象和证据**

- 当前 `GraphFactBuilder` 自己定义 extraction prompt、Pydantic 响应、实体规范化、描述合并、edge repair 和 source 记录：`src/rag/application/graph/graph_fact_builder.py`。
- `GraphRetriever` 自己组合 node/edge 向量分支和 Neo4j traversal，并用 `_Candidate` 重新表达结果：`src/rag/application/retrieval/graph_retriever.py`。
- LightRAG 参考实现把 extraction/query operation 与 KV/vector/graph/doc-status storage 分开，并在 storage namespace 中显式携带 workspace：`services/rag/references/LightRAG/lightrag/operate.py`、`base.py`、`kg/qdrant_impl.py`。

**根因**

原实现先围绕本地 Mongo/Qdrant/Neo4j 组织了图谱业务类，再试图把图谱能力扩展成通用接口；LightRAG 的抽取、规范化、local/global/hybrid/mix 查询语义还没有被提取为可测试的本地 core。

**影响**

图谱行为与 LightRAG 参考实现没有 golden 对照边界；换 storage 会连带改动 ACL、revision 和查询流程；跨资源同名实体的合并语义也没有在 tenant/revision 边界上先定下来。

**后续必须讨论**

先决定本地需要复制的 LightRAG 行为子集和输入/输出值对象，再把 storage 替换成 RAG 自己的 fact/projection adapter。workspace 隔离语义可借鉴，但不能把 LightRAG runtime 当作本服务的租户或生命周期管理器。

### P1-5：测试、打包和验证基线无法支撑分阶段重构

**现象和证据**

- 当前测试只有少量 document/context、outline 和 projection 文件；没有 tenant 隔离、ACL 真值表、active snapshot、发布并发、删除重试或 graph golden suite。
- `test_context_expander.py` 引入不存在的 `context_expander.py`，说明测试先于实现或旧文件被删除后未同步。
- 在仓库根执行 `uv run pytest --collect-only -q` 失败，错误为 workspace member `services/rag` 缺少 `pyproject.toml`；这属于当前仓库配置阻塞，不是测试通过/失败结论。
- `services/wisepen-rag-service/pyproject.toml` 的 wheel packages 只有 `src/rag`，没有未来的 `rag_v4`。

**根因**

重构计划、旧测试和 workspace 配置没有共享一个可运行的 package/validation boundary；当前测试更多验证已删除 span 的负面约束和迁移异常，而不是验证完整业务能力。

**影响**

不能把 pytest collection、局部 mock 或旧异常测试当作 RAG 可运行性的证据。每个阶段需要先建立自己的最小 package、fake contract 和故障矩阵，否则会在大量补丁后才发现入口不可导入。

**后续必须讨论**

确定服务级 uv workspace/package 结构和测试运行方式；随后为 tenant/ACL/revision 建立底座测试，再逐层增加 chunk、contextual、retrieval、reading、graph。验证范围必须跟随能力边界，而不是最后才跑全量测试。

## 4. 需要在讨论中先澄清的合同

以下内容在 00 计划中已有方向，但当前代码和参考实现还不足以直接固化为实现细节：

1. **可信身份与 ACL 边界**：MCP 适配层如何构造 `PermissionScope`，工具参数和 `tool_context` 不得成为授权来源；上游 ACL、本地投影、索引预过滤和最终判权的职责见 [02-可信身份与 ACL 边界.md](02-可信身份与%20ACL%20边界.md)。
2. **一致性、责任与容错边界**：明确哪些状态必须强一致、哪些只需版本自洽、哪些允许最终一致；确认上游 ACL 版本/事件顺序合同，以及 ACL 延迟和请求期间 active 切换的业务容忍度。
3. **active snapshot**：查询需要保证的原子性，是一次读取时的版本 fence、Mongo 事务、还是候选回查的二次确认；各入口是否共享同一个对象。
4. **revision 与投影**：文档 active 是否只依赖文档投影；图谱属于可选附加能力还是某些资源的发布前置条件；每个投影失败的重试和观测事实是什么。
5. **DocChunk 合同**：必须保留的字段、`retrieval_context` 是否持久化、section/chunk ID 的本地语义，以及 SourceSpan 仅限内部结构的边界。
6. **普通检索组合**：Dense/BM25 的候选如何转换为 Common `Candidate`，Fusion 选 `RoundRobinFusion` 还是 `RrfFusion`，component `top_k` 与 request `top_k` 的所有权如何分配。
7. **图谱 core**：复制 LightRAG 的 extraction/merge/query 哪些行为；跨资源同名实体是否只在结果层合并；deterministic producer 如何表达没有 chunk source 的事实。
8. **删除与重建**：先撤销可见性后清理的残留如何记录，如何按 resource/revision 幂等删除，projection 失败后何时可以安全重建。

## 5. 后续讨论路径

每一阶段都先写小合同和故障矩阵，再写实现；阶段未通过不得进入下一阶段。讨论顺序如下：

### 01-A：可信身份与 ACL 边界

产出：MCP 适配层到 RAG application 的 `PermissionScope` 合同、用户/群组 subject 规则、ACL 判权真值表和预过滤/最终判权合同。平台保证资源、用户、群组 ID 全局唯一，因此不引入 tenant/workspace 维度。

必须验证：缺少可信身份、工具参数伪造身份、ACL 缺失、撤权传播、索引预过滤错误和批量请求中的资源混合；验证所有最终结果都经过统一 ACL capability 判权，并按后续一致性策略处理投影延迟。

### 01-B：ContentRevision、active snapshot 与发布失败语义

产出：revision 三元组、active/staged 条件更新、查询 snapshot 结构、文档投影与图谱投影的独立状态、删除/重建任务语义。

必须验证：旧事件、同版本内容漂移、并发 stage/apply、active 切换期间查询、单投影失败、重复删除和清理重试。

### 01-C：Markdown 到 DocChunk 的最小事实

产出：`MarkdownChunker -> Document/DocChunk` 的字段合同、稳定本地 ID、section/anchor 的保留范围、metadata 删除清单和序列化边界。

必须验证：chunk 顺序、空文档、无标题正文、多 section、重复重建和跨 revision ID 不碰撞。

### 01-D：Contextual 与读取能力

产出：普通检索 context 变换、graph target-only context、预算/并发/缓存键、parent/section read 的最小响应。

必须验证：section/revision/resource 边界、预算不足、LLM 失败、context 只改变检索文本、命中后可以得到可读结果而不是迁移异常。

### 01-E：普通 Dense/BM25 检索

产出：最小 `VectorStorage`/Qdrant adapter、Common Candidate/Fusion adapter、Mongo 批量回查、ACL snapshot 和 rerank 的责任图。

必须验证：Dense/BM25 空结果、候选身份冲突、Fusion 稳定性、ACL 预过滤错误、active revision 变化、批量回查和 top-k 所有权。

### 01-F：LightRAG 图谱 core 与本地事实边界

产出：抽取/解析/规范化/去重/描述合并/source 关联的 golden contract；local/global/hybrid/mix 查询的候选语义；ontology 和 producer SPI。

必须验证：target-only 事实、非法 ontology、同名节点、重复边、无 source 的 deterministic fact、跨 revision 查询和 token 截断。

### 01-G：图谱投影、读取和组合根

产出：持久化 Chunk 图谱 metadata、GraphStorage adapter、图投影重建、graph retriever 和能力级装配；HTTP/Kafka composition 后续单独接入。

必须验证：Chunk facts 是图谱投影重建来源、Neo4j/Qdrant 可重建、图谱投影失败不改变文档可见性、旧实现可以被整体替换或删除。

## 6. 对 00 计划的修正意见

- 00 计划中 `RoundRobinFusion`、`ProjectionManifest`、`LocalCitation`、`src/rag_v4/` 等是候选设计或未来文件，不应在问题确认阶段写成已存在能力。
- 00 计划把“先建完整新目录、最后一次性切入口”作为默认迁移方式；在身份/ACL、revision 合同未确定前，连新目录中的模型和 storage protocol 都不应大量创建。
- 00 计划要求的 LightRAG golden cases、ACL 故障矩阵和完整 RAG 测试目前不存在，应作为后续阶段的验证产物，而不是当前实现的验收证据。
- 00 计划关于不引入上游 `source_units`、不把 RAG 做成 LlamaIndex Node 兼容层、删除伪精确 span 证据的方向与当前代码事实一致，应继续保持；但它们不能替代身份/ACL、snapshot 和投影失败语义的合同。
