# RAG V4 子方案 03：ACL 基础投影与一致性边界

## 0. 子方案目的

本方案基于当前已经存在的 `AclRecalculateMessage` 实现 RAG 的基础 ACL 校验能力。它不等待上游新增完成事件，也不替上游承诺或补偿跨服务一致性。

当前事件只表示“这个资源的 ACL 需要刷新”，不表示上游的 `computedGroupAcls` 已经完成更新。RAG 接受这个事实，并把短暂旧投影视为当前最终一致性边界内的工程权衡。

本方案不设计：

- `acl_revision`、Fence 或跨 Mongo/ES/Qdrant/Neo4j 的强一致 Snapshot；
- 固定延迟、轮询、重复读取来猜测上游重算是否完成；
- RAG 对上游标签、群组、市场权限规则的独立重算；
- 每次查询都调用上游实时判权；
- 用本地时间戳伪造上游事件顺序或完成语义。

## 1. 责任边界

| 能力 | 上游 Resource Service | RAG |
|---|---|---|
| 权限规则和权威判权 | 保存配置并计算真实 ACL | 不复制规则 |
| ACL 重算通知 | 发布现有 `AclRecalculateMessage(resourceId, triggerSource)` | 将事件作为刷新触发 |
| 预计算 ACL | 异步更新 `computedGroupAcls` | 读取当时可见的上游状态 |
| 本地 ACL | 不负责 RAG 投影 | 保存本地 `ResourceAcl`，供检索和读取判权 |
| 跨服务一致性 | 不向 RAG 承诺全局观察点 | 不自行补偿或伪造该承诺 |

上游未来可以增加完成事件或稳定 API，但这些不是本阶段的前置条件。本阶段不根据缺失的上游能力增加复杂补偿机制。

## 2. 基础刷新流程

```text
AclRecalculateMessage(resource_id)
  -> 校验 resource_id
  -> 读取上游当前资源 ACL 投影
  -> 校验必要字段和 ACL 结构
  -> 完整替换 RAG 本地 ResourceAcl
  -> 后续查询统一使用本地 ACL capability
```

刷新读取的字段包括：

- `ownerId`；
- `specifiedUsersGrantedActionsMask`；
- `computedGroupAcls`；
- 资源不存在或已删除状态。

RAG 只做结构校验和权限事实转换，不解释 `triggerSource` 的业务语义，也不根据事件内容推断新旧 ACL 的先后关系。

## 3. 一致性语义

### 3.1 允许的正常延迟

事件到达 RAG 时，上游可能仍在执行 ACL 重算。因此本地投影可能暂时保持旧状态，表现为：

- 新授权尚未在 RAG 生效，属于短暂可用性延迟；
- 新撤权尚未在 RAG 生效，属于已知安全风险窗口；
- RAG 无法仅凭现有事件判断该次刷新是否已经包含本次变更。

这些情况不由 RAG 通过等待、重试或本地版本比较伪装成强一致。它们必须作为运行监控和后续产品安全策略的已知边界记录。

### 3.2 RAG 必须保证的内容

即使接受 ACL 最终一致，RAG 仍必须保证：

1. 没有本地 ACL 投影时不得直接判定资源可读；
2. 所有用户可见结果经过同一 `ResourceAcl.can_read(scope)`；
3. Qdrant、Neo4j 的 ACL 过滤只能预过滤，不能绕过最终判权；
4. 一次刷新完整替换一个资源的 ACL，不拼接不同读取时刻的字段；
5. 事件重复消费不会产生错误的重复数据；
6. 资源删除或上游读取不到资源时，本地 ACL 被删除或标记为不可读。

这些是 RAG 自身的数据和授权正确性，不是对上游重算时序的补偿。

## 4. 本地并发和幂等

本阶段只解决 RAG 本地写入的基本安全性：

- 事件处理按资源执行完整替换；
- 相同资源的重复事件可重复执行；
- 本地写入不能产生半份 ACL；
- 同一消费组内依赖 Kafka 资源 key 和消费者顺序处理正常事件。

本阶段不引入本地 generation 来模拟上游 ACL 版本，也不使用 `updateTime` 的大小比较证明某个事件更新更“新”。如果未来出现独立刷新入口造成真实的本地并发覆盖问题，再单独增加资源级串行或条件写入，并保持其名称为本地投影写入保护。

## 5. 查询和失败语义

常规查询路径使用最近一次成功写入的本地 ACL，不在每次查询时回源上游。上游事件消费失败时：

- 保留最近一次本地投影；
- 记录消费失败和资源标识；
- 由 Kafka 消费重试或死信机制处理消息；
- 不在查询路径隐式发起上游实时判权。

本阶段不规定“撤权必须零延迟”。是否对某类资源要求更严格的撤权语义，属于后续产品安全策略，不通过底层 Snapshot 统一解决。

## 6. 实施阶段

### 03-A：事件和上游读取适配

建立 `AclRecalculatePayload` 校验、上游资源 ACL 读取 adapter 和结构转换。删除对 `triggerSource` 业务解释以及对 `acl_revision` 顺序语义的依赖。

### 03-B：本地 ACL 投影

按资源完整替换 `ResourceAcl`，处理重复事件、资源不存在、ACL 字段缺失和单资源失败。投影字段只保留真实查询判权需要的事实。

### 03-C：统一查询判权

让搜索、直接读取和图谱查询都通过同一个 ACL capability。provider ACL 过滤只作为候选缩减，最终结果必须再次判权。

### 03-D：有限验证和观测

验证正常事件、重复事件、资源删除、ACL 缺失、上游读取失败和消费重试。增加事件消费延迟、刷新成功/失败和本地 ACL 缺失指标，但不把指标解释为上游 ACL 版本或完成证明。

## 7. 后续讨论门槛

本方案完成后，可以继续进行 ContentRevision、请求内 active revision、普通检索和图谱能力设计。后续方案必须遵守：

- 内容 revision 在请求内固定；
- ACL 使用本地最终一致投影；
- 不建立跨后端全局一致观察点；
- 各能力自行定义局部失败和部分返回；
- 上游未来改进作为可利用的增强，不作为当前 RAG 正常运行的必要条件。
