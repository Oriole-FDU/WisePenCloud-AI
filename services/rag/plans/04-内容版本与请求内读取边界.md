# RAG V4 子方案 04：内容版本与请求内读取边界

## 0. 子方案目的

本方案冻结内容版本、active 指针和用户请求内读取的最小一致性语义。它承接 03 中的 ACL 基础投影：ACL 允许本地最终一致，内容则必须保证一次读取不会把不同 `content_revision` 的正文、chunk 和图事实混在一起。

本方案不构造 Mongo、Qdrant、Neo4j 之间的全局一致观察点，也不要求请求结束时仍然使用最新 active revision。

2026-10-12 已实现 application 共享资源快照与 Document／Chunk 读取，见 [18 资源快照读取实施记录](18-application-snapshot-implementation.md)。名称中的 snapshot 只表达一次调用内逐资源固定的版本与权限决定。

核心合同是：

> 每个资源在一次能力调用中第一次确定版本与可见性后，后续该资源的正文和派生产物都沿用该决定；applied、ACL 或 destroyed 在调用期间变化时，本次调用继续使用已经固定的结果，不重试、不切换版本、不增加输出前回查。

## 1. 已有事实和需要修正的地方

### 1.1 可以继承的事实

- `DocumentReadyPayload` 已携带 `resourceId`、`version` 和完整 Markdown `content`。
- `ContentRevision` 已使用 `resource_id`、`document_version` 和 `content_sha256` 构造不可变内容身份。
- `Chunk`、Section、Chunk metadata 中的图谱事实和向量 payload 已带有 `content_revision` 边界。
- `ResourceIndexState` 已区分 `staged_content_revision` 与 `applied_content_revision`。
- `apply_revision` 已在切换 active 前检查正文、chunk 和文档向量是否完整。
- 删除流程已先清除 active 可见性，再进行物理清理。

### 1.2 旧实现中需要收敛的地方

- `ActiveDocumentSnapshotLoader` 和 `HybridRetriever` 各自重复读取 active、文档和 ACL，容易产生不同入口的读取顺序漂移。
- 当前 `snapshot` 命名容易让调用方误以为它提供跨 Mongo、Qdrant、Neo4j 的原子观察点。
- `stage_revision` 允许同一 `document_version` 使用不同内容 hash 覆盖暂存指针，尚未明确同版本内容漂移语义。
- Qdrant/Neo4j 的候选可能来自旧 revision，必须在 Mongo 回查时按本次固定的 active revision 丢弃，而不能继续拼接。
- 图谱投影不是文档内容 active 的发布前置条件；图谱失败不能阻塞正文和文档向量可见性。

## 2. 内容身份合同

### 2.1 `ContentRevision` 的字段语义

| 字段 | 语义 | 来源 |
|---|---|---|
| `resource_id` | 资源全局身份 | 上游事件 |
| `document_version` | 上游内容版本，用于旧事件和发布顺序判断 | 上游事件 |
| `content_sha256` | RAG 对收到 Markdown 的完整内容摘要 | RAG 计算 |
| `content_revision` | 上述字段的本地组合键 | RAG 派生 |

`content_revision` 不是新的上游版本。所有正文、chunk、向量和图事实必须带同一 `resource_id/content_revision`，不能仅凭 chunk ID 或资源 ID 拼接不同版本的数据。

### 2.2 同版本内容漂移

对同一资源：

- 同一 `document_version` 和同一内容 hash 的重复事件是幂等重放；
- 同一 `document_version` 但内容 hash 不同，视为内容合同冲突，记录并拒绝覆盖已经暂存或发布的同版本内容；
- 更高 `document_version` 可以创建新的 staged revision；
- 低于当前 staged/applied 版本的事件丢弃，不恢复旧 active 指针。

RAG 不猜测同版本两个正文哪个“更新”，也不使用接收时间解决冲突。

当前 ContentRevision 位于 core.schema，组合键使用完整 SHA-256，摘要基于原始 `Document.text` 的 UTF-8 字节。最高 staged/applied 版本先用于旧版本淘汰，随后才判断同版本内容冲突；已 applied 的同内容重放直接跳过，不重写 metadata。

## 3. staged/applied 发布语义

### 3.1 staged

staged revision 是后台构建中的候选，不对用户可见。它可以在正文、chunk、向量或图谱投影尚未完成时存在。

阶段顺序：

```text
校验事件与 ContentRevision
  -> 条件写入 staged 指针
  -> ContentWriter 保存 Document
  -> 普通 Pipeline：ChunkFactsIndexer 保存 Chunk，再构建必需文档检索投影
  -> 检查事实与必需投影完整，条件切换 applied
  -> 普通内容摄入成功后确认消息处理完成
  -> 独立构建可选图谱
```

如果构建中断，旧的 applied revision 仍然可读；staged 记录可以被同版本重试或被更高版本替换。

staged 允许先于内容事实存在，只表示候选构建已开始。ContentStorage 不维护这两个指针，内容写入本身不触发发布。内容、ACL 和删除事件不能依赖跨 topic 的到达顺序；版本与条件更新由各自业务入口解释。

### 3.2 applied

只有以下事实都存在时才允许切换 applied 指针：

- `Document` 正文和结构完整；
- 该 revision 的 `Chunk` 集合完整；
- 文档检索所需的向量投影完整；
- 条件更新确认 staged 指针仍然指向当前 revision。

切换 applied 是一个 Mongo 指针更新，不代表 Qdrant、Neo4j 和 ACL 在同一瞬间完成。图谱投影属于附加能力，可在 applied 之后独立重建。

发布属于 application.publication 用例，不作为独立领域能力。普通用例注入外部完整 Pipeline，开发者固定事实 Indexer 在必需投影前执行；内部装配依靠合同与测试，不进行组件校验。Pipeline 成功后返回最终 Chunk 列表，publication 回查 Document 身份以及精确有序的 Chunk ID 集合。必需投影依靠 Indexer 全部写入确认后才成功的合同，不额外查询向量完整性。零 Chunk 内容可以发布。

同资源构建由调用方串行；Mongo 条件更新防止状态变化后旧任务覆盖候选或发布。条件失败只重新读取分类，不自动重试；仍可接受但本次未完成的竞争抛 PublicationStateChangedError，由调用方决定后续动作。

### 3.3 删除

物理销毁时先永久置 destroyed 并清除 applied/staged；未摄入资源也建立标记，不允许同 ID 恢复。新调用首次观察到 destroyed 后，即使旧正文、chunk、向量和图事实暂时残留，也不能返回该资源。已确定可见性与版本的调用仍沿用首次决定；已选事实被清理则省略，不增加输出前销毁回查。物理清理由后续任务处理。

此操作只对应 `wisepen-resource-physical-destroy-topic`。个人 `.Trash` 保留业务主档并触发权限剥离，softRemoveResources 移入审计回收集合，hardRemoveResources 才发布物理销毁事件。回收站与软删除的 RAG 搜索可见性另行处理，不能通过永久标记代替。

## 4. 请求内读取合同

### 4.1 请求内资源快照

共享读取模块为 `application/snapshot.py`，只包含两个对象：

- `ResourceSnapshot`：绑定可信 PermissionScope，内部缓存 `resource_id -> ContentRevision | None`。获准读取时保存 selected revision，不可见时保存 None；不保存正文或额外拒绝原因。
- `ResourceSnapshotReader`：显式注入 PublicationStore、ResourceAclRepository 和 ContentReader，提供 `read_documents(resource_ids, *, snapshot)`、`read_chunks(chunk_ids, *, snapshot)`。版本与授权解析收为内部方法，不再独立装配 resolver。

每次独立能力调用由 application 创建新快照，同一次上层编排的子操作显式共享它。共享 Reader 只保存固定依赖；不跨调用、用户或聊天会话复用快照，也不把快照注入 Retriever constructor 或隐式上下文。

这里的快照不是数据库事务、版本 Fence、跨后端原子快照或全局时间点。ACL 来源仍是 03 中的本地最终一致投影，不能与 `content_revision` 拼成虚假的联合版本。

### 4.2 首次确定和后续复用

- 显式 Document 读取：批量读取尚未观察资源的 publication 状态，再对未 destroyed 且存在 applied 的资源批量读取 ACL；只读取授权的 selected revision。
- 指定 Chunk 读取：批量定位所属资源，再复用同一快照的资源级决定；定位阶段取得的内部正文只有通过授权与版本检查后才能交给响应或外部模型。
- 后续标题树、普通混合检索和图谱用例：复用上述 application 读取入口，将所有子操作显式绑定到同一快照。

同一资源在一次能力调用中首次完成的版本与可见性决定固定，首次不可见也不重新查询。applied、ACL 或 destroyed 变化时沿用该决定，不增加输出前回查。已选事实缺失或身份不符则省略，不切换新版、不回退其他版本，staged 不进入读取路径。空输入无 I/O，批量去重保序。

Document 回查核对 resource、document_version、revision 字符串与原始 text 的完整 SHA-256；Chunk 核对所属资源与 selected revision，并继承 Document 级授权。数据库异常直接传播，未完成的解析不会缓存为不可见。并发子操作交错时保留最先完成的决定，不引入锁、轮询或自动重试。

### 4.3 各后端的使用边界

- Mongo `DocumentRevision` 和 `Chunk` 是正文与结构事实来源；
- Qdrant 只提供候选，候选的 `content_revision` 必须与本次 selected revision 相等；
- Neo4j 只提供图拓扑或候选，最终回查必须校验 resource/revision；
- ACL 使用本地 `ResourceAcl` capability，不因为内容 revision 变化而伪造 ACL 版本；
- 任一投影缺失都只能影响对应候选或能力，不得回退到另一个 revision 的数据。

## 5. 局部失败语义

不同能力自行定义失败范围，不由统一读取上下文强制全请求失败：

| 能力 | 单资源/单投影失败时的基础语义 |
|---|---|
| 普通搜索 | 不可见、旧版本、投影身份不符或缺失正文的候选省略，不补召回；连接、查询、解码异常传播；重排异常降级保留排序前顺序与分数 |
| 批量 Document／Chunk 读取 | 不可见、身份不符或缺失的对象省略，保留其余可见对象，不回退其他 revision |
| 后续 Section／标题树读取 | 继承资源级判权与已选版本；目标不可确认时不返回旧结构，具体接口在对应切片确定 |
| Outline/Neighborhood | 无法确认目标资源时不返回该资源的旧版本结构 |
| 图谱查询 | 图谱投影缺失时按图谱能力返回空/部分结果，不改变文档 active |
| 文档发布 | 文档向量不完整时不切换 applied；旧 active 继续可见 |

这些语义不承诺所有后端同时成功，也不要求基础 ACL capability 为所有调用方设计统一重试策略。数据库连接、查询和解码异常直接传播，不能将基础设施故障伪装成不可见或空结果。

## 6. 实施阶段

### 04-A：冻结 ContentRevision 和事件幂等

同步事件模型、revision 构造、旧版本丢弃和同版本内容漂移处理。建立同版本相同 hash、同版本不同 hash、低版本和重复事件测试。

### 04-B：收敛 staged/applied 发布

保留条件 stage/apply 和“完整投影后才 applied”的行为，明确正文/chunk/文档向量是文档可见性前置；图谱投影从发布前置中分离。

### 04-C：建立请求内 selected revision

让搜索、Section、outline 和图谱入口复用同一套按资源确定并固定 revision 的读取规则。删除各入口重复解释 active 的分支。

共享模块、Document／Chunk 入口及普通混合检索 use case 已完成，见 [19 检索实施记录](19-hybrid-retrieval-implementation.md)。HybridRetrieval 在 Common Pipeline 的 prepare_candidates 阶段批量调用 ResourceSnapshotReader.read_chunks，核对向量投影的资源与 revision 后才允许正文进入模型。标题树和图谱消费者后续实现。Retriever 的检索配置在初始化时确定，retrieve 只接收查询文本；快照显式留在 application，Storage 仍只按明确身份读取事实。

### 04-D：投影回查与局部失败

为 Qdrant、Neo4j、Mongo 回查增加 resource/revision 校验，验证 active 切换期间不会混版，并按能力实现部分结果或目标失败。

## 7. 验收证据

1. 旧内容事件不能覆盖较新的 staged/applied revision；
2. 同版本内容漂移不会静默覆盖已存在内容；
3. staged 构建失败时旧 active 继续可读；
4. 文档向量不完整时 applied 不切换；
5. active 在请求期间变化时，本次调用不混用两个 revision，也不自动重试；
6. Qdrant/Neo4j 返回旧 revision 候选时，最终回查丢弃它；
7. 图谱投影失败不影响文档 revision 可见性；
8. 新调用观察到 destroyed 后不能返回旧 revision 残留事实；已确定决定的调用不增加输出前撤权或销毁回查；
9. ACL 使用本地最终一致投影，不新增跨服务一致性版本、Fence 或跨后端原子快照；已有 `ResourceAcl.acl_revision` 保留，不将其当作上游重算完成版本。
