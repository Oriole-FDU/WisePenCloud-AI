# RAG V4 实施排期与验收门槛

## 0. 排期原则

当前方案已经足以进入实现。后续不再以继续讨论架构为前置条件，而是按可独立验收的纵向阶段推进。本文件是后续执行入口，组件合同见 [11-RAG-V4设计文稿.md](11-RAG-V4设计文稿.md)。00–09 作为背景和决策依据保留，冲突处以这两份整合文档及用户后续明确决策为准。

本排期不包含 HTTP 路由、HTTP schema、服务发布或部署。MCP 的可信身份来源作为既定边界保留，本轮不扩展工具注册和传输协议；通过可直接调用的业务入口验证能力。现有内容、ACL 事件的解析与处理纳入排期，上游读取 adapter 沿用既有协议。

本次完全重构，没有线上调用和兼容性要求。不安排双写、灰度、旧数据迁移、兼容别名或保留旧 schema 的过渡窗口。旧实现用于提取算法和行为测试，不成为新实现的运行时依赖。

每个阶段都必须满足以下规则：

- 先建立真实可运行的最小能力，再扩展下一个能力；
- 阶段失败不通过临时兼容层隐藏；
- 新阶段只依赖前置阶段已经冻结的合同；
- 不为了跨数据库强一致、未来并行或上游未提供的版本语义增加状态机；
- 每个阶段完成后都能用 fake storage、固定 fixture 或本地 adapter 独立验证。

实现顺序采用 `P0 -> P8`。每个交付切片单独修改、验证和审阅，通过后才继续；同一切片不顺便改造后续阶段。

### 工期假设

以一名实现者串行推进、每天约一个有效工作日估算，包含 focused tests 和阶段审阅，核心实现约 **22–29 个工作日**。这是初始估算，不是承诺日期；不包含等待数据库、模型凭据、环境排障或讨论回复的时间。P0 后用实际依赖状况修订，之后只在阶段结束时更新剩余估算。

采用相对工作日，不假定开始日期或周末工作。每个阶段拆成约 0.5–2 个工作日可审阅的切片，禁止把一整个阶段做成不可评审的大补丁。

4. 仅建立当前切片使用的 fixture；模型、Storage 和 LLM fake 在 P2–P5 随真实接口增加，避免 P0 先虚构后续类型。

### 不做

- 不接 HTTP/MCP route；
- 不迁移旧入口；
- 不实现 Qdrant、Neo4j 的 provider 细节；
- 不为旧 `DocChunk`、旧 metadata codec 或 `chunk_selector` 保留兼容层。

### 验收

- 第一批测试只依赖新合同，不把旧实现当作运行时依赖。

## 3. P1：身份、ACL 和内容版本

### 工作内容

1. 实现全局唯一 `resource_id`、user ID、group ID 的本地模型，不增加 tenant/workspace。
2. 定义 application 层的 `PermissionScope`。身份只由可信安全上下文适配器提供，公开业务参数不接受 `user_id` 或 ACL 覆盖字段。
3. 复用现有 `ResourceAcl.can_read(scope)` 顺序，统一搜索、直接读取和图谱读取判权。
4. 基于现有 `AclRecalculateMessage` 实现本地 ACL 刷新：事件只作为刷新触发，读取当前可见上游状态，完整替换本地投影。
5. 不引入 `acl_revision`、Fence、轮询等待或本地伪造的上游版本。
6. 定义 `ContentRevision(resource_id, document_version, content_sha256, content_revision)`。
7. 实现 Mongo staged/applied 条件更新、同版本 hash 冲突拒绝、旧版本事件丢弃和删除先撤销可见性；apply 的投影完成条件在 P4 接入真实向量写入后验收。
8. 实现请求内 selected revision：一次能力调用中首次确定后固定使用，不因 active 变化重试或切换。

### 产出

- `PermissionScope` 和 ACL capability；
- `ResourceAcl` 本地投影接口及 fake implementation；
- `ContentRevision`、`ResourceIndexState` 和 publication ports；
- selected revision/read context；
- ACL、版本和发布状态 focused tests。

### 验收门槛

- ACL 真值表全部通过；
- ACL 缺失、读取失败和本地投影不存在时不直接判定可读；
- 同一版本同一 hash 幂等，同一版本不同 hash 拒绝覆盖；
- active 在请求期间变化时，后续读取仍只使用已选 revision；
- P1 不要求 Mongo、Qdrant、Neo4j 同时处于同一观察点。

## 4. P2：Chunk 与 IngestionPipeline

### 工作内容

1. 定义 `Document` 和 `Chunk`。Chunk 使用 `metadata: dict[str, object]`，不使用 `ChunkDerivedMetadata` 或 Pydantic schema。
2. `Chunk` 至少包含 resource/revision/chunk identity、section 归属、raw text、token count、anchor labels 和 metadata；同时冻结 P3 需要的 GraphNode/GraphEdge 字段，不在此实现图谱抽取。
3. 实现 `retrieval_text` property：读取 `metadata["contextual_context"]`，有值时与 raw text 拼接，否则返回 raw text。
4. 封装现有 `MarkdownChunker` 为 `Chunker.split(document) -> list[Chunk]`。
5. 定义三个最小 Protocol：

```python
class Chunker(Protocol):
    async def split(self, document: Document) -> list[Chunk]: ...


class Transformer(Protocol):
    async def transform(
        self, chunks: list[Chunk], *, document: Document | None = None,
    ) -> list[Chunk]: ...


class Indexer(Protocol):
    async def index(self, chunks: list[Chunk]) -> None: ...
```

6. 实现 `IngestionPipeline.run(document)`：Chunker 一次调用，Transformers 按序调用，Indexers 按配置顺序串行调用。
7. 允许 Transformer 原地修改 metadata 或返回新 Chunk；Pipeline 始终使用返回值，不自动深拷贝。
8. 保持 Chunk identity、来源、顺序和 raw text 稳定；Indexer 只读，不用 `pop()` 消费 metadata。
9. 开发者固定正确组件组合，保证 Extractor 有对应 Indexer、必需投影 Writer 齐全；不添加运行时装配检查。

### 失败合同

- Transformer 异常：停止后续 Transformer 和所有 Indexer；
- Indexer 异常：停止后续 Indexer，已完成写入保留；
- Pipeline 只有全部阶段成功才返回成功；
- 不提供 rollback、`continue_on_error`、并行调度或统一 failure object；
- 发布和部分索引可见性由外部 capability 决定。

### 验收门槛

- 使用 fake Chunker/Transformer/Indexer 完成完整 pipeline 测试；
- 验证完整 list 输入、返回值传递、原地 metadata 修改和 identity 稳定；
- 验证 Transformer/Indexer fail-fast；
- 用固定应用流程的行为测试验证事实与必需投影顺序，不增加装配校验测试；
- 验证普通 pipeline 不依赖 GraphExtractor、GraphIndexer 或任何数据库。

## 5. P3：VectorStorage、GraphStorage 和过滤

### 工作内容

1. 定义 Reader/Writer Protocol，同一个具体 Adapter 可以实现两者。
2. 定义统一 `VectorRecord`、`VectorQuery`、`VectorMatch`。Chunk、Entity、Relationship 只在投影时转换为 VectorRecord。
3. 定义 collection-bound `VectorStorage`；Record 不携带 namespace。
4. 定义 `GraphStorage`，直接使用 `GraphNode`、`GraphEdge`，提供节点、关系、邻接和有界遍历原语。
5. 将 Transformer 产出的 Chunk（含图谱 metadata）持久化到现有 Mongo Chunk 内容事实集合；不增加 GraphFactStore 或 GraphChunkSource 集合。
6. 定义通用 `MetadataFilters`。plugin 负责把垂类请求过滤编译为通用条件，Storage 只执行。
7. 实现 fake storage contract，再实现 Qdrant/Neo4j adapter 的最小读写方法。

### 不做

- Storage 不理解 ACL、active revision、Chunk 生命周期或 local/global/hybrid；
- 不增加 Repository、Storage Router 或跨存储事务；
- 不把 Cypher、Qdrant 查询字段或业务 request 下沉到 Storage。

### 验收门槛

- VectorStorage 批量 upsert/query/delete 通过；
- GraphStorage 节点、关系、邻接和 bounded traversal 通过；
- collection 由 Storage 实例绑定；
- MetadataFilters 的 plugin 编译和 adapter 翻译通过；
- fake storage 不需要 ACL、HTTP request 或 active revision 即可通过 contract。

## 6. P4：Contextual、VectorIndexer 和普通检索

### 工作内容

1. 实现 `Contextualizer.transform(chunks)`，只写 `metadata["contextual_context"]`。
2. 使用同一 revision 的连续 section/chunk 窗口和字符预算；不跨 resource、revision 或 section 边界。
3. contextual 不修改 raw text、Chunk identity 或图谱事实归因。
4. 实现 `VectorIndexer.index(chunks)`：选择 `retrieval_text`、生成 embedding、构造 VectorRecord、调用 VectorWriter。
5. 通过 ContentWriter 保存 Document，并由 ChunkFactsIndexer 保存 Transformer 返回的完整 Chunk；MongoContentStorage 实现两个内容集合的批量读写，不另加 Repository 或通用 Mongo 框架。普通 metadata 随 Chunk 保存，仍不增加 metadata schema 或 codec。
6. 实现 RAG Qdrant Dense/Sparse Retriever adapter；用 Common `Candidate`、`FusionRetriever` 和显式 `RoundRobinFusion`/`RrfFusion` 做候选组合。Common `BM25Retriever` 是对内存 Candidate 列表建索引，不作为 Qdrant sparse adapter。
7. Fusion 后先校验 selected revision 和本地 ACL，再从 Mongo 批量读取授权 Chunk 正文；只有授权正文进入 Common `RetrievalPipeline` 的 rerank/diversity 阶段，最终 `RankedCandidate` 再映射为 `ChunkHit`。
8. 接受并测试 Common `RetrievalPipeline` 当前的 reranker 失败降级语义：保留原候选顺序；若后续合同要求失败即终止，RAG 改为只复用 Candidate/Fusion 等组件。
9. 图谱不可用时，Chunk hybrid retrieval 仍然独立工作。
10. 接入 Document/Chunk Mongo 事实写入和普通检索发布条件；提供直接内容读取、section、outline/neighborhood 的业务入口，共用 selected revision 与 ACL，不增加 HTTP 路由。

### 验收门槛

- context 缺失时 `retrieval_text == raw_text`；
- context 只改变 embedding/检索文本，不改变 Chunk identity；
- Dense、Qdrant sparse、显式 Fusion、selected revision/ACL 回查、授权正文 rerank 和 `RankedCandidate -> ChunkHit` 转换形成闭环；
- staged 内容只有 Mongo 事实和 Chunk 向量完整后才发布；直接读取与 outline 无权/旧版本时不返回正文；
- 旧 revision 候选无法混入当前请求；
- 图谱组件完全不启动时普通检索仍通过。

## 7. P5：Ontology、GraphExtractor 和 GraphIndexer

### 工作内容

1. 复用现有 `Ontology`、EntitySpec、RelationSpec，不增加 ontology 独立版本 ID。
2. 实现三层约束：Prompt renderer、结构化输出校验、写入前业务硬校验。
3. 实现 `GraphExtractor.transform(chunks)`，将结果写入普通 metadata 的 `entities` 和 `relationships`。
4. Transformer 不访问 GraphStorage 或 VectorStorage。
5. 实现 `GraphIndexer.index(chunks)`：读取抽取 metadata，生成确定性结构关系，执行实体归一、关系去重和 ontology 校验。
6. 确定性 Producer 与 LLM Extractor 结果都保存在来源 Chunk metadata；GraphIndexer 统一归一后投影到同一 GraphNode/GraphEdge 模型，不设计事实优先级和复杂冲突仲裁。
7. Entity ID 使用 ontology domain、类型和规范化名称；相同稳定 ID 采用基础 upsert。
8. 先由 `ChunkFactsIndexer` 保存完整的 Chunk 图谱 metadata，再由 GraphIndexer 写拓扑和配置的 Entity/Relationship vectors；投影失败不回滚 Chunk 事实，可据此重建。
9. `graph_enabled` 由外部选择 Pipeline，组件不自行判断。
10. Plugin 只增加 `name`、`version` 和由两者生成的 `plugin_id`，PluginRegistry 负责冲突判定。

### 验收门槛

- 非法 Entity/Relationship 按事实粒度丢弃，合法事实继续处理；
- GraphExtractor 只写 metadata，GraphIndexer 才写 Storage；
- 确定性和 LLM 两条路径进入同一 GraphStore 模型；
- 在普通 Pipeline 成功发布之后独立构建可选图谱；图谱失败不撤销已发布的普通内容，任一 Pipeline 自身仍严格 fail-fast；
- graph-enabled Pipeline 消费完整 Chunk 列表，没有 Chunk selector；
- 相同 plugin name/version 生成相同 plugin_id，重复注册被拒绝。

## 8. P6：LightRAG 图谱查询

### 工作内容

1. 以 P5 已完成的抽取为基础，复制本地 LightRAG 查询语义，不依赖 LightRAG runtime；记录参考 commit 和最小原版用例，不以自己生成的期望值宣称对齐。
2. 实现 Entity/Relationship keyword 处理、规范化、去重、描述合并、token 截断和 query context 组装。
3. 实现 `GraphRetriever` 的 `local`、`global`、`hybrid` 三种模式，并配置其实际需要的 Entity/Relationship 向量 Writer/Reader；拓扑遍历本身不强制需要向量库。
4. `mix` 不进入 GraphRetriever；由外层组合 Chunk hybrid retrieval 与 graph retrieval。
5. GraphStorage 返回来源 Chunk ID；再通过既有 Chunk reader 批量读取正文并统一应用本地 ACL 和 selected revision。
6. 图谱查询按资源/revision 边界过滤，不能只依赖 Neo4j 投影属性。

### 验收门槛

- local/global/hybrid golden cases 与参考语义一致；
- GraphStorage 不包含 query mode 编排；
- ACL、active revision 和 Neo4j 来源 Chunk ID 到 Mongo 正文回查通过；
- 图谱局部失败不会绕过普通 Chunk ACL；
- `mix` 仍在外层组合。

## 9. P7：Chunk 种子、候选节点和可选父块

### 工作内容

1. 普通 Chunk 检索结果直接从已授权 Chunk metadata 生成轻量 Entity `GraphNodeReference`。
2. `ChunkHit.graph_nodes` 只表示候选，不表示已经选中的 seed。
3. 模型选出的 node ID 必须再次验证 resource、content revision、ACL 和来源关系。
4. 只把验证通过的 node ID 放入 `GraphRetrieveRequest.seed_node_ids`。
5. 图遍历提供有界深度、方向、关系类型和节点类别约束。
6. 父块展开由外层工具参数控制，默认关闭；不把父块展开混入 Chunker 或 GraphStorage。
7. 节点候选补充失败时返回普通 ChunkHit，候选列表为空；响应层的空值移除仍由外部处理。

### 验收门槛

- Chunk hybrid retrieval 不依赖图谱才能返回；
- 模型未选中的候选不会自动进入 traversal；
- 跨 resource/revision 的 seed 被拒绝；
- 没有图谱 metadata 的 Chunk 仍是有效普通结果；
- 父块开关不改变 Chunk identity 和普通检索排序。

## 10. P8：发布、重建和切换准备

### 工作内容

1. 把 DocumentRevision 与包含图谱 metadata 的 Chunk 作为权威内容事实记录。
2. 从 Mongo Chunk metadata 按 Graph topology、Entity vector、Relationship vector 分别重建投影；重建投影不重新调用 Chunker 或 LLM。
3. 删除时先撤销 staged/applied 可见性，再异步清理 Mongo/Qdrant/Neo4j，失败可重试。
4. publication capability 只根据普通内容 Pipeline 成功及必需投影完整状态切换 applied；可选图谱在内容发布后独立执行，不把图谱异常改成 Pipeline 成功。
5. 清理旧 metadata builder、codec、selector、extracted node fields、ContextMigrationRequired 和未完成迁移分支。
6. 建立重建、重复事件、旧 revision、删除、投影部分失败和 ACL 缺失的故障矩阵。
7. 在 HTTP/MCP 之外完成 application、fake adapter、真实数据库 adapter 和离线重建的全链路测试。

### 最终门槛

- 从 Mongo 权威事实可重建普通向量和图谱投影；
- active revision 不因图谱附加能力失败而错误切换；
- 请求内不会混用不同 content revision；
- ACL 缺失、旧 revision 候选和超出已读取本地 ACL 的候选不能直接返回；ACL 投影相对上游撤权的延迟仍按 03 的已知边界保留，不能声称零延迟撤权；
- Chunk、Transformer、Indexer、Storage、Retriever 的职责边界可由 focused tests 证明；
- HTTP/MCP 尚未接入也不影响核心能力验收。

## 11. 阶段间依赖与可并行部分

关键路径为：

```text
P0
 -> P1 identity/ACL/revision
 -> P2 Chunk/Pipeline
 -> P3 Storage
 -> P4 ordinary retrieval
 -> P5 graph production
 -> P6 graph retrieval
 -> P7 seed composition
 -> P8 rebuild/publication
```

初版按切片串行推进，不设同时修改共享模型的独立分支。未来确有分工时可拆开同一合同的实现与测试，例如：

- P1 的 ACL tests 与 ContentRevision tests 可以并行；
- P3 的 VectorStorage fake 与 GraphStorage fake 可以并行；
- P4 的 Contextualizer tests 与 VectorIndexer adapter tests 可以并行；
- P5 的 ontology validator 与 GraphExtractor prompt/parser tests 可以并行。

这不是 Pipeline 的并行调度合同；不能跳过阶段门槛或把相邻阶段混成一次提交。
