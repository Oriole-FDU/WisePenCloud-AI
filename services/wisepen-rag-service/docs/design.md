# RAG V4 设计文稿

RAG V4
把文档摄入、可见版本选择和检索证据组织成可独立组合的能力。核心目标是：业务扩展能够复用通用链路，同时正文、版本与权限的权威边界保持清楚。本文解释决策与取舍，模型、接口和操作细节分别由[模型](models.md)、[抽象](abstractions.md)、[用例](README.md)
与[运维](operations.md)说明。

## 1. 以正文事实为中心

Document、DocumentStructure 和 Chunk 分别表达完整正文、原文结构和分块事实。保留它们的区别，使章节阅读可以直接切完整原文，检索可以按
Chunk 召回，而不必把数据库节点、标题节点与业务实体合成一个模型。

内容和 Chunk 图事实落在 Mongo；向量与 Neo4j
拓扑是可重建的投影。生成上下文帮助召回，不能替代原文；图描述也不能替代来源正文。这使展示、重排与证据读取有明确来源，避免用投影中的旧材料拼出看似完整的答案。实际数据流见[架构](architecture.md)。

内容身份只纳入资源、上游版本与原文摘要。业务字段和构建配置分别由摄入合同及显式维护负责，避免把每一种投影配置都扩展成内容身份。代价是
metadata/type 的摄入变更要提高 version，更换本体、分块或模型也不会自动重建历史数据。

## 2. 顺序写入，条件发布

五类抽象把正文边界、知识增强、投影生成、后端存取与候选召回分开。Pipeline 只负责固定顺序，开发者组合完整必需链；组件无需推断邻接阶段，也不为内部装配再造依赖图。

摄入成功不直接等于可见。发布用例保留旧 applied，先构建 staged 的内容与投影，再回查正文身份及本次预期 Chunk 集合，最后条件
apply。必需投影由各 Indexer 等待实际写入确认，不引入第二套完成清单。

这接受了跨库部分写入，换取清楚的失败恢复：失败停止后续阶段，旧版本仍可见，同 staged
重跑恢复。条件发布阻止被新版本或永久销毁取代的旧任务重新可见。详细状态与重试见[发布用例](usecases-publication.md)。

## 3. 授权与版本决定归应用用例

Retriever 只返回候选定位。application 用请求级快照选择资源版本和权限，再从内容事实回查材料，核对投影身份；通过这些检查的材料才进入排序模型和响应。查询不依赖向量库中的
ACL 副本，也不让召回组件保存用户状态。

一次上层编排显式共享首次完成的资源决定，使检索、目录与后续章节阅读保持相同版本选择。它不承诺三种数据库在同一时刻，也不在每个子操作中重新刷新权限。独立调用重新观察，事实缺失或身份不符返回部分结果；基础设施错误仍传播。边界见[授权用例](usecases-access.md)。

## 4. 图事实保留来源，查询保持通用

图逻辑实体可由多个 Chunk 支持，关系保留方向和独立来源描述。因此拓扑能够连接多个可见文档，而证据仍能逐条回查当前正文，不把共享图元的某次
upsert 当作所有来源的事实。

本体约束写入及缓存合法性；读取核对结构、来源、当前事实与明确筛选条件，不绑定一个当前本体对象。这样多个本体的事实可以共存，业务工具也能直接使用通用图用例。显式一跳让调用方根据证据选择后续探索，材料预算留给上层。当前筛选能力与证据范围见[图用例](usecases-graph.md)。

## 5. 平台生命周期统一，业务能力显式扩展

平台拥有唯一发布器、消费者、共享客户端、集合初始化、就绪与销毁 GC。扩展声明 Pipeline、额外集合和可选 API，不复制平台运行时。专用
metadata 只作为投影增量，通用身份始终来自 Chunk；业务差异不会外溢到所有存储或查询层。开发方式见[扩展指南](extensions.md)。

永久销毁先阻断可见性，再由 GC 反复回收已配置存储，保留标记以抵挡迟到写入。在线运行与维护窗口 repair
各自有明确入口：前者负责生命周期，后者修复显式资源且不改变发布状态。跨库强一致、在线重构建及活跃资源历史贡献回收仍是后续独立工作。

当前实现已经覆盖核心用例、装配与完整扩展示例；替身测试和真实环境验收分开记录。设计不把已实现能力重新写成待开发项，也不以单元测试通过代替模型效果或生产联调。
