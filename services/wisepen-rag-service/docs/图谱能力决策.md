# 图谱能力决策

本文记录当前图谱能力的边界和取舍。它约束后续维护：不要因为某个垂域的局部需求，把图谱、切块或检索底座扩张成没有明确消费者的通用框架。

## 1. 当前问题

图谱事实有两条来源路径：

- LLM 从 `DocChunk` 抽取节点和关系，并用 `TextGraphEvidence` 回到原文证据；
- 确定性 producer 从已校验的文档 metadata 或其他结构化事实生成节点和关系。

旧结果视图把 LLM 路径压缩成 Chunk 指针，把确定性路径压缩成图元、producer 和 revision 指针。它们都不足以让模型直接理解事实，调用方还要二次回查内部存储，既增加编排，也容易泄露审计和生命周期字段。

另一个实际问题是 LLM 默认对 active revision 的全部 Chunk 发起抽取。对论文这类资源，实体与关系往往集中在摘要、方法、实验说明或正文中的明确 instruction；把参考文献、附录和无关段落全部送入模型，成本高且噪声大。

## 2. 已采用的解决方案

### 2.1 结果以模型可读文本为中心

`GraphSearchResult` 统一返回 `GraphSearchHit`：

```python
GraphSearchHit(
    resource_id="paper-001",
    text="...",
    score=0.91,
    section_id="rsec_...",  # 仅 LLM Chunk 路径有值
    section_path=["论文标题", "摘要"],
)
```

LLM 路径的 `text` 是经 Evidence、版本和 ACL 校验后的 Chunk 完整可读文本；`section_id`、`section_path` 用于最小定位。确定性路径的 `text` 是图元投影的 `get_fact_text()`，由端点名称、谓词和事实描述组成。两条路径都不对结果暴露 Chunk ID、图元 ID、content revision、producer ID 或 Evidence ID。

`get_fact_text()` 同时服务局部精排和最终展示，保证模型看到的确定性事实就是系统实际判断相关性的文本，而不是另一套摘要或审计结构。

### 2.2 Ontology 保持宏观约束

Ontology 只定义实体类别、关系谓词和关系端点类别。它不约束 Chunk 类型、Chunk metadata 或标题层级。

这是有意保持的分层：Ontology 回答“图里允许什么事实”，Chunk 选择回答“哪些原文范围值得送去抽取”。将二者合并会把文档结构策略误写成领域事实，并迫使所有垂域服从同一种局部切分模型。

### 2.3 只在抽取前选择 Chunk

`RagPlugin.chunk_selector` 是 `Callable[[DocChunk], bool]`。图谱构建在调用 LLM 前筛出目标 Chunk：

```text
全部 revision Chunk
  -> plugin.chunk_selector
  -> 仅目标 Chunk 调用 LLM
  -> Evidence 仍只允许落在目标 Chunk
```

未选中的 Chunk 仍可以作为目标 Chunk 的共享上下文，不能单独产生事实。筛选为空时不回退全量抽取，也不把它视为构建失败；确定性 producer 继续处理完整 Document 并正常写入事实。

这个选择器只控制构建成本和噪声，不是通用查询过滤器。当前不增加“只检索实验部分”的图谱查询参数：这类细分过滤容易由主观标签造成漏召回，且尚无稳定、跨垂域的产品需求支撑其复杂度。

## 3. 当前适用范围

当前插件体系适合有完整 Markdown 正文、稳定 Section/Chunk 边界，以及文档级 metadata 的文档型资源。论文是典型场景：可用标题路径选择摘要、方法或实验 Chunk，引用、作者、机构等强结构化信息则由确定性 producer 生成。

`DocumentPreparer` 现在接收单个 `DocumentChunkMetadataBuilder`。它按已注册图谱插件的垂域规则，为匹配的文档 metadata 生成并持久化强类型 Chunk metadata；容器同时注册该类型，Mongo 回读后仍可恢复具体子类。`chunk_selector` 可据此选择抽取目标，也可继续读取标题路径、页码和锚点。

这条能力只解决“垂域如何在文档准备期给既有 Chunk 添加确定性语义”。它不改变 Ontology 的宏观职责，也不自动衍生 Chunk 级检索过滤。更细粒度的 Chunk 能力仍是可选的未来方向：应等待真实调用场景证明其标签权威性、召回代价和消费方价值后再决定是否继续扩展，而不是承诺必然实现。

插件核心位于 `rag.application.plugins.core`，并严格分为 `contracts`（metadata 模型与多态编解码）、`ontology`（图谱约束）、`plugin`（SPI 与 `RagPlugin`）、`filters`（声明式 metadata 过滤）和 `registry`（启动期装配、路由）。垂类只能依赖 `plugins.core`，彼此不能横向导入；核心也不得出现任何垂类字段或条件分支。未来出现真实垂类时，应在 `rag.application.plugins.paper`、`rag.application.plugins.course_plan` 等独立包中完整定义自己的 metadata、Chunk builder、Ontology、producer、过滤器和最终插件实例，包入口只导出一个 `RagPlugin`，再由容器显式注册。当前不预建这些空包。

图谱与文档检索的 metadata 查询过滤使用 `DeclarativeMetadataFilter`。垂类以 `Annotated` 声明面向模型的自然字段名（例如 `min_year`）与来源投影 metadata 键（例如 `publication_year`）的比较映射；`RagPlugin` 仅接受该声明类型并编译为既有 `MetadataFilterCondition`。因此 Qdrant、Neo4j 和调用方都不需要了解垂类内部的转换代码。该能力只允许查询插件已经写入来源投影的文档级 metadata 标量，不能借此过滤 Chunk metadata 或任意 JSON 路径。

## 4. 明确不提前抽象的资源

### 条款类资源

合同、制度、法规等条款资源的基本阅读和引用单位是条、款、项及其相互引用，不是通行 Markdown 切块或普通父块。它们需要独立的编号解析、层级、修订和引用定位语义。现有 Section/Chunk 可以承载原文，但不能代替条款模型。

### 纯表格资源

纯表格的行、列、单元格、合并单元格和跨表关系不具备稳定的自然语言 Chunk 边界。把表格强行按字符切块，会破坏字段对应关系，也无法可靠建立父块。当前不把表格抽取策略塞进通用图谱或 Chunk metadata。

如果未来出现明确的条款或表格产品需求，应优先为其设计独立资源边界、结构事实和检索/阅读契约；可能共享权限、版本和投影基础设施，但不应继续给当前通用文档底座堆叠抽象。这里是方向，不是实现承诺。

## 5. 后续维护原则

- 新增图谱字段前先确认它是否直接服务模型阅读、持久化生命周期或真实过滤需求；没有消费者的指针和审计字段不进入结果视图。
- 新增 Chunk 选择规则应由垂域插件承担，避免在 RAG 核心中写论文、课程等领域名称和规则。
- 若需要 Chunk 级查询过滤，先以真实产品问题验证召回损失、标签权威性和调用方需求；不要从抽取选择器自动推导出查询过滤协议。
- 若新增新的资源形态，先判断其结构单位是否仍是 Document/Section/Chunk；不是时建立独立边界，而不是修改 Ontology 来掩盖结构不匹配。
