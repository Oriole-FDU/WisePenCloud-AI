# RAG V4 子方案 07：摄入管线与五类核心抽象

## 0. 已确认架构

RAG 写入侧收敛为五类核心抽象：

```text
Chunker -> Transformer(s) -> Chunk(s)
                         -> Indexer(s) -> Storage

Retriever <- Storage Reader
```

核心职责如下：

| 抽象 | 职责 | 不负责 |
|---|---|---|
| `Chunker` | 将 Document 分成 Chunk，确定边界、顺序和结构归属 | Embedding、图谱抽取、持久化 |
| `Transformer` | 对 Chunk 做内容加工或知识增强 | 直接访问 Storage、Embedding、持久化 |
| `Indexer` | 通过 Writer 保存最终 Chunk 事实或构建检索投影 | 底层 CRUD、检索策略 |
| `Storage` | 提供内容、向量、图的存取原语 | ACL、revision 生命周期、检索模式 |
| `Retriever` | 通过 Storage Reader 执行查询策略和候选组合 | 索引构建、持久化 |

`IngestionPipeline` 只负责组装和执行 Chunker、Transformers、Indexers，不理解 Indexer 内部如何生成 embedding 或写入数据库。

## 1. Document、Chunk 与派生 metadata

### 1.1 Document 和 Chunk

`Document` 是摄入的基础数据类型，`Chunk` 是分块后的主要内容单元。Chunk 继续保存 raw text、结构归属、顺序和 revision identity。

Document、DocumentStructure 和 Chunk 统一定义在 `rag/core/schema/content.py`，ingestion 和 ContentStorage 都依赖该框架合同；schema 不依赖执行阶段。旧 `document.py` 和 ingestion 的 Chunk 导出不保留。

```python
@dataclass(slots=True)
class Chunk:
    chunk_id: str
    resource_id: str
    content_revision: str
    chunk_index: int
    section_id: str | None
    section_path: list[str]
    raw_text: str
    content_token_count: int
    anchor_labels: list[str]
    metadata: dict[str, object] = field(default_factory=dict)

    @property
    def retrieval_text(self) -> str:
        context = str(self.metadata.get("contextual_context") or "").strip()
        return f"{context}\n\n{self.raw_text}" if context else self.raw_text
```

### 1.2 metadata 的边界

本次不恢复旧的任意垂类 `ChunkMetadataBuilder`、metadata codec 或插件自定义 Chunk metadata 注册链。`metadata` 是普通 `dict[str, object]`，由开发者遵守约定的 key：

```python
metadata["contextual_context"]  # Contextualizer 的检索上下文，可缺失
metadata["entities"]            # GraphExtractor 的 Entity 结果
metadata["relationships"]       # GraphExtractor 的 Relationship 结果
```

约束：

- `metadata["contextual_context"]` 是检索正文拼接使用的约定字段；
- `entities` 和 `relationships` 是 GraphExtractor 的抽取结果，也是持久化 Chunk 中可重放的图谱事实输入；
- 图谱启用时，Chunk metadata 随 Chunk 事实写入 Mongo；它是重建图投影的来源，不意味着 Entity/Relationship 在语义上从属于 Chunk；
- Transformer 可以原地修改 metadata，也可以返回新的 Chunk；Indexer 只读，不通过 `pop()` 等操作消费或修改共享 metadata；
- 不允许通过 metadata 改变 Chunk identity、顺序、ACL 或 active revision 语义。

这些是开发者遵守的组件约定，不引入 metadata Pydantic 模型、字段注册表、通用 schema 校验或逐阶段防御性检查。LLM 输出解析和 ontology 事实校验仍由图谱组件承担，二者不等同于对 Chunk metadata 建立类型校验体系。

Chunk 不要求不可变，也不由 Pipeline 自动深拷贝。开发者负责保持身份和来源字段稳定，并保证 Indexer 只读共享输入。

## 2. Chunker

```python
class Chunker(Protocol):
    async def split(self, document: Document) -> list[Chunk]: ...
```

Chunker 负责：

- 分块边界；
- `chunk_index`；
- Section 归属和 section path；
- 必要的结构字段；
- `resource_id`、`content_revision` 命名空间下的 Chunk identity。

Chunker 不调用 embedding、LLM、GraphStorage、VectorStorage 或 Mongo。

## 3. Transformer

### 3.1 通用合同

```python
class Transformer(Protocol):
    async def transform(
        self,
        chunks: list[Chunk],
        *,
        document: Document | None = None,
    ) -> list[Chunk]: ...
```

Transformer 可以顺序组合，类似 LlamaIndex 的 Node transformations，但使用 RAG 自己的 Chunk，不引入 Node 抽象。

每个 Transformer 接收完整 `list[Chunk]`，自行决定逐 Chunk 处理、批处理或内部并发；Pipeline 不逐 Chunk 调用，也不增加上下文抽象。

每个 Transformer 必须：

- 保持 Chunk 数量和顺序；
- 保持 `chunk_id`、resource、revision、chunk_index、section_id 和 raw_text；
- 可以原地修改 `metadata`，也可以返回新的 Chunk 列表；Pipeline 始终使用返回值；
- 不直接访问 Storage；
- 不做 embedding；
- 不负责持久化和索引；
- 不承担 Chunk selector 职责。

### 3.2 Contextualizer

`Contextualizer` 为 Chunk 生成可选 contextual context：

- 使用传入的 Chunk 列表、section 字段和已准备好的必要结构 metadata；
- 优先使用同一 Section 的连续上下文；
- 超预算时按 Chunk 顺序取相邻窗口；
- 不跨 resource、revision 或不相关 Section；
- 不修改 raw text；
- Transformer 内部可以把可接受的单 Chunk 缺失结果表示为空 metadata；真正的异常直接终止 Pipeline。

### 3.3 GraphExtractor

`GraphExtractor` 从 Chunk raw text 和允许的 contextual background 中提取 LightRAG 风格的 Entity/Relationship：

- 接收 ontology；
- 只输出 ontology 允许的类型；
- 将抽取结果写入 Chunk 的 `metadata["entities"]` 和 `metadata["relationships"]`；
- 不写 GraphStorage 或 VectorStorage；
- 不负责最终实体归一、关系去重和 upsert；
- 确定性结构关系由 GraphIndexer 生成，不要求新增一条结构 Transformer 路径。

`graph_enabled=False` 时由外部组装入口不把 GraphExtractor 放入 Pipeline；已有图谱事实不受影响。

## 4. Indexer

### 4.1 通用合同

```python
class Indexer(Protocol):
    async def index(self, chunks: list[Chunk]) -> None: ...
```

Indexer 是 Transformer 与 Storage 之间的明确边界。多个 Indexer 接收同一批只读 Chunk，不应通过修改共享 metadata 影响其他 Indexer。

Pipeline 按配置顺序串行调用 Indexer。Indexer 内部可以批处理或并发，但初版不提供跨 Indexer 并行调度。

### 4.2 VectorIndexer

`VectorIndexer` 负责：

1. 选择 Chunk 的索引文本，默认使用 `chunk.retrieval_text`；
2. 调用 embedder 生成 Chunk embedding；
3. 生成统一 `VectorRecord`；
4. 通过注入的 `VectorWriter` 批量 upsert 到绑定的 Chunk collection；

```python
class VectorIndexer:
    async def index(self, chunks: list[Chunk]) -> None:
        # 选择索引文本、生成 embedding 并转换为 VectorRecord。
        # 调用注入的 VectorWriter.upsert() 完成写入。
        ...
```

Embedding 属于 VectorIndexer，因为 embedding 维度、文本选择和目标 collection 都是索引语义，不是通用 Transformer 语义。

### 4.3 GraphIndexer

`GraphIndexer` 负责：

1. 读取 Chunk metadata 中的 Entity/Relationship 抽取结果；
2. 结合 Chunk 携带的结构 metadata 生成确定性图事实；
3. 执行必要的 Entity 归一、Relationship 去重和 ontology 校验；
4. 将 GraphNode/GraphEdge 投影到注入的 `GraphWriter`；
5. 从每个图事实所属 Chunk 派生 source Chunk ID，并写入 GraphStorage 投影；图谱事实本身保留在 Chunk metadata；
6. 对配置的 Entity/Relationship vector collection 生成 embedding 并调用 VectorWriter。

GraphIndexer 不实现 Neo4j、Qdrant 或 Mongo CRUD，也不负责 local/global/hybrid 查询。

```python
class GraphIndexer:
    async def index(self, chunks: list[Chunk]) -> None:
        # 从 metadata 收集实体与关系，生成确定性结构关系。
        # 实体归一、关系去重和 ontology 校验后调用 GraphWriter.upsert_nodes/relations()。
        # 按配置生成 Entity/Relationship 向量并调用 VectorWriter。
        ...
```

### 4.4 Indexer 失败

- 最小 Pipeline 按配置顺序执行，任一未处理异常直接向调用方传播，不提供 `continue_on_error`、回滚或统一 failure 对象；
- Transformer 失败时不调用后续 Transformer 或 Indexer；
- Indexer 失败时停止后续 Indexer，已经完成的写入保留；
- GraphExtractor 可以在自身成功的情况下把没有抽取结果的 Chunk 表示为空 metadata，单个异常不能被 Pipeline 静默吞掉；
- Indexer 正常完成返回 `None`，不承担 Document 发布状态管理。

Pipeline 只有全部阶段成功才算成功；部分索引的可见性与 revision 发布由外部业务能力决定，Pipeline 不保证跨 Storage 原子性。

## 5. Storage 与 Retriever

### 5.1 Storage

Storage 只提供通用向量和图存储原语：

- `VectorStorage` 使用统一 `VectorRecord/VectorQuery/VectorMatch`；
- `GraphStorage` 直接使用 GraphNode/GraphEdge，并提供节点、关系、邻接和有界遍历；
- Reader/Writer 通过 Protocol 隔离，同一具体后端 Adapter 可以实现两者；
- collection 绑定 Storage 实例；
- 通用 `MetadataFilters` 由 plugin 编译、由 Storage 执行；
- VectorStorage/GraphStorage 不理解 Chunk 生命周期、ACL、active revision 或检索模式；现有 Mongo Chunk 内容事实仍由 RAG 内容写入能力负责。

### 5.2 Retriever

Retriever 独立于 IngestionPipeline，通过 Storage Reader 获取候选：

- 负责 query 构造、dense/sparse/hybrid、local/global/hybrid 和候选组合；
- 不调用 Indexer，不写 Storage；
- 当前 `retrieve(query: str)` 可以保留；
- Dense、Sparse、Hybrid 或图谱策略通常在 Retriever 初始化时配置；
- 动态切换由外层选择不同 Retriever 实例或组合，而不是 Storage 解释 mode。

## 6. IngestionPipeline

### 6.1 配置形态

```python
pipeline = IngestionPipeline(
    chunker=chunker,
    transformers=[
        Contextualizer(llm),
    ],
    indexers=[
        ChunkFactsIndexer(writer=content_storage),
        VectorIndexer(
            writer=chunk_vectors,
            embedder=embedder,
        ),
    ],
)

await pipeline.run(document)
```

`chunker` 可以使用 MarkdownChunker 实现；Embedding 位于 Indexer；写入侧通过 Storage Writer 完成持久化。

上述配置表示普通内容 Pipeline。它成功后由外部 publication 条件发布，再独立执行可选图谱构建；可选图谱异常不会被吞掉或撤销已发布的普通内容。

最小执行合同为：

```python
class IngestionPipeline:
    def __init__(
        self,
        *,
        chunker: Chunker,
        transformers: list[Transformer],
        indexers: list[Indexer],
    ):
        self.chunker = chunker
        self.transformers = transformers
        self.indexers = indexers

    async def run(self, document: Document) -> list[Chunk]:
        chunks = await self.chunker.split(document)

        for transformer in self.transformers:
            chunks = await transformer.transform(chunks, document=document)

        for indexer in self.indexers:
            await indexer.index(chunks)

        return chunks
```

`Document` 进入 `Chunker.split()`，并作为可选参数传给 Transformer。Transformer 和 Indexer 都接收完整的 `list[Chunk]`；Indexer 按只读约定消费同一批列表，不依赖 Document 生命周期或上游 DTO。

Document metadata 和结构中确实被后续组件消费的信息，在准备或分块时传递到 Chunk 字段或普通 metadata；不要求每个 Chunk 携带完整 Document，也不恢复插件的逐 Chunk metadata builder/codec 链。

### 6.2 执行顺序

```text
Document
  -> Chunker
  -> raw Chunks
  -> Transformer 1
  -> Transformer 2
  -> transformed Chunks
  -> each Indexer
  -> each Indexer's Storage Writer
```

Pipeline 不直接处理 embedding、图谱去重或数据库 CRUD。它只负责顺序、共享输入和等待各 Indexer 完成，不提供并行调度。

### 6.3 Document 策略与发布边界

- 组装入口根据 Document 级 `graph_enabled` 决定是否配置本次 GraphExtractor/GraphIndexer；启用时消费完整 Chunk 列表；
- 上层可以预先组装并复用普通检索 Pipeline 与带图谱的 Pipeline，GraphExtractor/GraphIndexer 自身不解释 Document 级策略；
- `graph_enabled=False` 不清理已有图谱，也不影响已有图谱的查询；
- `ChunkFactsIndexer` 是 `Indexer` 的具体实现，依赖 `ContentWriter.upsert_chunks()` 持久化最终 Chunk 与普通 metadata；MongoContentStorage 同时实现 ContentReader 和 ContentWriter，保存独立的 Document、Chunk 模型；不另加 Repository 或通用 Mongo Storage 框架；
- staged/applied 和物理销毁属于 `application.publication` 的应用用例，不加进通用 Pipeline 的三个执行循环；
- VectorIndexer/GraphIndexer 均使用 `index(chunks) -> None`，Pipeline 使用 `run(document) -> list[Chunk]`；只有全部阶段成功才返回最终同一列表；
- 普通检索与图谱的发布、降级策略由业务入口决定，不通过额外返回对象或隐式回调扩大核心接口。

### 6.4 开发者装配合同

内部组件由开发者正确装配，并通过行为测试验收。DocumentPublication.publish 内部完成摄入，只注入外部完整 Pipeline；外部固定 `ChunkFactsIndexer -> 必需投影 Indexers`。必需投影配置齐全且全部写入确认后才成功，是开发者遵守的合同。

Pipeline 和用例不增加组件识别、空配置检查、装配校验、`produces/consumes` 声明、依赖图或逐阶段 metadata 校验。图谱的 Extractor/Indexer 配对及对应向量 Writer 也由开发者负责。发布时回查持久化内容属于 application.publication 的事实检查，不是 Pipeline 装配检查。

## 7. 实施顺序

### 07-A：统一 Chunk 派生 metadata

- 保留普通 `dict[str, object]` 作为 Chunk 的 `metadata`；
- 约定 `metadata["contextual_context"]`、`metadata["entities"]` 和 `metadata["relationships"]` 的用途；
- 对启用图谱的 revision，将 `entities`/`relationships` 随 Chunk 持久化；`contextual_context` 不因此变成必需的持久化字段；
- 由 `retrieval_text` property 从 `metadata["contextual_context"]` 组装检索文本；
- 删除旧的任意 Chunk metadata builder/codec 和 `chunk_selector`；
- 保证 metadata 不改变 Chunk 基础身份。

### 07-B：实现 Chunker/Transformer/Pipeline

- 定义 `Chunker.split(document)`、`Transformer.transform(chunks)`、`Indexer.index(chunks)` 和 IngestionPipeline；
- 实现 Contextualizer；
- 实现 GraphExtractor；
- 通过组件验收验证数量、顺序和 identity 不变量；Pipeline 不做装配检查或深层 metadata schema 校验；
- 保证 Transformer 不访问 Storage。

### 07-C：实现 VectorIndexer

- 选择 `retrieval_text`；
- 调用 embedder；
- 生成 VectorRecord；
- 通过 VectorWriter 写入 Chunk collection；
- 成功返回 `None`，失败按具体组件语义抛出异常。

### 07-D：实现 GraphIndexer

- 消费 Chunk.metadata 中的 Entity/Relationship；
- 装配确定性结构事实和语义事实；
- 通过 GraphWriter 写入 GraphStorage，并按配置写入图向量 Storage；
- source Chunk ID 从持久化 Chunk metadata 派生并随图投影保存；查询时 GraphStorage 返回来源 Chunk ID，再由 Mongo Chunk reader 回查正文，不建立独立 GraphFactStore/GraphChunkSource 集合；
- 失败停止后续 Indexer，不回滚已经完成的普通 Chunk projection。

## 8. 验收证据

1. `Chunker.split(document) -> Transformer.transform(chunks) -> Indexer.index(chunks)` 可以独立执行；
2. Transformer 不访问任何 Storage，也不生成 embedding；
3. Contextualizer 只写入 `metadata["contextual_context"]`，不修改 raw text 或 identity；
4. GraphExtractor 只把抽取结果写入 Chunk 派生 metadata；
5. VectorIndexer 和 GraphIndexer 可以消费同一批 Chunks；
6. 一个 Indexer 不会通过修改共享 Chunk metadata 影响另一个 Indexer；
7. VectorIndexer 负责 Chunk embedding 和 VectorRecord 投影，并只依赖 VectorWriter；
8. ChunkFactsIndexer 持久化完成 Transformer 加工的 Chunk facts；GraphIndexer 负责图谱归一、校验和图投影，并只依赖 GraphWriter 及其配置的图向量 Writer；
9. Storage 只被 Indexer Writer 和 Retriever Reader 使用；
10. 未处理的异常向调用方传播；Indexer 失败停止后续 Indexer，但不回滚已完成的 Chunk 向量写入；
11. `graph_enabled=False` 不执行新图谱抽取，但不删除已有图谱；
12. Pipeline 配置缺少 GraphExtractor/GraphIndexer 消费关系时，在构造或启动阶段立即失败；
13. Transformer 可以原地修改 metadata 或返回新 Chunks，下一阶段始终接收其返回值；Pipeline 不自动深拷贝；
14. Transformer 异常停止后续所有阶段；Indexer 异常停止后续 Indexer，Pipeline 只有全部阶段成功才正常返回；
15. 所有组件按配置顺序串行调用，组件内部批处理与并发由自身负责；
16. 上层可以复用不同 Pipeline 配置，Document metadata 只传递后续组件真正需要的信息；
17. IngestionPipeline 不承担数据库 CRUD、图谱检索策略或跨库一致性。
