# 持久化设计

本文确定 RAG V3 的最终持久化边界。目标是减少在线跨库 IO，同时保留旧代码中已经验证的 staged/applied 发布一致性和 ACL 同步行为。

## 1. 先说结论

- Mongo 保存内容、结构、Chunk、LLM 文本 Evidence 和 RAG 本地 ACL 事实。
- Qdrant、Neo4j 是可由 Mongo 事实重建的检索投影。
- 一个资源只有一个状态记录，记录正在构建的 `staged_content_revision` 和当前生效的 `applied_content_revision`。
- 新版本所有数据和索引准备好后，才把 staged 原子提升为 applied。
- 首版不拆 `source_part`，不保存静态父块、查询结果、索引拼接文本或 Redis 内容缓存。

## 2. 仓储总览

| 存储 | collection / 投影 | 保存内容 | 角色 |
|---|---|---|---|
| 上游 Mongo | `wispen_resource_items` | 资源和 ACL 来源事实 | 上游权威，RAG 只读 |
| RAG Mongo | `resource_index_states` | staged/applied 内容版本指针 | 发布协调事实 |
| RAG Mongo | `resource_acls` | 从上游投影的当前 ACL | RAG 在线判权事实 |
| RAG Mongo | `document_revisions` | 内容版本、Markdown、结构、metadata | RAG 内容权威 |
| RAG Mongo | `doc_chunks` | DocChunk 和增强产物 | RAG 检索事实 |
| RAG Mongo | `text_graph_evidences` | LLM 图谱抽取的文本 Evidence | RAG 图谱事实 |
| Qdrant | `document_chunk_vectors` | Chunk Dense + BM25 | 可重建索引 |
| Qdrant | `graph_node_vectors` | 图节点 Dense | 可重建索引 |
| Qdrant | `graph_edge_vectors` | 关系 Dense + BM25 | 可重建索引 |
| Neo4j | GraphNode、GraphEdge；LLM 图元的 Evidence 关联；确定性图元的资源/revision/producer 投影 | 图谱拓扑投影 | 可重建索引 |

### 2.1 一个 Mongo revision 文档

首版把一个 revision 的 `raw_content`、Common `Section`、`Page`、`Anchor` 和文档 metadata 放在同一个 `document_revisions` 文档中。正常读取不会访问 source part、section collection、page collection 等多个 Mongo collection。

只有实际数据证明存在 Mongo 单文档大小问题时，才引入正文分片；不为低概率异常提前承担持续复杂度。

`doc_chunks` 和 `text_graph_evidences` 独立保存，因为数量多、更新节奏不同，且查询需要按 ID 批量取回。确定性 producer 不创建 Evidence 文档，其图元直接写入图存储和图索引。禁止逐条跨库读取。

## 3. `resource_index_states`：staged / applied

```python
class ResourceIndexState(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    resource_id: str
    staged_content_revision: str | None = None
    staged_document_version: int | None = None
    applied_content_revision: str | None = None
```

唯一索引：`unique(resource_id)`。

- `staged_*`：当前允许继续构建的一版；
- `applied_content_revision`：在线查询唯一可见的一版；
- 两者都为空表示资源尚未发布。

不放 Kafka offset、删除状态、结构/检索/图谱多套 revision 或构建进度。

### 3.1 发布流程

```text
stage_revision(revision)
  -> 写 document_revisions、doc_chunks、text_graph_evidences
  -> 写 Qdrant 三类索引和 Neo4j 投影
  -> 完整性检查
  -> apply_revision(revision)
  -> 异步清理旧 revision
```

`stage_revision` 使用文档版本单调条件：较旧版本不能覆盖较新 staged 版本；相同 revision 重试幂等。`apply_revision` 只有在状态仍指向这版 staged revision 时才允许执行，并在一次 Mongo 原子更新中设置 `applied_content_revision`、清空 staged 字段。新版本构建期间如果又 stage 了更新版本，旧任务 apply 会失败，不能覆盖线上版本。

查询只读取一次状态记录，拿到 `applied_content_revision`，后续 Mongo/Qdrant/Neo4j 查询全部带该版本过滤。旧版本清理失败只影响占用，不影响正确性。

删除资源时先原子清空 staged/applied 指针，资源立即不可查询，再异步物理删除各库数据；不保留逻辑删除标记和回滚状态机。

删除任务按资源和 revision 批量执行，重复执行必须成功或明确返回“已不存在”。某个库失败时保留可重试任务；超过重试上限进入 DLQ 并报警。清理失败不会恢复 active 指针，也不会让查询读取残留旧投影。

上游文档事件只作为触发信号。消费者按 `document_version` 做单调判断：旧版本忽略，同版本允许幂等重试；不保存 Kafka offset，也不以消息到达顺序代替权威版本。

## 4. ACL 仓储

上游 `wispen_resource_items` 是 ACL 所有权和来源权威。RAG 使用旧代码的 `AuthoritativeAclReader` 将 `ownerId`、用户 VIEW 权限位和 `computedGroupAcls` 投影到本地 `resource_acls`：

```text
resource_id
acl_revision
owner_id
readable_users
excluded_read_users
group_acls
```

`resource_acls` 唯一索引为 `unique(resource_id)`，写入沿用 `save_if_newer`：更高 revision 才覆盖，相同 revision 重试允许成功。

在线查询从本地 `resource_acls` 批量读取 ACL 并调用 `ResourceAcl.can_read()`。Qdrant 和 Neo4j 的 ACL 只是预过滤投影；最终返回正文或 Evidence 前必须复查本地 ACL。ACL 更新不需要重建内容 revision。

## 5. Mongo 内容事实

所有内容事实携带 `resource_id + content_revision`，允许新旧 revision 在发布切换期间并存。

### 5.1 `document_revisions`

一条记录保存 `resource_id`、`content_revision`、`document_version`、`content_sha256`、完整 `raw_content`、重写全局 ID 后的 Common `sections/pages/anchors` 和强类型文档 metadata。

唯一索引：`unique(resource_id, content_revision)`。

另建多键索引 `structure.sections.section_id`。RAG Section ID 包含资源和 revision，Section 读取与邻域工具可以用一批 ID 一次定位候选 revision，再批量核对 `resource_index_states.applied_content_revision` 和 ACL。旧 revision 即使尚未异步清理，也不能因 Section ID 命中而变成可读。

### 5.2 `doc_chunks`

保存完整 `DocChunk`：身份、版本、顺序、Section 定位、`raw_text`、`source_spans`、页/Anchor 标签、增强产物、强类型 Chunk metadata 和 `extracted_node_ids`。

索引：`unique(chunk_id)`、`unique(resource_id, content_revision, chunk_index)`，以及按资源、版本、Section 的查询索引。

不保存 Dense/BM25 拼接文本、向量、静态父块或 Chunk Set ID；这些由 DocChunk 方法或查询时动态装箱重建。

### 5.3 `text_graph_evidences`

只保存 LLM 从正文抽取图元时产生的 `TextGraphEvidence`：Evidence ID、目标图元、资源和版本、Chunk ID、Section ID、原文坐标及 quote。quote 必须能从当前 Markdown 回读。

索引：`unique(evidence_id)`、`(target_type, target_id)`、`(resource_id, content_revision)`。

确定性 producer 的强类型输入已经在生成时完成校验，不建立 metadata Evidence collection。其图元投影保存资源、content revision、producer 标识以及检索和过滤真正需要的字段；active revision 和 ACL 直接决定这些图元是否可见。

## 6. Qdrant 与 Neo4j 投影

- `document_chunk_vectors`：Chunk Dense + BM25，payload 只放 Chunk ID、资源/版本、Section ID、`extracted_node_ids`、ACL 预过滤和已注册 metadata 过滤字段。
- `graph_node_vectors`：节点 Dense，payload 放节点 ID、类别、资源集合、ACL 和 metadata 过滤投影。
- `graph_edge_vectors`：关系 Dense + BM25，payload 放边 ID、端点、关系类型、资源集合、ACL 和 metadata 过滤投影。
- Neo4j：保存 GraphNode、GraphEdge；LLM 图元关联 `evidence_id`，确定性图元直接携带资源、revision 和 producer 投影。LLM 图元必须回到正文 Evidence；确定性图元不经过 Evidence resolver。

这些投影都必须带版本或能追溯到带版本的 Evidence。查询顺序是：读取 active 状态 -> Qdrant/Neo4j 候选 -> 按版本和 ACL 批量回查 Mongo -> 排序/门控 -> 返回。不会为每个候选单独跨库读取。

## 7. 不持久化的数据

- 动态父块及其正文；
- 标题树邻域、命中森林、全局大纲和 Page/Section 读取结果；
- reranker 分数、相关性门控结果和一次查询候选池；
- `semantic_index_text`、`lexical_index_text` 和图元索引拼接文本；
- `SectionIndex`、格式化面包屑、Kafka offset、逻辑删除、静态 ReadingBlock、Chunk Set ID。

## 8. Redis 决策

首版不使用 Redis。一次 Page/Section 请求只读取一次 `document_revisions`，检索结果按资源和版本批量回查；当前没有证据表明整资源缓存能抵消 active 切换、ACL 更新、失效和大对象占用的复杂度。

只有监控证明同一 `resource_id + applied_content_revision` 高频重复读取且 Mongo 组装成为显著瓶颈，才考虑缓存不可变 revision 内容。ACL 仍单独读取，缓存不能绕过 active 指针和权限复查。

## 9. 最终检查

- active pointer 是在线可见性的唯一门闩；staged 版本永远不可查询。
- apply 受 staged revision 条件保护，旧任务不能覆盖新版本。
- ACL 来源是上游资源记录，本地 `resource_acls` 是 RAG 在线判权副本，索引 ACL 仅预过滤。
- Mongo 一个 revision 默认一文档保存正文和结构，避免正常读取的多 collection 拼装。
- Chunk 和 LLM 文本 Evidence 使用批量查询，禁止逐条跨库 IO；确定性图元直接按 active revision 和 ACL 过滤。
- Qdrant、Neo4j 任何命中都必须按 active revision 和 ACL 回查 Mongo。
- 不持久化 source part、静态父块、读取结果、查询分数或 Redis 缓存。
