# RAG V3 架构与开发顺序

本文只规定 RAG V3 的分层职责、能力边界和开发顺序，不规定类名、框架写法或具体依赖注入形式。实现时应以各专项文档中的领域事实和结果契约为准。

## 1. 架构原则

RAG V3 不是一条每次请求都必须从文档处理走到图谱检索的流水线，而是一组围绕同一份 active 文档事实运行的独立能力。

需要区分两件事：

- **能力依赖**：例如索引必须消费 `DocChunk`，图谱构建必须消费文档和 Chunk 事实；
- **请求编排**：一次混合检索只执行混合检索需要的步骤，不自动触发图谱检索、标题树或读取。

因此，application 层按用例编排能力，不建立一个覆盖所有功能的总管对象，也不让 MCP 或 HTTP 入口决定内部顺序。

## 2. 四层职责

### 2.1 `api`

`api` 是传输适配层，负责：

- 接收 HTTP/RPC 请求；
- 做认证、基础参数校验和错误映射；
- 调用一个明确的 application 用例；
- 将 application 结果转换为外部响应。

API 请求/响应模型只属于传输边界。它们不应成为 application 或 domain 的内部数据结构。

### 2.2 `application`

`application` 负责业务用例和流程顺序。每个用例只编排完成自身目标所需的能力，并负责：

- 读取 active 指针和 ACL 前置状态；
- 调用 domain 接口；
- 组织批量读取、排序、门控和结果拼装；
- 决定失败是否中止、重试或交给异步清理。

application 不直接依赖 Mongo、Qdrant、Neo4j 或具体 LLM SDK。

建议按能力分组：

```text
application/
  document/       文档解析、Chunk 生成、增强
  graph/          图谱抽取、Ontology 校验、图谱事实构建
  indexing/       文档 Chunk 和图谱索引投影
  retrieval/      混合检索、图谱检索
  reading/        Page/Section 读取
  outline/        标题树局部视图
  publication/    revision 构建、发布、ACL 同步、删除
```

这些目录是能力边界，不表示它们必须对应同名类或单一文件。

### 2.3 `domain`

`domain` 只保留 RAG 需要长期稳定的事实和端口：

- 数据库实体及其持久化字段；
- Mongo、Qdrant、Neo4j 等仓储接口；
- Chunker、Embedding、Reranker、Graph Extractor、Ontology、ACL 等外部能力接口。

domain 不放 API schema、检索展示对象、标题树渲染结果或一次构建任务的临时上下文。

### 2.4 `core`

`core` 实现 domain 接口，包含：

- 数据库适配器；
- OpenAI/Instructor、Embedding、Reranker 客户端；
- Common chunker 和结构模型的适配；
- 上游资源、内容和 ACL 的客户端。

core 只提供技术能力，不决定“先做什么、是否调用另一项能力、返回哪些业务结果”。

## 3. 写入侧编排

写入侧只有一条需要协调的主流程：把一个文档版本准备好，完成文档检索投影，最后发布 active 指针。图谱是发布后的独立补建能力，不劫持这条主流程。

```text
上游文档和 ACL
  -> 文档事实准备
  -> 保存 Document、DocChunk、metadata
  -> 文档 Chunk 索引投影
  -> 完整性检查
  -> apply active 指针
       └─> 图谱事实构建与外部投影（独立触发、可单独重试）
```

### 3.1 文档事实准备

这一阶段只负责产生权威事实：

- 获取 Markdown 和文档 metadata；
- 调用 Common chunker 一次；
- 生成 RAG 自己的 Document、DocChunk；
- 生成 contextualize、key terms 等增强产物；
- 校验坐标能够从当前原文重建。

它不写 Qdrant，不写 Neo4j，也不构建静态父块。

### 3.2 投影构建

文档事实保存后，文档 Chunk 索引是发布前唯一的投影分支：

- Chunk 索引消费 DocChunk，写入文档 Dense/BM25 collection；

它通过完整性检查后才能 apply。图谱开关、图谱事实或图谱投影的失败均不影响文档可见性或混合检索。

### 3.3 图谱独立补建

图谱只从已发布的 Document、DocChunk 和 metadata 事实开始：垂类插件先生成 Mongo 图谱事实，随后独立投影到 Neo4j 和两个图谱 Qdrant collection。它可以按资源 revision 整体重跑，不重新解析文档；失败只返回失败结果，允许下一次重试。

图谱检索同样是独立查询用例。它只消费既有 Mongo 图谱事实和 Neo4j/Qdrant 投影，绝不在查询中抽取、投影、修复或发布文档版本。

### 3.4 发布

文档 Chunk 投影完成并通过完整性检查后，才将 staged revision 提升为 applied revision。发布协调只负责版本条件和可见性，不负责具体索引算法或图谱算法。

旧版本清理是发布后的异步工作。清理失败可重试或进入 DLQ，但不能恢复 active 指针。

### 3.5 ACL 同步

ACL 同步是独立写入用例，不要求重建内容 revision。它更新 RAG 本地 ACL 事实和索引过滤投影；查询在候选资源集合确定后读取一次本地 ACL 快照。允许异步传播延迟，ACL 缺失仍 fail-closed。

## 4. 查询侧编排

查询能力之间没有强制总顺序。它们都从 active 文档快照开始，但之后各自完成自己的工作。

### 4.1 混合检索

```text
文档 Dense/BM25 并集池
  -> active/ACL 快照
  -> 当前 DocChunk 批量回查
  -> reranker 和相关性门控
  -> ChunkHit
  -> 动态父块
```

混合检索只返回它的命中 Chunk、动态父块和从 Chunk 取出的 `node_ids`。它不隐式启动图谱检索。

### 4.2 图谱检索

```text
Low/High/Hybrid 图谱向量召回
  -> Neo4j 有限遍历和细粒度过滤
  -> active/ACL 快照
  -> LLM 图元批量回查 TextGraphEvidence 和 Chunk
  -> 确定性图元按快照校验 active revision 和 ACL
  -> 粗排
  -> 前 N 条精排
  -> Top-K Chunk/确定性图事实
```

调用方可以直接传 query，也可以把混合检索命中的实体节点 ID 作为 seed 传入。两种入口共享图元召回、粗排和请求级 ACL 快照；只有 LLM 图元进入 TextGraphEvidence/Chunk 回查，确定性图元直接参与排序。

### 4.3 标题树和读取

标题树只消费 active Document 的结构事实，生成批量 Section 邻域或全局大纲；读取只消费 active Document 的正文和结构，执行 Page 或 Section 读取。RAG Section ID 是全局且版本化的，邻域和 Section 读取可以只传一批 ID 跨资源调用。两者都不调用向量检索或图谱检索。

## 5. 跨用例共享的最小前置

所有查询都需要确定：

1. 当前 `resource_id` 的 applied revision；
2. 当前 Document 事实；
3. 当前用户是否具备读取权限。

可以在 application 层共享一个“active 文档快照加载”前置，但它只负责这三件事，不承载排序、渲染、父块构建或图谱遍历。

候选回查后的 ACL 判断属于具体查询用例，但它使用该请求已经建立的本地 ACL 快照，不重复读取同一批 ACL。

Section 邻域和 Section 读取是一个特殊入口：请求只提供全局、版本化的 `section_id`。application 先批量定位这些 ID 所属的候选 Document，再批量核对 applied revision 和 ACL；同一 Document 在一次请求内只装载一次。这个定位流程不改变正文和权限的权威来源。

## 6. 依赖方向

```text
api -> application -> domain interfaces/entities
                         ^
                         |
                      core adapters
```

约束如下：

- api 不直接访问 core persistence；
- application 不导入具体数据库客户端或具体 LLM SDK；
- domain 不依赖 api 和 core；
- core 不反向调用 application；
- 一个 application 用例可以依赖多个 domain 接口，但不应依赖另一个无关用例的内部实现。

## 7. 开发顺序与优先级

优先级按“所有能力的共同地基”到“可独立交付的查询能力”排序。

### P0：领域事实、仓储和可见性

先完成：

- Document、DocChunk、GraphNode、GraphEdge、TextGraphEvidence 等持久化实体；
- Mongo revision、Chunk、LLM 文本 Evidence 仓储接口和实现；
- staged/applied active 指针；
- 权威 ACL 读取、本地 ACL 投影和 `can_read` 语义；
- active 快照加载和批量回查基础能力。
- 全局 Section ID 重写、嵌入 Section ID 索引和跨资源批量定位。

验收标准：一个 revision 可以写入、查询 active 指针、按 ACL 判权，并能从 Mongo 重建完整文档事实。

### P1：文档准备和文档 Chunk 索引

再完成：

- Common chunker 适配；
- DocChunk 生成和坐标校验；
- contextualize、key terms 增强；
- Dense/BM25 文档索引投影；
- 索引投影的幂等写入和单独重建。

验收标准：同一 revision 可以重复构建，索引文本由 DocChunk 方法实时生成，Mongo 仍是正文权威来源。

### P1：混合检索和动态父块

在文档索引可用后立即实现：

- Dense/BM25 各自 Top-N 和并集去重；
- Mongo 批量回查和请求级 ACL 快照；
- Common ranking 及相关性门控；
- ChunkHit 和 `extracted_node_ids` 挂载；
- 动态父块构建，不保存静态父块。

验收标准：小块命中可准确回查，父块内容来自当前 Document，低相关结果不会被装箱逻辑掩盖。

### P2：图谱构建扩展点

然后实现：

- Instructor + Pydantic + OpenAI 抽取边界；
- GraphNode、GraphEdge、LLM TextGraphEvidence 持久化；
- Ontology 注册和校验；
- 确定性 producer 插件接口；
- 图谱 Node/Edge 两类向量投影。

验收标准：通用 RAG 不包含论文字段，但可以通过插件注册一个垂类 ontology 和一个确定性关系 producer；确定性图元无需 Evidence/resolver，LLM 图元必须完成正文 Evidence 回查。

### P2：图谱检索

图谱事实和两个向量 collection 可用后实现：

- Low、High、Hybrid 三种检索路径；
- query-only 和 seed-node 两种入口；
- direction、relation type、metadata 等过滤；
- LLM TextGraphEvidence/Chunk 批量回查；
- 确定性图事实直接校验；
- 两类候选的粗排、局部精排和 Top-K。

验收标准：不做 PPR 或贡献聚合；不会返回无法回读正文的 LLM 图元、旧 revision 的确定性图元或无权资源。

### P3：标题树和读取

最后实现用户侧阅读能力：

- 批量 Section 邻域和全局大纲；
- current JSON 定位字段、Markdown outline 和统一 `[+N]` 规则；
- Page 读取；
- Section `DIRECT` 和可控深度的 `RECURSIVE` Markdown 阅读。

验收标准：输出只展示轻量结构信息和正文，不返回内部 span，不引入 Range 读取，也不依赖图谱服务。

### P4：上层工具和运维增强

所有核心 application 用例稳定后再接入：

- HTTP/RPC/MCP 等调用入口；
- 重试、DLQ、指标和日志；
- 有数据证明后再评估 Redis 等缓存；
- 索引和图谱的后台重建任务。

工具层只能调用既有 application 能力，不能为了工具参数新增 RAG 内部字段或反向改变数据模型。

## 8. 每阶段的共同验收底线

- 查询只读 active revision；
- 所有外部索引命中都按版本和 ACL 回查；
- 正文权威来源是 Mongo Document，不是向量 payload；
- 跨库读取按批次完成，不逐候选单独 IO；
- 投影可从 Mongo 事实独立重建；
- 垂类能力通过插件和 ontology 扩展，不污染通用模型；
- application 编排能力，domain 保持事实和接口，core 提供技术实现。
