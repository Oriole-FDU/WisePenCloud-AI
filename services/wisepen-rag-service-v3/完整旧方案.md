# 一、前置基础工具增强

## 1. 混合检索融合算法拓展：并集池化（Union Pooling）

将该算法定义在common.ranking.fuse中，作为一个融合算法插件

在 RAG 检索流水线中，稠密检索（Dense Semantic Search）与稀疏检索（Sparse / BM25 Lexical Search）各有特异性（约 30% 独有语义召回、30% 独有专有名词召回、40% 重合召回）。

为了避免传统 RRF（倒数排名融合）因“共识优先”机制稀释单路高置信度特异结果，系统引入 **并集池化融合器（Union Pooling Fusion）**：在初检阶段不做启发式分数相加，各路并行截取 Top-K 候选，按唯一标识去重合并后，统一交由 Cross-Encoder Reranker 进行精准重排。

```text

                    │      User Query / Rewrite     │
                    └───────────────┬───────────────┘
                                    │
           ┌────────────────────────┴────────────────────────┐
           ▼                                                 ▼
┌──────────────────────┐                          ┌──────────────────────┐
│ Dense 检索 (Qdrant)  │                          │ BM25 检索            │
│ 取 Top-K 候选 (30 条) │                          │ 取 Top-K 候选 (30 条) │
└──────────┬───────────┘                          └──────────┬───────────┘

│  - 按 chunk_id 进行 Set Union 去重                                     │
│  - 形成 40~45 个无损候选池 (保留每路原始得分与来源标记)                 │
```

# 二、领域核心模型

本章节定义 RAG 系统的核心数据契约。设计原则只有三条：

1. **容器与切块职责分离**：权限、版本和结构骨架收口在 `Document` 容器；`DocChunk` 纯粹作为物理检索与坐标单元，不背负权限所有权。
2. **多态扩展**：通过 `Discriminated Union` 预留论文等专有类型的扩展插槽，当前通用模式下零冗余字段。
3. **权威真值与检索增强分离**：数据库只存一份权威原文 `raw_text`，用于向量化和 BM25 的 `embed_content` 通过方法即时装配，不额外占库。

## 2. 版本与聚合根 Document

`Document` 是系统的唯一权威事实源，持有权威 Markdown 原文、完整大纲树、多维版本和权限事实。

```python
class ContentRevision(BaseModel):
    """权威内容版本命名空间"""
    model_config = ConfigDict(frozen=True)

    resource_id: str = Field(..., description="资源 ID")
    doc_version: int = Field(..., ge=1, description="上游文档版本号")
    content_hash: str = Field(..., description="raw_content 的 sha256 前 16 位")

    @classmethod
    def create(cls, resource_id: str, doc_version: int, content: str) -> "ContentRevision":
        content_hash = hashlib.sha256(content.encode("utf-8")).hexdigest()[:16]
        return cls(
            resource_id=resource_id,
            doc_version=doc_version,
            content_hash=content_hash,
        )

    @property
    def revision_id(self) -> str:
        return f"{self.resource_id}@{self.doc_version}#{self.content_hash}"


class Document(BaseModel):
    """
```

## 3. 基本物理单位 DocChunk

`DocChunk` 是检索、向量化和局部坐标定位的最小物理单元（目标 ~800 字符）。它严格挂载在唯一一个 `Section` 下，使用连续递增的 `chunk_index` 替代链表指针，并统一通过 `get_embed_content()` 提供检索增强文本。

```python
class DocChunk(BaseModel):
    """
    RAG 物理检索原子 (单次切分核心载体)
    """
    model_config = ConfigDict(extra="ignore")

    # 1. 唯一标识与版本命名空间
    chunk_id: str = Field(..., description="规范化 ID，如 'res_1024_rev1_c3'")
    resource_id: str = Field(..., description="所属资源 ID")
    content_revision: str = Field(..., description="权威内容版本号")
    chunk_index: int = Field(..., ge=0, description="文档内全局连续切块序号 (0, 1, 2, ...)")

    # 2. 严格唯一归属的结构层级
    section_id: str = Field(..., description="唯一挂载的直属 Section ID")
    section_path: list[str] = Field(
        default_factory=list,
        description="标题面包屑路径，如 ['3. Methodology', '3.2 GQA']"
    )

    # 3. 权威原文与物理字符区间 (全系统唯一不可变真值)
    raw_text: str = Field(..., description="权威切片正文 (保留 LaTeX 与 Markdown 表格)")
    source_spans: list[SourceSpan] = Field(
        ...,
        description="在权威 Markdown 中的物理字符半开区间 [start, end)"
    )

    # 4. 检索增强字段 (仅存储，不影响权威原文)
    contextual_prefix: str = Field(
        default="",
        description="Anthropic 上下文前缀 (50~100 Tokens)：提供指代消解与段落定位"
    )
    key_terms: list[str] = Field(
        default_factory=list,
        description="提取出的核心概念/专有名词 (用于 BM25 词频提权与 Neo4j 实体挂载)"
    )

    # 5. 强类型过滤元数据（预留插槽，当前使用默认通用类型）
    metadata: AnyChunkMetadata = Field(default_factory=GeneralChunkMetadata)
    extral_meta: dict[str, any] = Field(default_factory=dict)

    # -----------------------------------------------------------------------
    # 检索增强文本装配
    # -----------------------------------------------------------------------

    def get_embed_content(self) -> str:
        """
        获取用于检索增强的文本（供 Dense 向量化与 BM25 分词共用）
        装配顺序：确定性标题路径 -> 动态上下文前缀 -> 专有关键词提权 -> 权威正文
        """
        blocks: list[str] = []

        # 1. 结构定位 (确定性锚点)
        if self.section_path:
            blocks.append(f"[{' > '.join(self.section_path)}]")

        # 2. 语义上下文 (软语义消解)
        if self.contextual_prefix:
            blocks.append(self.contextual_prefix.strip())

        # 3. 专有名词 (BM25 词频增益)
        if self.key_terms:
            blocks.append(f"Keywords: {', '.join(self.key_terms)}")

        # 4. 权威正文
        blocks.append(self.raw_text)

        return "\n\n".join(blocks)
```

## 4. ACL 权限模型（复用领域事实）

直接复用已验证的领域权限模型，保持请求身份、群组例外判定与资源授权逻辑完全一致。

```python
"""RAG ACL 的领域事实、请求身份和资源授权行为。"""

from collections.abc import Mapping
from dataclasses import dataclass, field
from common.core.domain import GroupRoleType


@dataclass(slots=True)
class PermissionScope:
    """一次可信请求中的用户身份和群组角色。"""

    user_id: str
    group_roles: dict[str, GroupRoleType | None] = field(default_factory=dict)

    @property
    def managed_group_ids(self) -> set[str]:
        """返回用户作为 owner/admin 管理的群组。"""
        return {
            group_id
            for group_id, role in self.group_roles.items()
            if role in (GroupRoleType.OWNER, GroupRoleType.ADMIN)
        }

    @property
    def joined_group_ids(self) -> set[str]:
        """返回用户实际加入的群组。"""
        return {
            group_id
            for group_id, role in self.group_roles.items()
            if role is not None and role is not GroupRoleType.NOT_MEMBER
        }

    @classmethod
    def from_group_roles(
        cls,
        user_id: str,
        group_roles: Mapping[str, GroupRoleType | None],
    ) -> "PermissionScope":
        """将安全上下文提供的角色映射复制为 ACL 规则使用的请求事实。"""
        return cls(user_id=user_id, group_roles=dict(group_roles))


@dataclass(slots=True)
class GroupResourceAcl:
    """一个群组在资源上的默认 VIEW 权限及成员例外。"""

    group_id: str
    default_readable: bool
    readable_users: list[str] = field(default_factory=list)
    excluded_read_users: list[str] = field(default_factory=list)


@dataclass(slots=True)
class ResourceAcl:
    """一个资源的完整 VIEW 授权事实。"""

    resource_id: str
    acl_revision: int
    owner_id: str
    readable_users: list[str] = field(default_factory=list)
    excluded_read_users: list[str] = field(default_factory=list)
    group_acls: list[GroupResourceAcl] = field(default_factory=list)

    def can_read(self, scope: PermissionScope) -> bool:
        """根据资源和群组规则判断当前请求是否拥有 VIEW 权限。

        资源 owner 和资源级显式授权优先于资源级排除；资源级排除只阻断
        后续普通群组授权。managed group 直接放行，joined group 遵循组默认
        权限和成员例外。
        """
        if scope.user_id == self.owner_id:
            return True
        if scope.user_id in self.readable_users:
            return True
        if scope.user_id in self.excluded_read_users:
            return False

        for group_acl in self.group_acls:
            if group_acl.group_id in scope.managed_group_ids:
                return True
            if group_acl.group_id not in scope.joined_group_ids:
                continue

            if group_acl.default_readable:
                if scope.user_id not in group_acl.excluded_read_users:
                    return True
            elif scope.user_id in group_acl.readable_users:
                return True

        return False
```

# 5. 知识图谱领域模型

## 5.1 设计思想：本体驱动、图文锚定与三态节点

系统在架构上将模式定义（Ontology）**与**图谱数据（Graph Data）明确分层：

1. **本体显式建模（Explicit Ontology Schema）**：

* 本体是可配置、可扩展的一等公民模型。不同垂域（论文、教材、代码库、医疗等）只需声明不同的 `Ontology` 实例，即可动态决定该领域的实体类别、合法关系谓词以及关联约束。

2. **图论空间与文本空间绝对正交**：

* `Node` 仅代表图论顶点，`DocChunk` 仅代表文本切片，概念不混淆、不继承。

3. **事实双向锚定（Evidence Grounding）**：

* 任何由本体构造出的实体（`GraphNode`）和关系（`GraphEdge`），必须通过 `GraphEvidence` 挂载到具体的 `DocChunk` 及其 `SourceSpan` 字符区间上，保证有据可查、杜绝幻觉。

4. **宏微一体的三态节点体系**：

* 节点收敛为三态：`entity`**（微观概念/算法/实体）**、`resource`**（库内收录的文档/课件）** 与 `extern_resource`**（未入库的外部引用/论文/仓库）**。保留外部节点为 Agent 后续触发联网搜索提供显式路标。

```text
┌────────────────────────────────────────────────────────────────────────┐
│                      显式本体模型 (OntologySchema)                      │
│   - entity_specs:  {"concept": ..., "author": ..., "model": ...}       │
│   - relation_specs: {"OPTIMIZES": ..., "CITES": ..., "PART_OF": ...}   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ (动态驱动抽取提示词 & 构造校验)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                      通用图谱底座 (Graph Domain)                        │
│   - GraphNode:  node_type (entity|resource|extern_resource), category  │
│   - GraphEdge:  relation_type (开放谓词), keywords, weight             │
│   - GraphEvidence:  chunk_id, source_spans, quote_text                 │
└────────────────────────────────────────────────────────────────────────┘
```

```python
        description: str = "",
        aliases: list[str] | None = None,
        node_type: Literal["entity", "resource", "extern_resource"] | None = None,
        extra_meta: dict[str, Any] | None = None,
    ) -> GraphNode:
        """根据本体规则构造合法的 GraphNode"""
        spec = self.entity_specs.get(category)
        resolved_node_type = node_type or (spec.default_node_type if spec else "entity")

        return GraphNode(
            node_id=f"{category}:{slugify(name)}",
            name=name.strip(),
            node_type=resolved_node_type,
            category=category,
            description=description.strip(),
            aliases=aliases or [],
            mention_count=1,
            extra_meta=extra_meta or {},
        )

    def build_edge(
        self,
        source_node: GraphNode,
        relation_type: str,
        target_node: GraphNode,
        description: str = "",
        keywords: list[str] | None = None,
        weight: float = 1.0,
    ) -> GraphEdge:
        """根据本体约束校验并构造合法的 GraphEdge"""
        rel_key = relation_type.strip().upper()
        spec = self.relation_specs.get(rel_key)

        # 拓扑合法性校验（若本体配置了约束）
        if spec:
            if spec.allowed_sources and source_node.category not in spec.allowed_sources:
                raise ValueError(
                    f"Invalid source category '{source_node.category}' for relation '{rel_key}'. "
                    f"Allowed: {spec.allowed_sources}"
                )
            if spec.allowed_targets and target_node.category not in spec.allowed_targets:
                raise ValueError(
                    f"Invalid target category '{target_node.category}' for relation '{rel_key}'. "
                    f"Allowed: {spec.allowed_targets}"
                )

        edge_id = GraphEdge.generate_edge_id(source_node.node_id, rel_key, target_node.node_id)
        return GraphEdge(
            edge_id=edge_id,
            source_node_id=source_node.node_id,
            target_node_id=target_node.node_id,
            relation_type=rel_key,
            description=description.strip(),
            keywords=keywords or [],
            weight=weight,
        )

    def to_extraction_prompt(self) -> str:
        """将本体规则动态编译为注入给 LLM 的抽取指令"""
        lines = [f"### 领域本体定义: {self.domain} ({self.description})", "#### 允许提取的实体类型:"]
        for k, v in self.entity_specs.items():
            lines.append(f"- **{k}**: {v.description}")
        lines.append("\n#### 允许提取的关系谓词与约束:")
        for k, v in self.relation_specs.items():
            constraint = ""
            if v.allowed_sources or v.allowed_targets:
                src = ",".join(v.allowed_sources) or "Any"
                tgt = ",".join(v.allowed_targets) or "Any"
                constraint = f" [{src} -> {tgt}]"
            lines.append(f"- **{k}**{constraint}: {v.description}")
        return "\n".join(lines)
```

## 5.4 出现频次（`mention_count`）的工程应用机制

`mention_count` 是图谱在长期运行中**对抗噪声、动态沉淀核心概念**的关键指标：

```text
                    ┌────────────────────────────────────────────────────────┐
                    │                      mention_count                     │
                    └───────┬───────────────┬────────────────┬───────────────┘
                            │               │                │
            ┌───────────────┴────┐   ┌──────┴──────┐  ┌──────┴───────────────┐
            ▼                    ▼   ▼             ▼  ▼                      ▼
     【图谱降噪与剪枝】          【PPR 拓扑扩散先验】      【Prompt 上下文装箱预算】
     低频孤立节点不入向量库       引导随机游走优先沿        综合公式打分截断：
     降低 40% 无效索引开销       高频骨干概念向下遍历     Score × α + log(count) × (1-α)
```

1. **图谱动态降噪与入库剪枝（Denoising & Pruning）**：

* 大模型提取容易产生长尾低价值实体（如“该实验”、“第一行”）。
* **策略**：只有 `mention_count >= 2` 或与已有核心节点存在强关系的实体，才被推入 Qdrant 建立稠密向量索引；单次提及的孤立节点仅存留在 Neo4j 低频冷区，避免稀释向量检索质量。

2. **PPR（个性化 PageRank）拓扑扩散先验**：

在进行 1~2 跳子图扩散时，将 $\log(mention\ count)$ 作为初始转移概率偏置。检索算法会优先沿着**领域公认的骨干概念**（如 `Attention`、`KV Cache`）向下遍历，抑制偏门杂音节点。

3. **Agent 提示词上下文装箱截断（Context Budgeting）**：

图检索召回数十个候选节点时，Prompt 预算有限。系统通过混合得分公式进行贪心截断

$$
FinalScore = Vectorsimilarity \times \alpha + \log(mention\_count) \times (1 - \alpha)

$$

确保高语义相关且高领域重要度的核心概念优先装入 Prompt。

# 三、核心算法设计

本章提炼 RAG 系统在**动态装箱、多路检索融合、图谱增量演化与扩散**四个维度的核心算法思路。算法设计聚焦于消除存储冗余、保证语义连续性与提供确定性计算逻辑。

## 1. 自适应动态父块装箱算法（Adaptive Parent-Context Assembly）

本算法参考

services\wisepen-chat-service\src\chat\application\tools\session_tools\cached_tool_output_tools\search_by_semantic.py

### 1.1 算法背景与设计哲学

传统 RAG 采用“离线切大块、再切小块”的静态父子索引，不仅导致存储体积膨胀 200%，且静态边界极易将连续的公式、表格或推导硬生生撕裂。 本算法采用“单次物理切分（~800 字符 DocChunk）+ 运行时内存自适应呼吸装箱”。在检索命中局部原子块后，算法以命中的焦点为中心向外动态扩散，在保证章节边界纯洁度的前提下，为下游 LLM 或 Agent 装配最佳视窗。

> **RAG Service 适配约束（去指针化）**： 本算法在 RAG 服务内部执行时，**不做任何&#x20;**`range_ref`**&#x20;或指针替换**，始终返回物理组装完成的完整父块文本（`assembled_text`）与精确绝对区间（`SourceSpan`）。大文本的上下文预算管理与截断缓存由调用方（Agent / Prompt Engine）统一管控，RAG 服务内部绝不进行静默截断。

### 1.2 完整决策流程（5 步装箱法）

```text
[ Rerank 命中 Top-N DocChunks ]
              │
              ▼
[ 1. 按 (resource_id, section_id) 聚合分桶 ]
              │
              ├─────────────────────────────────────────┐
              ▼ (Section ≤ 4000 字符)                   ▼ (Section > 4000 字符)
       【 步骤 1: 整章返回 】                    【 步骤 2 & 3: 窗口扩展与粘合 】
     直接取 Section 全文作为父块                   1. 每个 Chunk 前后各扩展一个chunk
                                                  2. 相邻间距 ≤ 2 chunk 自动粘合
                                                  3. 计算合并窗口在 Section 中的覆盖率
                                                        │
                              ┌─────────────────────────┴─────────────────────────┐
                              ▼ (窗口数==1 且 覆盖率≥80% 且 Section≤8000)          ▼ (其他常规情况)
                       【 步骤 2: 触发整章升级 】                           【 步骤 3: 产出合并视窗 】
                       整章高密度命中，升级为整章全文                         产出 1~M 个连续的父块视窗
                              └─────────────────────────┬─────────────────────────┘
                                                        │
                                                        ▼
                                            【 步骤 4: 无标题内容自适应 】
                                            无标题模式退化为单一伪 Section 跑步骤 3
                                                        │
                                                        ▼
                                            【 步骤 5: Top-K 评分与全局去重 】
                                            1. 父块得分为内部包含子块的最高分 (Max Pooling)
                                            2. 按分数降序排序
                                            3. 基于 (resource_id, section_id, start, end) 去重
                                            4. 输出 Top-K 个完整父块
```

### 1.3 核心步骤思路详解

* **步骤 1：小章节整章直出（Section&#x20;**$\le$ **4000 字符）**

  * **触发**：命中子块所属的 Section 总长度 $\le$ 4000 字符。
  * **动作**：直接拉取该 Section 对应的全文作为父块输出。
  * **原理**：基于 $1:5$ 的黄金父子比，对于中小章节，完整结构语义远胜于碎片的局部拼接。
* **步骤 2：高覆盖率整章升级（Section&#x20;**$>$ **4000 字符且覆盖密集）**

  * **触发**：Section 长度在 4000~8000 字符之间，且经过初步扩展后**合并窗口数恰好为 1**，且**该窗口字符长度占整章长度的比例&#x20;**$\ge 80%$ 。
  * **动作**：直接将该视窗向上升级为整章全文。
  * **原理**：避免在章节只剩 10%~20% 边角料未命中的情况下强行切出残缺窗口，直接提供完整章节语义。
* **步骤 3：常规窗口扩展与粘合（Section&#x20;**$>$ **4000 字符且离散分布）**

  * **扩展**：对该 Section 内命中的每个子块物理区间 `[start, end)`，向左向右各外扩 800 字符（遇 Section 首尾物理边界即停）。
  * **粘合**：若两个命中块之间的间隙 $\le$ 2 chnk ，判定为强相关逻辑段落，直接将两个区间融合成一个大区间，并在两端整体外扩 1 chunk。
  * **装箱输出**：直接根据最终合并的物理区间从权威 `raw_content` 切出完整父块文本。
* **步骤 4：无标题平铺内容自适应（Flat Text Fallback）**

  * **机制**：对于纯文本、无 Markdown 标题的文档，系统将其视为单个全局伪 Section，天然无缝复用步骤 3 的扩展与粘合逻辑，通过全局物理坐标 `(start, end)` 消除“父子同体”的边界割裂。
  * **步骤 5：分数传递、去重与 Top-K 输出**
  * **分数传递（Max Pooling）**：一个父块可能包含多个命中子块，父块的分数直接继承其内部子块的最高精排分（ $\max(Score_{\text{child}})$ ）。
  * **坐标去重**：基于 `(resource_id, section_id, start, end)` 去重，完全重合或被真包含的视窗直接合并。
  * **Top-K 截断**：按分数降序排序，取前 Top-K 个候选完整输出。

## 2. 并集池化多路融合算法（Union Pooling Fusion）

### 2.1 算法背景

在真实学术与专业检索中，稠密检索（Dense）与稀疏检索（Sparse / BM25）呈现典型的“30% 语义独有、30% 专有名词独有、40% 重合”的分布。传统 RRF（倒数排名融合）基于共识优先假设，会导致单路高置信度的独有召回被两路都平庸的重合候选挤掉。

### 2.2 算法核心思路

并集池化算法在初检阶段**不做任何启发式打分相加或无界映射**，而是构建无损候选池，由下游 Cross-Encoder Reranker 统一裁决。

```text
[ Dense 检索 ] ──► 取 Top-K (如 30) ──┐
                                     ├──► Set Union (按 chunk_id 去重并集) ──► Cross-Encoder 统一打分 ──► 截取 Top-N
[ Sparse 检索 ] ─► 取 Top-K (如 30) ──┘    (生成 ~40-45 个去重候选池)
```

1. **并行截断**：Dense 路与 Sparse 路各自独立并行执行检索，各自截取 Top- $K_1$ 个候选（如各取 30 条）。
2. **Keyed Set Union 去重**：

* 维护内存字典 `Pool: Dict[chunk_id, Candidate]`。
* 遍历各路候选，以 `chunk_id` 为唯一主键入池。
* **冲突处理**：若某 `chunk_id` 在两路均命中，保留其出现过的最高初检分，并打上多路召回标记（`is_multi_source = True`）。

3. **容量保护**：并集池设定硬上限 $M$ （如 $M = 80$ ），避免极端情况下输入过多候选导致下游 Reranker 计算超时。
4. **全交互注意力精排（Cross-Encoder Scoring）**：

* 将池中去重后的 40~50 个候选文本与原始 Query 组成 `(Query, Chunk_Text)` 对，批量送入 Cross-Encoder。
* 依真实全交互相关度打分并降序截断出最终 Top-$N$（如 8 条），送入动态父块装箱。

## 3. 图谱双轨入库与置信度增量聚合算法（Dual-Track KG Ingestion & Edge Weight Evolution）

### 3.1 算法背景

知识图谱如果全靠 LLM 抽取，存在 Token 开销大、幻觉多、确定性引用容易遗漏的问题；而如果只靠规则，又无法捕获深层语义。因此系统采用“确定性规则 + LLM 语义”双轨入库，并通过饱和增量公式实现实体与关系跨文档的自然演化。

### 3.2 算法核心思路

```text
                               ┌─────────────────────────────────────────────────┐
                               │           输入待入库文档 (Document)             │
                               └────────────────────────┬────────────────────────┘
                                                        │
                         ┌──────────────────────────────┴──────────────────────────────┐
                         ▼                                                             ▼
     【 轨道 A: 确定性抽取 (BibTeX / AST) 】                       【 轨道 B: 语义抽取 (Ontology-Guided) 】
     - 依据 Ontology 规范直接实例化                                 - 将 Ontology 编译为 LLM 结构化约束
     - 关系权重 W_init 强制锁定 1.0                                 - LLM 抽取实体/关系及 exact_quote
     - 证据绑定至 References / AST 物理 Span                        - Python 计算精确 SourceSpan 并生成 Evidence
                         │                                                             │
                         └──────────────────────────────┬──────────────────────────────┘
                                                        │
                                                        ▼
                                     【 图元融合与权重演化 (GraphMerger) 】
                                     1. 实体合并: 同名 node_id 累加 mention_count，并集 aliases
                                     2. 边权重饱和递增: W_new = 1 - (1 - W_old) * (1 - W_item * 0.5)
                                     3. 确定性保护: 若存在确定性证据，W 锁定为 1.0 不可降级
```

### 3.3 增量合并与演化逻辑

1. **实体聚合（Node Evolution）**：

* 提取实体经过 Ontology 的 `slugify` 产生规范化 `node_id`。
* 若图库中已存在该 `node_id`：

  * **频次递增**：`mention_count = mention_count + 1`。
  * **别名合并**：`aliases = aliases ∪ new_aliases`。
  * **描述增强**：保留包含信息量更丰富（长度更长）的定义阐释。

2. **关系权重饱和递增（Edge Weight Saturation）**：

* 关系唯一标识为 `edge_id = SHA256(src_id + "#" + relation_type + "#" + tgt_id)`。
* **初值赋值**：确定性规则产生边的 $W_{\text{init}} = 1.0$ ；LLM 抽取的边依据置信度等级赋予初值（如 explicit=0.8，implicit=0.6）。
* **跨切片多证据融合**：当相同 `edge_id` 再次被抽取出时，权重按饱和衰减曲线演化：

$$
W_{\text{new}} = 1.0 - (1.0 - W_{\text{old}}) \times (1.0 - W_{\text{item}} \times \gamma)

$$

（其中 $\gamma = 0.5$ 为增量衰减因子）。经过多次独立印证的关系其权重自动逼近 $1.0$。

* **确定性不可降级原则**：若该边包含任意一条来自确定性轨道的 `GraphEvidence`，其权重永久锁定为 $1.0$ 。

3. **证据链绑定（Evidence Stitching）**：

* 无论哪条轨道，均生成 `GraphEvidence` 记录其挂载的 `resource_id`、`chunk_id` 及绝对 `source_spans`，保证点边随时可回源高亮。

## 4. 图谱检索中的 PPR 先验扩散算法（Prior-Biased Personalized PageRank）

### 4.1 算法背景

在基于图谱的推理检索中，当从种子节点（Seed Nodes）出发进行 1~2 跳图扩散时，若采用均匀随机游走，会导致搜索迅速扩散到不相关的冷门边缘节点。引入基于节点 `mention_count` 和边 `weight` 的有偏 PPR，能引导扩散路径紧紧围绕“核心领域概念与强拓扑证据”。

### 4.2 算法核心思路

```text
[ Query 向量命中文档/实体 ] ──► 选定 Seed 节点集合 S (如 Top-3 概念)
                                      │
                                      ▼
                       【 初始化个性化重置向量 p_0 】
                       p_0(v) ∝ log(mention_count(v)) (仅针对 v ∈ S)
                                      │
                                      ▼
                       【 幂迭代游走扩散 (Power Iteration) 】
                       - 重置概率 α = 0.15 (保证不脱离 Seed 语义)
                       - 转移概率基于边权重归一化: P(u -> v) ∝ W_(u, v)
                                      │
                                      ▼
                       【 PPR 得分截断与回源装箱 】
                       1. 过滤 PPR 分数 < 阈值的长尾节点
                       2. 沿 Top 节点反查 GraphEvidence 提取 DocChunks
```

### 4.3 详细计算步骤

1. **种子选取与个性化偏置向量初始化（Seed & Prior Vector）**：

* 检索阶段通过 Qdrant Dense 检索或关键词匹配，定位出一组与 Query 高度相关的初始实体节点集合 $S = {s_1, s_2, \dots, s_k}$ 。
* 构造初始概率分布向量 $\mathbf{p}_0$ 。非种子节点的初始分为 0；种子节点的初始概率由其实体频次对数加权归一化：

$$
\mathbf{p}_0(v) =
\begin{cases}
\dfrac{\log(1 + \operatorname{mention\_count}(v))}{\sum_{u \in S} \log(1 + \operatorname{mention\_count}(u))}, & v \in S \\[6pt]
0, & v \notin S
\end{cases}

$$

2. **加权转移概率矩阵构建（Weighted Transition Matrix）**：

* 从节点 $u$ 转移至其邻居节点 $v$ 的转移概率，不采用均匀分布，而是由两点间 `GraphEdge` 的置信度权重 $W_{(u, v)}$ 归一化决定：

$$
T(u \to v) = \frac{W_{(u, v)}}{\sum_{k \in \text{Neighbors}(u)} W_{(u, k)}}

$$

3. **幂迭代求解（Power Iteration）**：

* 设定阻尼系数 / 保持率 $1 - \alpha = 0.85$ （即每次游走有 $15%$ 的概率跳回初始种子集合 $\mathbf{p}_0$ ），执行 $L$ 轮迭代（通常 $L = 3 \sim 5$ 即可收敛）：

$$
\mathbf{p}^{(t+1)} = (1 - \alpha) \cdot \mathbf{T}^{\top} \mathbf{p}^{(t)} + \alpha \cdot \mathbf{p}_0

$$

4. **子图剪枝与回源（Pruning & Grounding）**：

* 迭代结束后，输出各节点的稳态重要度得分 $\mathbf{p}^*$ 。
* 剔除 $\mathbf{p}^*(v) < \epsilon$ 的微弱噪声节点，截取 Top- $M$ 个高分节点及它们相连的高权重边构成**关联子图拓扑**。
* 通过各节点的 `GraphEvidence` 反查对应的 `chunk_id`，将相关文本块一并送入后续动态装箱，为 Agent 提供具备图拓扑支撑的连贯上下文。

## (1) 混合检索

### 一、数据库物理支撑与存储事实

混合检索只依赖 **Qdrant**（向量与过滤索引）与 **MongoDB**（权威原文与切块真值），彻底废除静态父块（`reading_blocks`）与指针映射表。

#### 1. Qdrant：`wisepen_rag_chunk_vectors`

* **定位**：检索加速索引，仅存储向量与用于 Pre-filtering、快速反查的精简标量，不存大段展示文本。
* **Vector 空间**：
* `dense`: 由 `DocChunk.get_embed_content()` 生成。
* `sparse`: BM25 稀疏向量。
* **Payload 存储项**（由基础设施层适配器组装，与领域模型解耦）：

  * **反查主键**：`chunk_id`, `resource_id`, `content_revision`, `chunk_index`, `section_id`
  * **结构面包屑**：`section_path`
  * **物理区间事实**：`source_spans: [{"start_offset": int, "end_offset": int}]`
  * **权限过滤标量（由父 Document.acl 投影）**：`owner_id`, `readable_users`, `excluded_read_users`, `group_ids`
  * **元数据过滤标量（由 DocChunk.metadata 序列化投影）**：动态展开 `metadata.model_dump()` 供向量库做结构化 Pre-filter

#### 2. MongoDB：`wisepen_rag_documents`（权威原文与结构大纲真值）

* **定位**：全系统唯一的全文与结构真值源，负责装箱时的原文切片与 Section 跨度判定。
* **物理存储**：
* `_id`: `"{resource_id}@{doc_version}"`
* `raw_content`: 完整的权威 Markdown 字符串（单文档单条存储，装箱时通过 Python 原生切片 `[start:end]` 极速切出内容）。
* `structure`: 树形大纲，记录每个 `Section` 的 `span`（整章绝对起止）与 `own_span`。
* `metadata`: 挂载 `AnyDocMetadata`。

#### 3. MongoDB：`wisepen_rag_doc_chunks`（物理切块元数据真值）

* **定位**：单次切分的物理切块实体，不存任何 ACL 权限字段。
* **物理存储**：

  * `_id`: `chunk_id`
  * `resource_id`, `content_revision`, `chunk_index`, `section_id`, `section_path`
  * `raw_text`: 权威切片正文
  * `source_spans`: 物理字符区间列表 `[start, end)`
  * `contextual_prefix`, `key_terms`: 检索增强字段
  * `metadata`: 挂载 `AnyChunkMetadata`
* **核心索引**：

  * `{"resource_id": 1, "content_revision": 1, "chunk_index": 1}`（范围区间查询复合索引）。

### 三、核心机制细节与边界保证

1. **元数据驱动的前置剪枝（Metadata Pre-filtering）**：

* 检索层不预设任何死板字段。调用方传入的过滤需求通过领域元数据模型校验后，由适配层编译为向量数据库的原生 Filter 下推；
* 在向量搜索与稀疏遍历的第一阶段直接完成剪枝，杜绝无权或类型不匹配的数据占用精排算力。

2. **并集池化保障特异高分召回（No-RRF）**：

* Dense 与 Sparse 各取 Top-K（K是需要设计的超参数），通过 `chunk_id` 做 Set Union 聚合出候选；
* 初检阶段不做任何有损的分数相加，全部文本原样送入 Cross-Encoder（如 `bge-reranker-large`）进行全交互自注意力精排。

3. **运行时动态装箱与物理坐标对齐**：

* 命中的 Top- $N$ `DocChunk` 聚合后，单次 I/O 批量读取对应父文档的 `Document.structure` 与 `raw_content`；
* 在内存中完成 1 chunk 扩展、 $\le$ 2 chunk 粘合及 $\ge 80\%$ 整章升级计算；
* 从 `raw_content` 切出完整父块并返回精确的 `SourceSpan`，保证输出无指针撕裂、绝对保真。

4. **服务层交付原则**：

* RAG 服务层只负责交付最真实的物理上下文与绝对坐标，不进行任何破坏语义的隐式截断；上下文预算管控由上层调用方依据大模型窗口统一处理。

#### 1. Low-Level 功能：微观局部推理检索

* **核心定位**：解决“具体概念定义、算法细节、直接依赖、公式参数”的细粒度挖掘。
* **功能步骤**：

1. **实体锚定（Entity Grounding）**：

* 将用户 Query 向量化；
* 在 Qdrant `node_vectors` 集合执行 ANN 检索，带入权限 Filter 与 `mention_count >= 2`（降噪）；
* 得到相似度最高的 Top-K 概念顶点作为**种子节点（Seeds）**。

2. **PPR 拓扑子图扩散（Neo4j Cypher 执行）**：

* 以种子节点为先验分布，在 Neo4j 中以 $15%$ 重置概率执行 1~2 跳 PPR 扩散游走；
* 过滤权重低于阈值（如 `weight < 0.5`）的边；
* 输出局部关系最密集的实体子图（包含节点和连接它们的边）。

3. **微观证据装配**：

* 提取该子图的所有 `node_id` 与 `edge_id`，去 MongoDB `graph_evidences` 表批量取出对应的 `chunk_id` 和精确 `SourceSpan`；
* 触发 5 步动态装箱，产出连续正文。

---

#### 2. High-Level 功能：宏观全局洞察检索（LightRAG 核心）

* **核心定位**：解决“技术路线演化、大类方法对比、全局架构优化趋势”等宽泛或无明确单一实体的查询（如“*大模型在降低显存开销方面有哪些主要手段？*”）。
* **功能步骤**：

1. **关系主题关键词召回（Keywords-Driven Retrieval）**：

* 在 Qdrant `edge_vectors` 集合上，对 Query 与边的 `keywords` 进行 **Dense + BM25 混合检索**；
* 命中一组打上了相关主题标签的高置信度边（如命中多条带有 `keywords: ["KV Cache", "显存带宽"]` 的边）。

2. **拓扑闭包与演化聚合（Neo4j Cypher 执行）**：

* 提取这批边的 `source_node_id` 和 `target_node_id`；
* 在 Neo4j 中执行 1 跳端点聚合，串联起宏观演化边（`EVOLVED_FROM`）、对比边（`COMPARED_WITH`）以及论文引用边（`CITES`）；
* 自动提炼命中的核心 `keywords` 频次，作为全局大纲主题。

3. **宏观证据装配**：

* 收集上述关键边的 `edge_id`，查 MongoDB 提取相关证据切片装箱。

---

#### 3. Hybrid 功能：宏微混合检索（默认生产通道）

* **核心定位**：同时需要宏观演化脉络与微观公式/代码支撑的综合分析场景。
* **功能步骤**：

1. **并行并发**：同时触发 Low-Level 实体锚定 与 High-Level 关系关键词召回；
2. **图论无损合并（Graph Union）**：

* 顶点集做并集：`Nodes = Nodes_low ∪ Nodes_high`（重合顶点保留更高相关度）；
* 边集做并集：`Edges = Edges_low ∪ Edges_high`；

3. **证据反查与动态装箱**：

* 汇总全部命中的实体与边，一次性单次 I/O 批量拉取 MongoDB `graph_evidences`；
* 按 `chunk_id` 聚合并运行 5 步动态自适应装箱算法；
* 输出结果：**既包含结构化的拓扑子图（点、边、主题词），又包含对应的高亮 Markdown 权威上下文**。

## (3) 领域标题拓展服务

领域标题树拓展服务是系统为 Agent 提供的“文档空间拓扑地图与导航罗盘”。

它的核心职责是解决长文档（数十页论文、百页技术手册、教材）中“全局大纲 Dump 撑爆 Token”与“切块平铺丢失空间上下文”的矛盾，提供宏观全局大纲、局部十字邻域对焦、以及检索命中投影森林（Hit Projection Forest）三大能力，建立“**看得见的节点零跳直读，折叠的暗区以父节点为锚点一跳下钻**”的确定性交互闭环。

```json
      "level": 3,

      "parent_id": "sec_1_2",
      "child_ids": ["sec_1_2_2_1", "sec_1_2_2_2", "sec_1_2_2_3"],
      "title_path": ["1. 架构总览", "1.2 注意力机制", "1.2.2 GQA 详解与实现"],
      "span": {"start": 24000, "end": 38000},
      "direct_spans": [{"start": 24000, "end": 26500}]
    }
  ]
}
```

* **物理存储特征**：
* **单文档原子化**：整棵大纲树作为 `structure` 字段与 `raw_content` 存储在同一 Document 记录中，单次 I/O 即可加载完毕，内存寻址耗时 $<0.1\text{ms}$。
* **双重物理区间（**`span`**&#x20;vs&#x20;**`direct_spans`**）**：
* `span`：记录该章节及其所有子章节的**完整子树字符区间** `[24000, 38000)`。
* `direct_spans`：严格记录该章节自身、**剔除了所有子章节**的正文段落（如导语、概述）区间 `[24000, 26500)`。
* **线性索引保序（**`order_index`**）**：全局递增整数序号，天然支持 $O(1)$ 数组偏移寻址，消除链表指针。

### 二、三大核心导航功能流与算法机制

```text
                             ┌──────────────────────────────────────────────┐
                             │       输入: resource_id + 操作模式            │
                             └──────────────────────┬───────────────────────┘
                                                    │
         ┌──────────────────────────────────────────┼──────────────────────────────────────────┐
         ▼                                          ▼                                          ▼
【 模式 A: 检索命中投影森林 】               【 模式 B: 局部十字邻域对焦 】               【 模式 C: 全局受限大纲 】
  (hit_projection)                          (neighborhood_focus)                      (global_outline)
  输入: 命中 chunk 的 section_ids           输入: target_section_id                   输入: max_level (如 2)
         │                                          │                                          │
         ▼                                          ▼                                          ▼
┌──────────────────────────────────┐       ┌──────────────────────────────────┐       ┌──────────────────────────────────┐
│ 1. 深度跨度与 LCA 判定           │       │ 1. 祖先链上溯 (ancestor_path)     │       │ 1. 内存过滤 level <= max_level   │
│ 2. 直筒单链路径折叠 (Radix Fold) │       │ 2. 兄弟扫视 (sibling_sections)   │       │ 2. 挂载子树规模估算 (char_count) │
│ 3. 祖先未命中兄弟 100% 剪除      │       │ 3. 直属子树下钻 (child_sections) │       │ 3. 产出全书顶层 TOC 骨架         │
│ 4. 命中同级半径 r=1 兄弟桩暴露   │                                              │
│ 5. 大跨度间隔折叠 (Gap Collapse) │       └──────────────────────────────────┘       └──────────────────────────────────┘
└──────────────────────────────────┘
```

#### 1. 模式 A：检索命中投影森林（`hit_projection` 剪枝算法协议）

当混合检索命中了多个切块时，系统自动触发 5 重剪枝与折叠规则，将命中的散点投影为一棵或多棵极简的**最小活性投影树（Hit Forest）**：

* **规则 1：森林分裂（Forest Partitioning）**：
* 若命中的切块跨越不同大章，其最近公共祖先（LCA）退化为全书 Root 且深度跨度 $\Delta \text{Level} \ge 3$ ，算法**拒绝强行拼接包含全书空洞目录的伪树**，直接切分为多棵独立的局部子树（`hit_forest`）。
* **规则 2：直筒单链路径折叠（Radix Path Fold）**：
* 对于中间无任何分叉命中的深层管道祖先（如 `1. -> 1.1 -> 1.1.1`），折叠为字符串前缀 `context_path: "1. 架构 > 1.1 注意力 > 1.1.1 基础"`，直接将视窗锚定在直接父节点，消除 4~5 层无意义的 JSON 嵌套缩进。
* **规则 3：祖先层未命中兄弟 100% 物理剪除（Zero Ancestor Siblings）**：
* 祖父辈、曾祖父辈等高层节点，**除命中骨架链条外，其余未命中的平级大章绝对不展开**，杜绝大目录泄露。
* **规则 4：命中层兄弟半径视窗（Radius-1 Sibling Window）**：
* 在命中节点所在的直接父分支下，不展开全部兄弟，**仅展示最左命中的前一个（-1）与最右命中的后一个（+1）作为未命中路标桩（**`is_stub: true, hit_count: 0`**）**。
* **规则 5：大跨度间隔折叠（Gap Collapse）**：
* 同级节点中若命中项之间间隔 $>2$ 个小节（如命中了第 1 节和第 6 节），中间未命中的小节折叠为 `{"is_omitted_gap": true, "omitted_count": 2}`。
* **规则 6：路标桩不展开下级（Depth = 0 on Stubs）**：
* 所有露出的兄弟桩（Stub）必须是纯叶子节点，严禁递归展开其子孙。

#### 2. 模式 B：局部十字邻域对焦（`neighborhood_focus`）

当 Agent 锁定了某个特定的 `target_section_id` 时，系统在内存中以其为坐标原点，生成包含 4 个维度的“十字拓扑罗盘”：

* **纵向上溯（**`ancestor_path`**）**：通过 `parent_id` 逐级回溯至根节点，提供完整的宏观背景面包屑。
* **纵向下钻（**`child_sections`**）**：读取 `child_ids`，**仅展开第一层直属子章节**（附带 `char_count` 与标题），提供下潜探测入口。
* **横向对比（**`sibling_sections`**）**：查找共享相同 `parent_id` 的平级(通过参数+- step控制)兄弟节点列表，方便同类方案对比（如在 `3.2 GQA` 处看到平级的 `3.1 MHA` 与 `3.3 MQA`）。

---

#### 3. 模式 C：全局受限大纲（`global_outline`）

* 用于冷启动全书概览，仅在内存中筛选 `level <= max_level`（默认 2）的节点；
* 每个节点计算并挂载 `char_count`（基于 `span.end - span.start`），为 Agent 评估阅读成本与规划长文本切分提供量化输入。

## (4) 原文确定性阅读服务（Deterministic Reading Service）

原文确定性阅读服务是系统**抵御大模型幻觉、保障 100% 事实保真与可解释性**的底座。

它完全绕过模糊向量检索与 ANN 排序，基于**逻辑边界（Section）**、**物理区间（SourceSpan）或图元多态外键（Graph Target ID）**，在内存中直接对权威全文执行物理切片，提供一字不差的原文。

### 一、数据库物理存储与索引支撑

确定性阅读依赖 MongoDB 中的权威全文表与图文证据表，全链路无任何中间静态父块缓存：

#### 1. MongoDB：`wisepen_rag_documents`（权威全文与结构映射）

* **定位**：全系统唯一的全文物理真值源。
* **字段结构**：
* `_id`: `"{resource_id}@{doc_version}"`
* `raw_content`: 完整的权威 Markdown 字符串（数十万字符单字段存储）。
* `structure.sections`: 提供逻辑 `section_id` 到物理 `[start, end)` 的映射表。
* **索引**：`{"resource_id": 1, "revision.doc_version": -1}`。

#### 2. MongoDB：`wisepen_rag_graph_evidences`（图文物理桥梁）

* **定位**：图谱事实与正文绝对区间的绑定表。
* **字段结构**：
* `_id`: `evidence_id`
* `target_type`: `"node" | "edge"`（多态外键判别器）
* `target_id`: `str`（`node_id` 如 `"concept:gqa"`，或 `edge_id` 如 `"hash_abc123"`）
* `resource_id`: `str`
* `content_revision`: `str`
* `section_id`: `str`
* `chunk_id`: `str`
* `source_spans`: `[{"start": int, "end": int}]`（在 `raw_content` 中的绝对字符区间）
* `quote_text`: `str`（原文章节精准摘录字串）
* **复合核心索引**：
* `{"target_id": 1, "target_type": 1}`（主查索引：支持图元点击 1ms 内反查证据）
* `{"resource_id": 1, "content_revision": 1}`（生命周期同步与版本失效管理）

### 二、确定性阅读三大执行通道

```text
                               ┌──────────────────────────────────────────────┐
                               │           Deterministic Reading 请求          │
                               └──────────────────────┬───────────────────────┘
                                                      │
         ┌────────────────────────────────────────────┼────────────────────────────────────────────┐
         ▼                                            ▼                                            ▼
【 通道 1: 逻辑章节直读 】                     【 通道 2: 图文证据穿透溯源 】                 【 通道 3: 绝对坐标/区间直读 】
  输入: resource_id + section_id               输入: resource_id + target_graph_id           输入: resource_id + source_spans
         │                                            │                                            │
         ▼                                            ▼                                            ▼
 查 documents.structure 获取:                  查 graph_evidences 表:                        直接读取传入的绝对字符区间:
 - direct 模式 ──► direct_spans               根据 (target_id, target_type)                 `spans = [(start, end), ...]`
 - subtree 模式 ──► span                      拉取关联的 `source_spans`                                     │
         │                                            │                                            │
         └────────────────────────────────────────────┼────────────────────────────────────────────┘
                                                      │
                                                      ▼
                       ┌────────────────────────────────────────────────────────┐
                       │ 统一底层执行: MongoDB 单次 I/O 投影加载 raw_content     │
                       │ - 内存字符串切片: `raw_content[start:end]`              │
                       │ - 证据溯源模式自动向外扩展 ±200 字符语境视窗            │
                       └──────────────────────┬─────────────────────────────────┘
                                              │
                                              ▼
                               [ 输出精确正文 + 高亮区间 + 面包屑 ]
```

---

#### 1. 通道 1：逻辑章节确定性直读（Section Reading）

* **场景**：Agent 依据大纲或投影树锁定了 `section_id`，发起正文精读。
* **模式隔离机制**：
* `read_mode="direct"`**（仅读本节概述）**：
* 提取 `section.direct_spans`；
* 切出当前章节自身开头的导论与段落，**物理剔除所有子小节的正文**；
* 彻底解决传统 RAG 中“读父章节必须连带把几万字子章节全部吞入”导致的 Context 膨胀。
* `read_mode="subtree"`**（整章递归深读）**：
* 提取 `section.span`；
* 连续切出包含当前章节及其全部子孙分支的完整长文本。

#### 2. 通道 2：图谱证据穿透溯源（Graph-to-Text Grounding）

* **场景**：用户在前端点击图谱中的实体圆圈（Node）或关系连线（Edge），或 Agent 在逻辑推理中需要验证图谱三元组的真实出处。
* **执行机制**：

1. 系统以传入的 `target_graph_id` 为入参，通过复合索引 `{"target_id": 1, "target_type": 1}` 单次 I/O 查询 `graph_evidences`；
2. 提取其绑定的 `source_spans`；
3. 读取 `documents.raw_content` 截取原始语句，并默认向前后自适应扩展 200 字符形成阅读段落；
4. 返回正文段落及段落内部的高亮相对偏移量，供前端渲染黄色高亮标黄（Highlight）或供 Agent 核实。

#### 3. 通道 3：绝对物理坐标切片（SourceSpan Slicing）

* **场景**：Agent 在多轮推理中针对前序工具调用返回的精确字符区间做复核，或基于分页页码（Page Number）换算后的起止字符进行读取。
* **执行机制**：
* 完全不解析 AST、不遍历结构树，直接在内存中执行 Python 字符串切片 `raw_content[span.start:span.end]`。

```python
class NavigateSectionTreeInput(BaseModel):

    )
```

### 工具 4：`tool_read_direct`（权威原文确定性精读）

* **认知定位**：当 Agent 明确获得了 `section_id`（来自大纲/投影树）或物理 `page_number`（来自文献引用/页码翻阅）时，**完全绕过向量检索与 ANN 排序，基于内存绝对切片 100% 确定性、一字不差地阅读原文**。
* **交付模式**：
* **逻辑篇章直读**：支持仅读当前节导言（`direct`，物理剔除子节，省 Token）或整章递归深读（`subtree`）；
* **物理页码直读**：按真实页码或跨页区间（`page_number` ~ `page_end`）极速切片。

#### 输入契约（Pydantic Schema）

```python
class ReadDirectInput(BaseModel):
    """权威原文确定性精读输入契约（支持章节与物理页码双通道）"""
    model_config = ConfigDict(extra="forbid")

    resource_id: str = Field(..., description="目标文档资源的唯一标识 ID。")

    # 通道 1: 逻辑章节阅读（二选一）
    section_id: str | None = Field(
        default=None,
        description="要精读的目标章节 ID（如 'sec_1_2_2'，来自检索 hit_forest 或大纲导航）。"
    )
    read_mode: Literal["direct", "subtree"] = Field(
        default="direct",
        description=(
            "章节阅读模式（仅在指定 section_id 时生效）：\n"
            "- 'direct': 仅读取当前章节自身的正文段落（物理剔除所有子小节），节省 Token；\n"
            "- 'subtree': 连续读取当前章节及其全部子孙分支的完整长文本。"
        )
    )

    # 通道 2: 物理页码阅读（二选一）
    page_number: int | None = Field(
        default=None,
        ge=1,
        description="要精读的物理页码编号（从 1 开始，如论文/书籍中的第 5 页）。"
    )
    page_end: int | None = Field(
        default=None,
        ge=1,
        description="可选的结束页码（用于连读跨页区间，如 page_number=3, page_end=5 读取 3~5 页）。若不填则仅读单页。"
    )
```

#### 输出载荷示例（Output JSON Payload）

```json
{
  "resource_id": "doc_llama3_spec",
  "query_channel": "section",
  "section_id": "sec_1_2_2",
  "read_mode": "direct",

  "content": "### 1.2.2 GQA 详解与实现\n为了在保持 MHA 表达能力的同时获得接近 MQA 的推理速度，GQA 将 Q 头均分为 8 个分组...",
```

## 3. 典型 Agent 推理与协同闭环工作流

这 4 个 MCP 工具在 Agent 端能够自然组合成人类专家的全流程研读路径：

```text
                    ┌────────────────────────────────────────────────────────┐
                    │                      User Prompt                       │
                    └───────────────────────────┬────────────────────────────┘
                                                │
         ┌──────────────────────────────────────┼──────────────────────────────────────┐
         ▼                                      ▼                                      ▼
【 链路 1: 细节查证与问答 】            【 链路 2: 架构对比与暗区深潜 】        【 链路 3: 长文档翻书式精读 】
`tool_search_hybrid`                  `tool_search_hybrid`                  `tool_navigate_section_tree`
         │                                      │                             (nav_mode="global_outline")
         ▼ (单步命中)                            ▼ (发现结构暗区/兄弟桩)                  │
拿到 `packed_blocks` 直接回答          1. 兄弟桩已暴露:                        ▼ (规划学习路径)
                                         直接调 `tool_read_direct`            循环调用 `tool_read_direct`
                                       2. 存在折叠暗区:                         (按章节或按页码连续精读)
                                         先调 `tool_navigate_section_tree`
                                         再调 `tool_read_direct`
```

### 场景 A：精准细节与公式查证（1-RTT 单步直达）

1. Agent 发起 `tool_search_hybrid(query="SwiGLU 门控公式推导")`；
2. 系统在底层完成混合初检、Cross-Encoder 精排与 5 步动态装箱，直接将前后粘合好的完整公式段落放在 `packed_blocks` 中交付；
3. Agent 单轮获得全部事实证据，立即合成回答，**零二次交互开销**。

### 场景 B：横向对比与结构缺口补齐（$O(1)$ 零跳直读）

1. 用户询问“*GQA 相比标准 MHA 节约了多少显存？*”；
2. Agent 调用 `tool_search_hybrid`，正文命中了 `1.2.2 GQA`，同时返回的 `hit_forest` 中清晰暴露了兄弟桩节点 `sec_1_2_1 (1.2.1 标准 MHA 基础, is_stub: true)`；
3. Agent 敏锐捕捉到对比基线，**手中已直接持有真实 `section_id: "sec_1_2_1"**`；
4. Agent 直接发起 `tool_read_direct(section_id="sec_1_2_1", read_mode="direct")`，秒级拉取基线原文，完成严密对比。

### 场景 C：深层暗区一跳下钻（1-Hop Anchor Drill-Down）

1. 面对 100 页的长文档，检索返回的 `hit_forest` 显示在 `sec_1_2` 节点下存在 `{"is_omitted_gap": true, "omitted_count": 3}`；
2. Agent 握着父节点 `sec_1_2` 的真实 ID，发起锚点下钻：

```python
tool_navigate_section_tree(nav_mode="neighborhood_focus", target_section_id="sec_1_2")
```

3. 后端瞬时仅展开该父节点下的直接子章节，Agent 获得被折叠小节的真实 ID（如 `sec_1_2_4`）；
4. Agent 顺藤摸瓜调用 `tool_read_direct(section_id="sec_1_2_4")` 完成深潜精读。

### 场景 D：宏观技术路线与演化综述

1. 用户询问“*大模型显存优化的演进脉络与关键里程碑*”；
2. Agent 调用 `tool_search_graph(mode="high", query="显存优化演进路线")`；
3. 系统返回宏观核心关键词、演化拓扑图（`MHA -> MQA -> GQA -> MLA`）以及各里程碑的代表性论文切片；
4. Agent 结合结构图与正文，结构化输出包含演化时间线与技术原理的深度综述。

## 4. 工具契约防御性设计与边界保障


| 维度                  | 防御机制                                                                                                                                                                                         | 收益                                                       |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **Pydantic 严格校验** | 所有 Input Model 开启`extra="forbid"`，禁止大模型随意捏造参数。                                                                                                                                  | 拦截 100% 由于 Prompt 污染或 LLM 幻觉引起的非法入参请求。  |
| **通道互斥校验**      | `tool_read_direct` 在校验器（Validator）中强制要求 `section_id` 与 `page_number` 至少存在其一且不同时传入。                                                                                      | 彻底规避逻辑维度与物理维度的语义歧义。                     |
| **Token 预算硬封顶**  | 检索的`hit_forest` 严格限制节点数 $\le 12$；大纲导航 `global_outline` 强制默认 `max_level=2`。             | 结构地图 Token 消耗始终稳定在 **$60 \sim 120\text{ Tokens}$**，绝不挤占正文上下文。 |                                                            |
| **物理真值单真值源**  | `tool_read_direct` 直接读取 MongoDB `raw_content` 执行切片，不依赖任何静态切块表与向量近似。                                                                                                     | 切片耗时$<0.05\text{ms}$，彻底杜绝数据版本滞后与高亮错位。 |
