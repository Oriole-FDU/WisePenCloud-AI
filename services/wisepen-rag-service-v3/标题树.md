# 标题树能力

标题树能力只读取当前 `Document.structure`，不访问 Qdrant、Neo4j，也不调用 LLM。它提供三种独立操作：检索命中投影森林、局部邻域、全局受限大纲。

这三种操作共享同一份 Common `Section` 事实。真实字段为：

- `parent_section_id`：直属父节点；
- `ordinal`：文档中的稳定顺序；
- `section_path`：从根到当前标题的路径；
- `content_spans`：本节直属正文，不包含子节；
- `subtree_span`：本节及全部子节的连续范围。

标题树不建立独立 Mongo collection，也不复制一套 `child_ids` 或 `order_index`。子节点和兄弟节点都从当前 Document 的 `sections` 在请求内计算。

## 1. Common `Section` 与接口模型的边界

Common `Section` 能完整满足标题树的内部计算，不需要 RAG 再定义一套 Section 领域模型。它也没有明显冗余：坐标、顺序、预览和父子关系都是结构解析、分块或阅读会使用的事实。

但 `Section` 不适合原样作为接口结果。它包含 `own_span`、`subtree_span`、`content_spans`、`ordinal` 和 `preview` 等内部字段；标题树调用方通常只需要标题和可导航的 `section_id`。直接返回 `Section` 会把实现细节暴露成 RAG 对外契约，也会让每个节点变得很重。

因此这里不再定义一个到处复用的“大而全” `SectionView`，也不为是否多一个 `char_count` 拆成两个模型。局部邻域统一使用一个轻量节点：

```python
class SectionItem(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    section_id: str
    title: str
    char_count: int = Field(ge=0)
    page_range: str | None = None
    anchor_labels: tuple[str, ...] = ()
```

字段含义：

- `char_count` 表示本 Section 的直属正文长度，由 `content_spans` 计算，不包含子节正文；
- `page_range` 由 Section 与 Common `Page.source_span` 的重叠关系计算，例如 `"3"` 或 `"3 - 5"`；
- `anchor_labels` 由 Section 与 Common `Anchor.source_span` 的重叠关系计算，只列出本节直属正文中的 Figure、Table、Formula 等 Anchor。

页码可以帮助调用方判断阅读位置和跨度，Anchor 可以提示本节是否含有值得直接读取的图、表或公式，因此二者有实际导航价值。它们不需要新增持久化字段；没有页码或 Anchor 时，接口序列化分别省略 `None` 和空数组。

原稿中的 `SectionIndex` 没有带来新的业务能力，它只是避免反复扫描 `sections` 的请求内优化。实现时用两个局部字典即可：`sections_by_id` 负责按 ID 查找，`children_by_parent` 负责找孩子和兄弟。构建一次是 O(n)，之后单点查找是 O(1)。它不持久化，也不作为领域模型或接口契约出现。

## 2. 模式一：命中投影森林 `hit_projection`

命中投影森林接收混合检索最终通过 ACL、当前版本回查和相关性门控的 Chunk 命中。它回答的是：“这些命中分别位于文档的什么位置，周围还有哪些可继续探索的标题？”

### 2.1 输入和输出

```python
class HitProjectionRequest(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    resource_id: str
    section_ids: tuple[str, ...] = Field(min_length=1)
    sibling_steps: int = Field(default=1, ge=0, le=2)


class HitTreeNode(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    section_id: str
    title: str
    matched: bool = False
    expandable: bool = False
    children: tuple["HitTreeNode", ...] = ()


class HitProjectionResult(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    resource_id: str
    roots: tuple[HitTreeNode, ...]
```

字段只表达调用方真正需要知道的事情：

- `matched=True`：这个 Section 确实有 Chunk 命中；为连接路径而补出的祖先和兄弟为 `False`；
- `expandable=True`：这个 Section 还有未展示的直接子节点，可以拿它的 `section_id` 调用 `neighborhood_focus`；
- `children`：当前投影中实际展示的子节点。

命中次数、Chunk 分数和具体命中内容已经由混合检索的 `hits` 返回，不在标题树里重复。`section_id=None` 的 flat-text Chunk 没有标题坐标，不进入投影森林，但不影响混合检索正文结果。

### 2.2 命中森林算法

算法分四步执行。

#### 第一步：校验命中

对 `section_ids` 去重。不存在于当前 `Document.structure` 的 Section 直接视为版本不一致错误，不能静默忽略。

#### 第二步：构造最小活性闭包

对每个命中 Section 沿 `parent_section_id` 回溯到顶层 Section，把路径上的所有祖先加入 `active_ids`。只加入连接命中所必需的祖先，不加入祖先的其他兄弟。

```python
active_ids = set(hit_ids)
for hit_id in hit_ids:
    current = sections_by_id[hit_id]
    while current.parent_section_id is not None:
        current = sections_by_id[current.parent_section_id]
        active_ids.add(current.section_id)
```

#### 第三步：按顶层活跃分支分森林

找到每条命中路径上的顶层 Section。不同顶层 Section 分别成为一棵投影树，不创建虚假的“文档根”把整份目录串起来。

这个规则替代旧方案中“LCA 退化为 Root 且层级跨度达到阈值才分树”的条件：是否分树只由真实顶层分支决定，不受标题层级深浅偶然影响。

#### 第四步：补少量兄弟并标记可展开节点

对每个直接命中 Section，在相同 `parent_section_id` 的兄弟列表中，向前后各补充最多 `sibling_steps` 个节点，帮助调用方理解命中位于同级目录的什么位置。这些兄弟节点只展示自身，不展开孩子。

- 真实命中节点设置 `matched=True`；
- 路径祖先和补充的兄弟设置 `matched=False`；
- 只要真实孩子没有全部出现在投影中，就设置 `expandable=True`；
- 所有节点和森林根都按 Common `Section.ordinal` 保持原文顺序。

不再返回 `Stub`、`Gap` 或被折叠的 `context_path`。这些字段描述的是算法如何省略节点，不是调用方的导航目标。调用方只需要根据 `expandable` 判断是否继续获取邻域。

### 2.3 小型示例

假设混合检索命中了同一文档中的四个 Chunk：

```text
chunk_a -> sec_1_2_2（1.2.2 GQA）
chunk_b -> sec_1_2_2（1.2.2 GQA）
chunk_c -> sec_1_3（1.3 FFN）
chunk_d -> sec_2_2（2.2 优化器）
```

`chunk_a` 和 `chunk_b` 位于同一个 Section。混合检索结果仍然保留四个真实 Chunk hit；调用标题树前只把它们的 `section_id` 去重为 `sec_1_2_2`、`sec_1_3`、`sec_2_2`。

文档目录是：

```text
1. 架构
  1.1 背景
  1.2 注意力机制
    1.2.1 MHA
    1.2.2 GQA       <- chunk_a、chunk_b 命中
    1.2.3 MQA
  1.3 FFN           <- chunk_c 命中
2. 训练
  2.1 数据
  2.2 优化器         <- chunk_d 命中
  2.3 训练稳定性
```

请求：

```json
{
  "resource_id": "doc_llama3_spec",
  "section_ids": ["sec_1_2_2", "sec_1_3", "sec_2_2"],
  "sibling_steps": 1
}
```

结果：

```json
{
  "resource_id": "doc_llama3_spec",
  "roots": [
    {
      "section_id": "sec_1",
      "title": "1. 架构",
      "expandable": true,
      "children": [
        {
          "section_id": "sec_1_2",
          "title": "1.2 注意力机制",
          "children": [
            {
              "section_id": "sec_1_2_1",
              "title": "1.2.1 MHA"
            },
            {
              "section_id": "sec_1_2_2",
              "title": "1.2.2 GQA",
              "matched": true
            },
            {
              "section_id": "sec_1_2_3",
              "title": "1.2.3 MQA"
            }
          ]
        },
        {
          "section_id": "sec_1_3",
          "title": "1.3 FFN",
          "matched": true
        }
      ]
    },
    {
      "section_id": "sec_2",
      "title": "2. 训练",
      "children": [
        {
          "section_id": "sec_2_1",
          "title": "2.1 数据"
        },
        {
          "section_id": "sec_2_2",
          "title": "2.2 优化器",
          "matched": true
        },
        {
          "section_id": "sec_2_3",
          "title": "2.3 训练稳定性"
        }
      ]
    }
  ]
}
```

这个结果体现了三件事：

- 同一 Section 命中两个 Chunk，只产生一个 `matched` 标题节点，Chunk 级审计仍留在混合检索 `hits` 中；
- `sec_1_2_2` 和 `sec_1_3` 共享顶层祖先，因此合并在“1. 架构”这棵树里；
- `sec_2_2` 位于另一个顶层分支，因此形成“2. 训练”这棵树。

`1.2.1`、`1.2.3`、`2.1` 和 `2.3` 是 `sibling_steps=1` 补出的同级导航节点。“1. 架构”的 `expandable=True` 表示还有未展示的直接孩子 `1.1 背景`。接口序列化时省略值为 `False` 的布尔字段和空 `children`，所以实际结果不会堆满默认值。

## 3. 模式二：局部邻域 `neighborhood_focus`

局部邻域以一个真实 `section_id` 为中心，提供向上、向下和横向的导航坐标。

```python
class NeighborhoodRequest(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    resource_id: str
    section_id: str
    sibling_steps: int = Field(default=1, ge=0, le=5)


class SectionNeighborhood(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    resource_id: str
    section_path: str
    parent: SectionItem | None
    current: SectionItem
    siblings: tuple[SectionItem, ...]
    children: tuple[SectionItem, ...]
```

返回规则：

- `section_path` 把 Common `Section.section_path` 格式化为 `" > ".join(section.section_path)`，例如 `"文档标题 > 第一章 > 1.2 方法"`；它只用于模型阅读和界面展示，不允许下游拆分字符串来恢复 Section 层级；
- `parent` 只返回直属父节点，用于立即向上导航，不重复返回全部祖先对象；
- `siblings` 返回 current 之前最多 `sibling_steps` 个、之后最多 `sibling_steps` 个同级节点，并保持原文顺序；
- `children` 只返回第一层直属子节点，不递归展开；
- current 不重复出现在 sibling 列表中。

这比返回完整祖先数组更省，同时没有损失宏观位置：面包屑负责“我在哪条路径上”，`parent` 负责“我如何向上走”。线性前后节点与标题层级导航关系很弱，也可以用兄弟窗口和阅读接口替代，因此不纳入契约。

旧代码 demo 的 `getSurroundingOutline(window_size=2)` 可以直接参考其父子读取、兄弟窗口、ACL 和 `exclude_none` 输出方式。V3 的主要变化只是把每个节点进一步缩减成上面的专用模型。

例如 `sibling_steps=1` 时：

## 4. 模式三：全局受限大纲 `global_outline`

全局大纲用于首次浏览整份文档，只返回指定层级以内的真实树骨架。这里直接复用 Common 已有的 `OutlineNode`，不再定义 `OutlineSection` 或另一套节点模型。

```python
class GlobalOutlineRequest(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    resource_id: str
    max_level: int = Field(default=2, ge=1, le=6)


class GlobalOutlineResult(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    resource_id: str
    roots: tuple[OutlineNode, ...]
```

`OutlineNode` 已经提供 `section_id`、`title`、`length`、`page_range`、`anchor_labels` 和嵌套 `children`，正是 `services/wisepen-rag-service/demo/test1_outline.txt` 中清晰且有效的表达。`length` 表示该标题子树的正文规模；页范围和 Figure、Table 等 Anchor 能帮助调用方快速判断内容位置和类型。

只输出 `section.level <= max_level` 的节点，达到 `max_level` 后不继续展开。接口序列化时省略 `None` 和默认空字段，避免每个节点都展示没有信息量的 `page_range: null`、`anchor_labels: []`。

`max_level` 使用 Common 解析出的真实标题 level，不把当前节点重新编号为相对层级。

## 5. 无标题文档和 ACL

标题树能力直接检查 `Document.structure.sections`：有 Section 时正常执行三个操作；没有 Section 时返回空森林或空大纲，邻域请求返回“Section 不存在”。无论正文是否为空，都不能制造“正文 1”“正文 2”之类伪标题。

每个操作都先按当前 `ResourceAcl` 校验资源可读性，再读取当前发布的 `Document.structure`。返回前再次确认 ACL 没有被撤销。标题树结果不得包含不可读资源的标题、Section ID、页标签或 Anchor 标签。

## 6. 与检索和阅读的关系

```text
混合检索 ChunkHit
  -> 对 section_id 去重
  -> hit_projection
  -> matched Section 可直接按 section_id 阅读
  -> expandable Section 可调用 neighborhood_focus
  -> 获得更细的真实 section_id 后继续阅读
```

混合检索可以在同一应用服务内部调用 `hit_projection` 并把结果随检索结果返回，但命中森林算法仍属于标题树能力。MCP 是否把三个操作包装成一个工具，不改变 RAG 内部的三个明确方法。

## 7. 验收标准

- 标题树只读当前 `Document.structure`，不访问向量库、图数据库或 LLM。
- 不建立冗余标题节点表，字段使用 Common 真实的 `parent_section_id`、`ordinal`、`content_spans`、`subtree_span`。
- 跨顶层分支的命中稳定拆成多棵树，不创建包含大量空洞的文档根。
- 最小活性闭包只包含命中路径；祖先未命中兄弟不会泄露进结果。
- 命中层只补充 `sibling_steps` 范围内的兄弟，并且不展开这些兄弟的孩子。
- `matched` 只标记真实命中，`expandable` 只表示仍有未展示的直接子节点。
- 投影结果不暴露 Stub、Gap、命中次数或路径折叠等算法内部状态。
- 森林和大纲始终按原文 `ordinal` 排序，不按检索分数重排。
- 邻域只返回面包屑、直属父节点、受 `sibling_steps` 控制的前后兄弟和直属孩子，不返回完整祖先对象或线性前后节点。
- 全局大纲复用 Common `OutlineNode`，严格执行 `max_level`，并保留子树长度、页范围和 Anchor 摘要。
- `Document.structure.sections` 为空时不生成伪标题树。
- ACL 撤销后不返回任何标题结构信息。
