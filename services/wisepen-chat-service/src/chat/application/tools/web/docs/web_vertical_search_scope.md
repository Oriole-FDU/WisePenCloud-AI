# Web 垂直搜索 API 范围说明

本文档说明本轮 `web` 工具体系不新增论文搜索、GitHub 搜索等垂直搜索 API 的原因，以及需要获取垂直站点内容时的推荐路径。

## 当前决策

本轮不新增以下类型的专用 API：

1. 论文搜索 API，例如 Semantic Scholar、Crossref、arXiv 聚合搜索等。
2. GitHub 搜索 API，例如 repository、issue、code search。
3. 其他垂直内容 API，例如 npm、PyPI、Reddit、Stack Overflow、专利库等。

当前继续保留通用能力：

1. `web_search`：负责通用搜索、查询规划、结果归并和排序。
2. `web_fetch`：负责强反爬页面抓取、正文抽取、文件识别和内容交付。
3. `web_crawl`：负责从种子页面出发进行受控链接发现和多页抓取。

## 暂不新增的原因

### API 限流严重

垂直 API 通常有较低的匿名额度或严格的 key 限制。接入后容易出现：

1. 免费额度很快耗尽。
2. 多用户并发下请求被 429 限流。
3. 不同 key 权限差异导致线上结果不稳定。
4. 失败重试会进一步放大限流压力。

如果没有稳定额度和明确 SLA，工具层接入这类 API 会把不确定性暴露给上层 Agent。

### 搜索质量不稳定

垂直 API 的排序和召回并不总是优于通用搜索：

1. 论文 API 对新论文、预印本、会议页、作者主页覆盖不一致。
2. GitHub API 搜索结果受 star、更新时间、索引延迟、语法限制影响明显。
3. 一些 API 返回元数据质量高，但正文、README、issue 讨论、PDF 内容仍需二次抓取。
4. 对中文、混合语言、长查询、具体错误信息等场景，垂直 API 质量波动更大。

因此，新增 API 不一定能显著提升最终答案质量，反而会增加 provider routing、凭证管理、错误处理和降级路径复杂度。

### 维护成本高

每新增一个垂直 API，都需要维护：

1. 凭证配置和热校验。
2. provider schema、错误码、限流策略。
3. 结果归一化和去重。
4. 质量评估和 fallback。
5. 文档、测试和监控。

在没有明确高频场景和稳定收益前，不应把这些复杂度提前固化进工具体系。

## 推荐替代路径

如果需要论文、GitHub 或其他垂直站点内容，优先使用现有链路：

1. 用 `web_search` 找到候选页面、仓库、论文页、PDF、文档入口。
2. 用 `web_fetch` 直接抓取目标 URL。
3. 需要多页信息时，用 `web_crawl` 从可信种子页面受控扩展。

`web_fetch` 已经具备更强的页面获取能力，适合绕过单一 API 的局限：

1. 支持动态页面抓取。
2. 支持正文抽取和 markdown 化。
3. 支持文件类型识别和文件内容交付。
4. 对常见反爬、重定向、页面阻断有更完整的处理链路。
5. 能直接获取 API 通常不会返回的正文、README、文档、release note、issue 详情、论文 PDF 内容。

## 典型用法

### 查论文

推荐流程：

1. `web_search` 搜索论文标题、作者、关键词或 DOI。
2. 优先选择论文官网、arXiv、publisher page、PDF URL。
3. `web_fetch` 抓取摘要页或 PDF。
4. 需要作者主页、项目页、补充材料时，再对明确 URL 使用 `web_fetch` 或小范围 `web_crawl`。

不推荐本轮新增论文 API 的原因是：最终仍经常需要抓取 PDF、项目页或作者页，单独搜索 API 只能解决一小段链路。

### 查 GitHub

推荐流程：

1. `web_search` 搜索仓库名、错误信息、包名、issue 关键词。
2. `web_fetch` 抓取 repository README、issue、pull request、release 或源码文件页面。
3. 对仓库文档站点或 wiki，可用 `web_crawl` 从入口页受控抓取。

不推荐本轮新增 GitHub API 的原因是：API 限流明显，code search 权限和质量不稳定，而且回答质量通常取决于 README、issue 讨论和文档内容，而不是搜索 API 的元数据。

## 后续重新评估条件

只有满足以下条件时，才建议重新考虑新增垂直搜索 API：

1. 出现明确高频场景，且通用搜索 + `web_fetch` 无法稳定覆盖。
2. 有稳定 API quota、凭证管理和限流策略。
3. 垂直 API 的召回或排序质量经过实测明显优于现有链路。
4. API 返回内容能减少后续抓取步骤，而不是只增加一个入口。
5. 能复用现有 `web_search` provider routing 和结果归一化机制，不引入平行体系。

本轮结论是：优先强化通用搜索、抓取和内容处理能力，而不是增加质量收益不确定的垂直 API。
