web_search 数据模型与流转图

这份图只描述当前 web_search 业务语义：工具参数如何变成 SearchManyRequest，Coordinator 如何规划、调度 provider、融合排序、追加 Wikipedia groundings，最后如何缓存 receipt、生成 candidate pages、citations 和 ranked evidence。

Overview

web_search 是“召回候选”，不是网页正文读取器

它返回搜索引擎候选证据：title、url、snippet、source_id、candidate pages、citations 和可选 Wikipedia 背景对齐。网页正文必须由后续 web_fetch 读取。

工具层

queriesmodeobjective

解析输入、预算、domain filters、custom provider 配置和 Wikipedia keywords，构造 SearchManyRequest。

Coordinator 层

SearchPlanProviderCallSelectorRanking

构建查询计划，选择 default/custom provider，异步 Wikipedia groundings，收集 VariantSearchResponse 后融合精排。

Tool 1/3

WebSearchTool 输入校验与预算控制

工具层的第一职责是把模型输入收敛成可执行搜索请求，所有模式都有固定输出预算。

fast

1 个 query，candidate_page_limit=0，source_display_limit=10，适合快速事实和官方站点。

normal

1-2 个 query，candidate_page_limit=5，ranked_evidence_limit=6，适合中等复杂检索。

deep

2-4 个 query，candidate_page_limit=12，ranked_evidence_limit=8，适合深度研究和交叉验证。

dataclass字段语义
OutputBudgetmin_queries/max_queries/candidate_page_limit/source_display_limit/ranked_evidence_limit/suggested_fetch_limit决定本次搜索召回、展示、候选抓取建议和精排输出规模。
DomainFiltersallowed_domains/blocked_domains工具层解析的域名过滤条件，搜索召回后执行。
Tool 2/3

SearchManyRequest 是 Coordinator 的唯一业务请求

工具层把 queries、mode、provider_mode、user_id、credential、wikipedia_keywords 打成强类型请求，Coordinator 不直接读取 tool kwargs。

SearchManyRequest

queries/mode/provider_mode/user_id/custom_provider_credential/wikipedia_keywords

custom 模式必须携带 user_id 和 credential；default 模式不需要 credential。

Custom Provider 策略

custom 不 fallback 到 default。custom 配置不可用时工具层直接返回错误；default 模式不会被 custom 分支拦截。

强边界：search_config.provider_mode == CUSTOM 才构造 CustomProviderCredential。否则 provider_mode 固定为 default。
Planning

SearchPlan 把多 query 编译成 QueryVariant

查询规划层把归一化 queries 变成带 role、max_results、weight 的独立变体，同时保留 Wikipedia 背景关键词。

QueryVariant

id/text/role/max_results/weight

底层 provider 只看到 QueryVariant，不关心原始工具参数。

SearchPlan

mode/query_variants/wikipedia_keywords

是 provider call 选择器的输入。Wikipedia keywords 不参与 provider 搜索结果融合，只作为背景对齐任务。

语义：wikipedia keywords 要是英文短实体或概念；它产生 Background Groundings，不是 candidate page。
Provider Routing

ProviderCallSelector 决定 default/custom 召回路径

default 模式先跑 FourGet，再根据结果决定是否补充 Serper；custom 模式只跑 CustomProviderRunner。

FourGet

平台内置默认召回通道。接收 default_calls 的 QueryVariant。

Serper

default 模式补充通道。只在 selector 认为需要 supplement 时调用。

Custom

用户自定义私有 provider。失败抛 CustomSearchProviderUnavailableError，不降级。

dataclass字段语义
VariantSearchResponsevariant/response/cache_hit单个 QueryVariant 对应的 provider 返回包，是排名融合的输入。
SearchResponsequery/source/results/metadataprovider 层或融合后的统一搜索响应。
SearchResulttitle/url/snippet/metadata最小网页候选证据，不含网页正文。
Groundings

Wikipedia Groundings 是并发背景对齐链路

如果 SearchPlan 含 wikipedia_keywords，Coordinator 会并发启动 WikipediaRunner；主搜索全空时取消该任务。

WikipediaGroundingResult

keyword/title/extract/url/cache_hit

用于实体消歧和术语背景，不参与 SearchResult 排序，也不是 web_fetch 候选。

使用边界

Background Groundings 不能覆盖当前 web search results，不能作为已抓取页面正文引用。

并发关系：groundings_task 与 provider recall 同时进行；只有主召回有结果时才等待并打包 groundings。
Ranking

多路响应进入 SearchResultRankingPipeline

Coordinator 将 collected_responses 交给 ranking pipeline，完成候选归一化、去重、域名多样性和最终 reranked order。

merged_limit

由 MERGED_CANDIDATE_LIMIT[mode] 决定不同模式候选合并窗口。

domain diversity

默认每个域名最多保留 2 条，降低单站点霸榜。

reranked order

最终 SearchResponse.results 已经是融合排序后顺序。

强关联：后续 CandidatePage、Citation、source_id 都必须基于最终 reranked results 生成，不能用 provider 原始顺序。
Domain Filters

Domain filters 在最终融合结果之后执行

allow-list 和 block-list 都作用于最终 SearchResponse.results。过滤统计会写入新的 metadata 副本，避免原地污染共享对象。

allowed_domains

只保留命中 allow-list 的结果。输入会 normalize 成裸域名。

blocked_domains

剔除命中 block-list 的结果。可与 allow-list 同时存在。

数据写入位置语义
domain_filtersSearchResponse.metadata记录 allowed、blocked、before_count、after_count 等过滤信息。
notestool 输出文本用于提示查询归一化、结果截断、过滤导致为空等用户可见状态。
Candidate Pages

CandidatePage 是 web_fetch 的候选入口，不是已抓取内容

normal/deep 会从 reranked results 中选出可抓取候选。fast 模式 candidate_page_limit=0，不建议 web_fetch。

CandidatePage

source_id/title/url/domain

source_id 来自最终展示顺序，web_fetch 应使用 search_content_id + source_ids 继续读取正文。

Citation

source_id/title/url/domain/order

order=reranked 明确 citation 编号来自融合排序后顺序。

边界：CandidatePage 只代表“可以抓取”，snippet 仍然是搜索引擎预览，不是页面正文。
Content Store

normal/deep 会缓存搜索证据包并执行 evidence ranking

工具层把搜索 artifact 写入 ContentStore，得到 content_id/receipt；如果传入 objective，则基于缓存内容运行 evidence ranking，生成 ranked_search_evidence 和 suggested_fetch_source_ids。

ContentReceipt

包含 content_id、chunk_count、content_type、metadata。metadata 内 citations 必须可 JSON 序列化。

EvidenceRankResult

基于 objective 对 search artifact 分块精排，输出 source_id、snippet、score、term_hit_stats。

suggested_fetch_source_ids

从 ranked payload 中截取，受 mode 的 suggested_fetch_limit 控制。

强关联：search_content_id 是后续 web_fetch_by_source_id 的路由锚点；source_id 必须匹配 cached artifact 中的 reranked results。
Output

最终输出分为可读文本和结构化 receipt

模型看到的是 evidence pack；系统保留 content receipt，供后续 web_fetch、tool_content_read 或 evidence_rank 继续使用。

Fast 输出

返回 sources 和 snippets，不返回 candidate pages；重点是低成本快速证据。

Normal / Deep 输出

返回 search_content_id、ranked_search_evidence、suggested_fetch_source_ids、candidate pages、citations、notes。

模型使用规则：如果需要页面正文，用 suggested source_ids 调 web_fetch；不要把 snippet 当作全文证据。

Strong Links

必须保持稳定的强关联关系

这些关系决定 web_search 后续能否正确 fetch、引用、缓存和追踪 provider 行为。

custom 不降级

custom provider 配置错误或运行失败必须返回 custom unavailable，不自动走 default provider。

source_id 来自最终排序

CandidatePage、Citation、ranked_search_evidence 都必须基于 reranked results 枚举。

content_id 是后续路由锚点

search_content_id 连接 cached artifact、web_fetch_by_source_id、tool_content_read 和 evidence_rank。

metadata 边界

domain filter 等后置写入应创建 metadata 副本；receipt metadata 必须 JSON-safe。

Wikipedia Groundings 边界

groundings 只提供背景，不参与候选页面集合，不应替代搜索结果或 fetched page body。
