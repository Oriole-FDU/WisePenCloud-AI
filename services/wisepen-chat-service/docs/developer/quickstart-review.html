WisePen Chat Service 快速上手与 Review

这份 quickstart 只做一件事：让第一次接手当前仓库的人，在最短路径上看懂真实运行结构、核心工具链和文档落点。稳定规则以 docs/team/ 为准，这里负责“先看哪里”。

先看什么

理解工具系统

先读 src/chat/container.py、tools/core/registry.py、tools/core/execution/executor.py、tools/tool_output_renderer.py、tools/tool_output_cache.py。

理解核心读取链

读 tool_content_read_tool.py、tool_content_read/service.py、tool_content_sequential_read_tool.py、tool_content_store/store.py。

理解外界信息链

读 web_search_tool.py、web_fetch_tool.py、web_crawl_tool.py、document_parse_tool.py。

理解基础设施

读 utils/ranking_engine/、utils/chunking_engine/、tools/web_tools/web_content_cache/。

代码地图

关注点路径说明
DI 入口src/chat/container.py当前唯一应用级依赖图入口，工具注册也从这里看。
Tool 契约src/chat/application/tools/core/definition.pyToolDefinition、ToolPolicy、ToolParametersSchema。
Tool 可见性src/chat/application/tools/core/registry.py控制本轮模型实际看到哪些工具。
Tool 执行src/chat/application/tools/core/execution/schema/context preflight、超时、错误包装。
统一渲染src/chat/application/tools/tool_output_renderer.py普通 Python 返回值和 ToolReturn 都从这里进 XML。
统一缓存src/chat/application/tools/tool_output_cache.py只处理 cacheable_texts，大文本转 cnt_*。
内容存储src/chat/application/tools/common/tool_content_store/短期大文本存储、chunk/index、receipt。
核心读取工具src/chat/application/tools/session_tools/当前只保留跨文档检索和单文档顺序阅读两把工具。
URL 内容缓存src/chat/application/tools/web_tools/web_content_cache/web/document 共用的 URL 级缓存边界。

主执行链

container-> ToolRegistry-> ToolScope-> LLM schemas-> ToolExecutor-> ToolOutputRenderer-> ToolOutputCache

业务工具本身应该尽量薄：写清 schema、边界和 service 调用。XML 渲染、缓存、receipt、会话隔离不是每个工具各自重做的事情。

核心读取链

工具用途边界
tool_content_read跨一个或多个 cnt_* 做全局检索只支持 ranked_expand / regex_match，返回全局有序 matches。
tool_content_sequential_read顺序继续读一个 cnt_*只接受单个 content_id，按 offset + limit 读。
当前仓库的核心读取心智模型已经收敛为两类动作：跨文档检索，或单文档继续阅读。不要再按旧思路寻找 evidence_rank 或 tool_content_batch_read。

外界信息链

web_search
  -> search_ref
  -> web_fetch(mode="from_search_results")
  -> cnt_*
  -> tool_content_read / tool_content_sequential_read

direct HTML URL
  -> web_fetch(mode="from_direct_urls")
  -> cnt_*
  -> session read tools

direct file URL
  -> document_parse(mode="from_direct_urls")
  -> cnt_*
  -> session read tools

unknown/search file URL
  -> web_fetch
  -> tfile_*
  -> document_parse(mode="from_web_fetch")
  -> cnt_*

web_fetch 和 document_parse 在 URL 缓存、fetcher 和 source metadata 上共享边界，这是当前仓库刻意保留的核心体系耦合，不是待拆耦合问题。

新增工具

  1. 先确认功能应该落在现有域，还是确实需要新域。
  2. 先写 ToolLLMSpec.description 和 ToolParametersSchema，把触发边界写清。
  3. 普通结果直接返回普通 Python 值；只有大文本才返回 ToolReturn。
  4. 大文本一律通过 cacheable_texts 进入统一缓存切面。
  5. 需要工具实例时再进 container.py 注册。
  6. 同步更新 docs/tools/ 和必要的 docs/team/ 规则。

返回与缓存

情况返回方式说明
短结构化结果dict / dataclass / list统一 renderer 会递归处理。
大正文ToolReturn(..., cacheable_texts=...)统一 cache 决定内联还是转 cnt_*。
读取窗口普通结构读取工具只消费已有 cnt_*，不再生成新 receipt。

当前 content_receipt 对模型可见字段已经收敛，不再暴露 read_action 和 read_modes。

文档定位

  • docs/team/：长期工程规则，review 以这里为准。
  • docs/tools/：当前已注册工具的真实契约。
  • docs/important/：已经落地且需要长期追溯的关键变更。
  • docs/todo/：即将实行的事项，不放完成项。
  • docs/plans/：有价值但短期不做的规划。
  • docs/ai_assist/：单次任务的 AI 接手文档，文件名必须精确反映任务。

Review 清单

  • 是否复用了统一渲染、统一缓存和统一引用协议。
  • 是否把大文本放进 cacheable_texts，而不是塞进普通 dict。
  • 是否误把 URL cache 和 ToolContentStore 混为一谈。
  • session 工具是否保持“跨文档检索 / 单文档顺序读”这两个清晰边界。
  • 是否把真实稳定规则沉淀到了 docs/team/ 或 docs/tools/，而不是堆进临时计划。

当前仍未完成的长期事项：ToolPolicy.allow_parallel 还没有真正进入 dispatcher 调度逻辑，这仍是活跃规划，不是已完成项。
