# 共享引擎与开发流程规范

本文约束团队在接入共享引擎、选择实现落点和扩展工具链时应遵守的开发边界。

它不是 utils 盘点表，也不是工具用法文档。它回答的是：

- 什么时候应该接入共享引擎
- 什么时候不应该自己再造一套
- 共享引擎和业务工具的职责边界在哪里
- review 时应该从哪些角度判断边界是否被破坏

## 共享引擎边界

当前最关键的两类共享引擎：

- `ranking_engine`
- `chunking_engine`

它们都是**共享基础能力**，不是业务工具。

### Ranking Engine

只负责候选排序，不负责：

- 读取 `ToolContentStore`
- 抓网页
- 解析文件
- 生成模型输出
- 决定业务流程

业务侧职责：

1. 把业务对象映射成 `RankCandidate`
2. 调用合适的 pipeline
3. 把排序结果映射回业务输出

### Chunking Engine

只负责把文本切成可读取、可检索、可定位的 chunk，不负责：

- 文档解析
- 网页抓取
- 排序
- Redis 持久化
- XML 渲染

业务侧职责：

1. 提供已归一化文本
2. 选择正确 pipeline
3. 消费 chunk / index 的稳定字段

## 开发流程判断顺序

新增工具或改造共享能力时，先按这个顺序判断：

1. **这是团队长期规则吗**
   - 是：放 `docs/team/`
2. **这是当前已完成且要长期追溯的关键变更吗**
   - 是：放 `docs/important/`
3. **这是当前工具的使用边界吗**
   - 是：放 `docs/tools/`
4. **这是共享实现入口和能力盘点吗**
   - 是：放 `docs/team/05-utils-inventory.md`
5. **这是近期要做的执行项吗**
   - 是：放 `docs/todo/`
6. **这是短期不做但仍有价值的规划吗**
   - 是：放 `docs/plans/`

## review 时怎么判断是否重复造轮子

以下情况优先复用共享能力：

- 需要 chunk / section / page / anchor 索引
- 需要候选排序、融合、rerank 或多样性控制
- 需要文件类型识别
- 需要 HTML / 表格转 Markdown
- 需要轻量 LLM query / embedding helper

以下情况不要抽成共享引擎：

- 单个工具私有且短生命周期的局部逻辑
- 只做一层机械转发的 helper
- 只在一个调用点存在、没有清晰边界收益的临时适配

## review 清单

- 新逻辑是否真的需要共享能力
- 是否已经存在合适的共享入口
- 是否把业务 IO、权限、渲染逻辑塞进了共享引擎
- 是否把共享引擎内部字段暴露成长期协议
- 文档是否把“规则”和“能力盘点”写到了正确位置
